# Spec: validation checks, freshness and monitoring

Thresholds below are defaults; each can be overridden per source group or indicator in config and every evaluated value is stored in `ops.validation_result` (check id, severity, metric, threshold). Severity: `error` blocks the load of that source group (or raw object); `warn` loads and alerts; `info` records only.

REV-01, REV-06 and REV-07 interplay (T1 alignment, round 6): for each raw object the check family is chosen ONCE, by the group: flag `reestimating` -> REV-06; else flag `edition_ordered` (named editions) -> REV-07; otherwise REV-01. The two flags are mutually exclusive (source-config rule 27, DDL CHECK), so the choice is never ambiguous. All three count only material revisions; non-material differences are REV-05 noise. The class decision and the counts are stored in `raw_load.detail`. Only REV-01 and the REV-06 cap can block an object; REV-07 never does.

Export checks (run in `export`, specified in `docs/specs/dashboard-export-spec.md` section 10; results recorded through `record-export`): EXP-01 schema conformance, EXP-02 no PROJ rows / comparison series / input and support indicators / global series in per-country files, and (round 5) no input or comparison `series_id` in `revisions/*` (the revision view is restricted to headline mappings of `kind = 'indicator'`), EXP-03 metadata completeness, EXP-04 row counts against `curated.v_headline_obs_published`, EXP-05 scorecard numbers equal `*_published` tables, EXP-06 size budgets, EXP-07 no secret-like strings, EXP-08 determinism, EXP-09 withheld-source non-leak including derived values. Severity `error` fails the `export` step and the deployment. The export runs under the read-only role `mm_reader` (there is no `mm_export` role). EXP-10 (round 4): in refresh mode the `analysis_run_id` read by the export must belong to the same `ingest_run_id` as the current run, otherwise the export fails (a stale analysis must not be republished under a fresh build time). Round 6 (ADR-012): the run is read from `analytics.v_run_published` (the row with the greatest `analysis_run_id` for the supplied `ingest_run_id`); no row means EXP-10 fails.

## 2. Release-calendar-aware freshness (feed health)

Inputs per series group (`release_calendar.yaml`): `frequency`, `typical_lag_days`, `tolerance_days`, optional explicit `dates`.

Definitions, evaluated at run date `T`:
- `expected_period_end` = end of the latest reference period `P` with `P.end + typical_lag_days <= T`. If explicit publication `dates` are configured, it is the end of the latest period published on or before `T`.
- `latest_period_end` = maximum `ref_period_end` among non-projection headline observations of the series (rows with `value_status = 'MISS'` count as published periods for feed health, because the source did publish the period).
- Per series state:
  - `fresh`: `latest_period_end >= expected_period_end`, or `T` is still within `tolerance_days` after the normal publication date of the expected period;
  - `late`: one period behind and beyond tolerance;
  - `stale`: two or more periods behind, or no new period for more than twice `typical_lag_days` beyond tolerance;
  - `broken`: the last fetch outcome for the series' request was `error` or `blocked` in two consecutive runs.
- Group state: `broken` if any core-indicator series is `broken`; `stale` if more than 20 % of its series are `stale`; otherwise the worst of `late`/`fresh` by majority.
- Known permanent exceptions (for example OECD Japan CPI ending 2021-06) are config entries `known_stale: true` with a note and are reported as `info`.

## 3. Ranking staleness (not feed health)
Computed in `analytics`: `age_days = run_date - ref_period_end` of the latest observation WITH a value (a later `MISS` period does not reset the age); `is_stale = age_days > limit(staleness_class)`. Limits per D14: MKT45 = 45, SURV75 = 75, ACT120 = 120, Q270 = 270, A730 = 730, TRI1460 = 1460, EVENT = 730 (no active row uses it). Stale values are displayed, flagged, excluded from ranks and never deleted. D14 is user-approved and is not changed by this design. Option `release_lag_aware` per indicator, `stale_limit_days = max(class_limit, typical_publication_lag_days + tolerance_days)` (analytics spec section 8, PROPOSED AMENDMENT P5), for annual indicators with long publication lags (A12, A14, A22): the global default is false; the option is on for a named list of indicators, and the list is pending the user (plan OQ-10). The coverage diagnostic COV-01 (section 1) reports where the limits exclude values on arrival.

## 4. Alert management
- Issue title key: `[<family>] <source group or check family>`; labels `pipeline`, `data-quality`, `source-drift`, `freshness`, `manual-action`.
- Open when a check at `warn`/`error` fails; comment with run URL and metric on each repeat (no new issue); close with a comment when the next run passes. Cap: 20 new issues per run; the remainder summarised in one `[summary]` issue.
- Alert content never includes secrets, URLs with credentials or raw data dumps; it includes check id, metric, threshold, run URL, affected group/series ids (at most 20 listed).
- Early-warning alerts (`analytics.alert`, z-score levels) are data products shown in outputs; they do not create issues in v1.

## 5. Run summary (`ops.run_summary` and `ops/heartbeat.json`) and dead-man detection
Per run: groups with status (`ok|partial|failed|skipped_*`), counts (new raw objects, new observations, revisions, tombstones, rejected rows, `MISS` rows), unloaded backlog (from `ingest.v_raw_unloaded`), Neon connect time, runner-to-database clock offset, database size, durations, export status (recorded by `record-export` into `ops.export_status`). `heartbeat.json` contains only run id, UTC timestamp and group statuses (no data values).

Detection of a silently disabled schedule (A6) must not depend on a scheduled workflow, because all scheduled workflows are disabled together. Fallback ladder (full text and the time-boxed AC-OPS-4 in workflows spec section 9):
- (a) heartbeat commit by the schedule itself (`finalize`); whether it counts as repository activity, and whether `GITHUB_TOKEN` may push to a protected default branch, are [UNVERIFIED] (BB1, BB26) and are measured by AC-OPS-4. A heartbeat from a non-scheduled path (`ingest-manual`, dispatch) is not relied on.
- (b) documented human check on the 2nd of each month: the Actions tab shows a monthly-refresh run for the 1st, `ops/heartbeat.json` has a new commit, the stale banner is absent and no `pipeline` issue is open. This is the only level that does not depend on GitHub's scheduler.
- (c) optional external free dead-man ping [OPTION, UNVERIFIED; not adopted; needs an ADR and the user's decision, design Q15].
The dashboard stale banner (round 5: the manifest's `known_cutoff`, not `generated_at`, older than 45 days, computed in the visitor's browser; a failed `analyze` must not be hidden behind a fresh build time) is a further signal that needs no workflow. FRESH-02 and the "overdue" status apply only when some workflow still runs (for example `ingest-manual`, `ci`, or a manual dispatch).

## 6. Acceptance criteria
- AC-VAL-1: each check ID has a unit or db test with a passing and a failing fixture.
- AC-VAL-2: a fixture with a changed base period triggers META-02 and results in a new series version only after an accepted `drift_event`, never in place; the deferred series then loads from stored raw.
- AC-VAL-3: a fixture with 25 % of keys materially revised in a group without the `reestimating` flag (and not `edition_ordered`) triggers REV-01 and loads nothing for that object (it stays archived-but-unloaded); the same fixture in a group with the group flag `reestimating` set, below the cap loads with `revision_class = 'reestimation'` and REV-06 `info`; above the cap REV-06 blocks it; the same fixture in a named-edition group (`edition_ordered`, round 6) loads, see AC-VAL-14.
- AC-VAL-4: a freshness test table (frequency, lag, tolerance, run date, latest period -> state) with at least 12 cases, including quarter ends and WEO months, passes.
- AC-VAL-5: repeated failure across two runs updates one issue (no duplicates) and recovery closes it (mock GitHub API).
- AC-VAL-6: every `error` result leaves no partial load for that object (transaction test) and does not advance `request_state`.
- AC-VAL-7 (A4): REV-05: a float-noise difference creates no row and increments the suppressed counter; DB-02 projection test: monthly sizes 600, 640, 680, 720, 760, 800 MB trigger the projection warning; DB-05 blocks an object above `max_insert_rows_per_load`.
- AC-VAL-8 (A2, A5): ORD-01, ORD-02 and LOAD-01 each have a pass and a fail fixture (backlog age 0.5 day, 2 days, 41 days).
- AC-VAL-9 (B7, rewritten in round 5, PROPOSED P20): COV-01 fixtures. (a) 20 qualifying entities (first stored period has `load_kind = 'new_period'`) of which 6 have `age at first availability > limit` -> 30 %, warn; 4 of 20 -> 20 %, no warn. (b) The same 20 entities with every first period stored as `initial` -> `n_qualifying = 0`, state `not_yet_measurable`, no warning, `status.json.validation` shows "not yet measurable". (c) 15 `initial` plus 5 qualifying entities, `cov_min_entities = 10` -> `not_yet_measurable`, `n_qualifying = 5` reported. (d) the D14 limits are unchanged in config.
- AC-VAL-10 (A10): FRESH-03 test: with no October edition file, no issue on 24 October, an issue on 25 October (the preflight day and the configured `remind_on`), an escalation 45 days after 1 October; the April case likewise. A config with `remind_on.day = 26` is rejected (source-config rule 11).
- AC-VAL-11 (B5): COMP-05 test for missing, stale and currency-mismatched support inputs (X01/X02), each resulting in n/a and never in a substituted denominator.
- AC-VAL-12 (T1 alignment, materiality; rewritten in round 5): with `published_decimals = 1`, a revision of exactly 0.05 is within the comparison rule (half a unit) and is not counted by REV-01 (counted by REV-05), a revision of 0.1 is counted; for a ratio-dimension unit with `materiality_abs` 0 the same holds, and the relative term is not applied; a 25 % share of material revisions triggers REV-01; the same share of immaterial ones does not.

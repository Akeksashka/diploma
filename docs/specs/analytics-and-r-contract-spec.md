## 1. Inputs, as-of rule and reproducibility
- Analytics read only `curated.v_headline_obs_observed` (latest vintage per key as of the run's cutoffs, `role = headline`, `value_status <> 'PROJ'`, `quality_flag = 'ok'` or overridden `include`, excluding rows with an `exclude` override). Rows with `load_kind = 'import'` (archive imports of older editions, PROPOSED P22) never reach this view. Rows with `value_status = 'MISS'` (the source published the period as missing, confidential or not available; `value` NULL) are returned as NA: they are never ranked, never alerted and never a value in an alert window; the snapshot of an (indicator, entity) takes the latest row WITH a value, so a later `MISS` period neither supplies a value nor resets the age used for staleness (a series whose latest periods are all `MISS` ages out and is stale like any other). Comparison-role series (A02b, A02c) are read by a separate view and never enter ranks (D18). Auxiliary inputs (`kind = 'input'`, support indicators with `is_support`, for example X01 nominal GDP) are read through the same view and used only inside transforms (section 3).
- Cutoffs (round 5, replaces "`known_cutoff` = start time of the analysis run"). At the start of `analyze`, in one short transaction on a direct connection, the run takes `pg_advisory_xact_lock(hashtext('mm-load'))` (the loader's lock; it waits for any in-flight load to commit) and reads `known_cutoff = load_cutoff = clock_timestamp()` from the DATABASE, not from the runner. The as-of reading uses `fn_observation_asof(known_cutoff, load_cutoff)`. Every load that committed before the cutoff has `loaded_at <= load_cutoff` and every later load has `loaded_at > load_cutoff` (ADR-002; the loader reads its `loaded_at` after taking the same lock, ingestion spec step 1b), so the pair identifies exactly what the run could see. A runner-clock cutoff, or `loaded_at` taken at transaction start, would let a load that started before the cutoff and committed after it be counted in the reproduction. Test AC-ING-15.
- History used for alert windows: `ref_period_start >= 1991-01-01` (D4).
- Reproducibility (replaces the earlier claim that an earlier cutoff always reproduces the earlier result; B11, second round). What is versioned and how:
  - `ref.series_map`, `ops.quality_override` (and the `ref.inheritance_rule` rows) hold the current configuration with business validity `valid_from`/`valid_to`; every change is mirrored by trigger into the append-only `ref.config_history`, and the as-of reading uses `ref.fn_config_asof(table, config_asof)` (round 4: single history model; the earlier "supersede by insert, filter on `recorded_at`" wording conflicted with the one-headline exclusion constraint and the DDL). `ops.quality_override` is insert-only; the latest row per target with `recorded_at <= config_asof` applies. Round 5: `ref.domain`, `ref.entity` and `ref.source` (`publish_site`, `archive_mode`) are also mirrored, because a domain's ranked flag, an entity's `is_ranked` and a source's publication flag change published results.
  - Indicator parameters (`rank_mode`, `good_dir`, targets, thresholds, staleness options, coverage and alignment parameters) are configuration in git, not effective-dated in the database. They are reproduced through `analytics.run.params`, which stores `config_sha256` (hash of the `config/` tree) together with `git_sha`; reproducing requires checking out that sha and loading it (`sync-config` into a scratch database or transaction).
  - Additional hashes `mapping_sha256` and `overrides_sha256` are stored in `analytics.run.params` as integrity checks of what was actually read.
  - Guarantee: for the database content with `known_at`/`recorded_at <= known_cutoff` (curated is append-only), and the same `git_sha` and `config_sha256`, `analyze` is deterministic. With a different config the result may legitimately differ. The guarantee is false if any of these histories is overwritten in place, which the DDL forbids.

## 2. Snapshot (per entity and indicator)
For each active, non-dropped indicator with `kind = 'indicator'`: if `scope = 'country'`, each of the 44 non-global entities (42 countries plus the EU27 and EA aggregates); if `scope = 'global'` (for example M24), only `WLD`. Global indicators are therefore not in the per-country snapshot, ranks or scorecards (B6). Inputs and support indicators are not snapshotted. For each row take the headline series' latest observed observation with a value (section 1); record value, `ref_period_end`, `known_at`, `source_release_at`, `age_days`, limit by staleness class (section 8), `is_stale`, `inherited` (ADR-009), `publish` (source `publish_site = 'public'`), `alignment` (section 4.3), and `deviation` for target-distance indicators. Projected values are reported separately and never used here. A03 (WEO forecasts) is descriptive/benchmark-only (section 9, P6): no ranking, no alert.

WEO estimate/projection boundary and A02 (review round 3; PROPOSED AMENDMENT P7; latest-edition rule restated in round 5). The WEO parser maps each year <= the country's `Estimates Start After` attribute [UNVERIFIED for the manual file; confirm on the first real file] to `value_status = 'EST'` and later years to `'PROJ'`. For A02 (NGAP_NPGDP) an output gap is never an outturn: "latest observed" is the latest EST year of the latest WEO edition, labelled `estimate` (`value_kind = 'estimate'`) in snapshot and export; PROJ years are excluded from ranks and alerts. "Latest WEO edition" is determined from the manifest, not from the rows: it is the loaded object of the WEO group with the greatest `raw_object.edition_date` (equivalently its `edition_label`, for example `WEO-2026-10`), ignoring archive imports. It is NOT read from the `vintage_label` of observation rows, because insert-on-change does not re-insert an `EST` (or `OBS`) value that is unchanged in a newer edition, so such rows keep the older edition's `vintage_label` while only `PROJ` rows are re-inserted for every edition. Procedure per entity: let L be the latest edition label; the earliest year of `PROJ` rows with `vintage_label = L` minus one is the last `EST` year (cross-checked against the `Estimates Start After` value recorded in `raw_load.detail` for that object); the A02 value is the latest stored version of that year as of the cutoffs, whatever its row label. Because the order of manual files is enforced by the loader (edition-order rule, ingestion spec step 2a, PROPOSED P22), an older edition committed later cannot become "latest". If the attribute is missing or unparseable, A02 fails closed (n/a) and a `schema_drift` event is raised (check WEO-01). Until P7 is approved A02 is shown as a labelled estimate and not alerted (cautious reading of D18). Test AC-AN-15. Round 6: the WEO group is a named-edition group (`edition_ordered`, `reestimating: false`, ADR-017); a rebasing edition revises history rows as ordinary revisions and is never blocked by the mass-revision rule.

## 3. Transforms (registry keys in `ref.indicator.transform_id`)
`LEVEL`, `YOY` (12 months / 4 quarters / 1 year, on levels or indices), `YOY_PCT_POINT_CHANGE`, `M3M3_ANN` (3-month over previous 3-month, annualised, SA series only), `QOQ_ANN` (SA only), `DIFF12`, `REAL_RATE` (policy rate minus core YoY; an ex-post real rate on backward-looking core inflation, labelled "ex-post real policy rate" in `meta/indicators.json.notes` and the UI; an ex-ante variant only when an expectations series exists, not in v1), `SPREAD_VS_REF` (yield minus Germany/US), `SUM12_PCT_GDP`, `RESERVE_COVER`, `DEV_FROM_AVG`, `GLOBAL_LCU_YOY` (specified, deferred in v1). Registry flags: `requires_sa` (`M3M3_ANN`, `QOQ_ANN`; checked by config rule 8), `inputs` (below).

Rules: never MoM/QoQ on NSA series (use YoY); transforms that need a second series (REAL_RATE, SPREAD_VS_REF) take both from headline mappings and are not computed if either is stale or missing. Currency basis (D7): B1 transforms operate in local units; B2 series are shown in USD levels but never ranked on USD growth; B3 in PPP. A `MISS` period in a transform input makes that period's transform value absent (n/a for that period), never zero.

Transforms with a denominator (B5, second round). Any transform expressing a ratio to GDP (`SUM12_PCT_GDP` and every "% of GDP" stock or flow computed by the pipeline) takes its denominator from a support indicator (`is_support`, never ranked, mapped through `ref.series_map` like any indicator, never in scorecards or the export indicator list). The default denominator is X01 nominal GDP (same currency as the numerator: X01 is nominal GDP in local currency, X02 is nominal GDP in USD). The transform fails closed: if the support series is missing, stale by its own class, of a different currency, of the wrong flow basis (below), or `calendar_basis <> 'CAL'`, the value is not computed (n/a, counted in N not n) and COMP-05 (warn) names the pair. No substitute denominator is ever invented.

| Transform | Numerator | Support input (ref.indicator_input) | Rule |
|---|---|---|---|
| `SUM12_PCT_GDP` | 12-month sum of a monthly flow in a currency C (for example M13 goods trade balance) | X01 nominal GDP in local currency (X02 when C is USD) | `100 * sum12(numerator) / D`, where D is the sum of the four most recent quarterly X01 values whose quarter-end is on or before the numerator's `ref_period_end` (latest vintage as of the cutoffs), each quarterly value being a PERIOD_FLOW (flow-basis guard below); if fewer than four quarters exist, the latest annual X01/X02 with year-end on or before that date; if neither exists or the denominator is stale by the input's own class (Q270 / A730), not computed |
| `RESERVE_COVER` | official reserves, USD, month-end | imports of goods and services, USD (support X03; PROPOSED P17) | `reserves / (imports12 / 12)` in months, where `imports12` is the sum of the last 12 monthly values (PERIOD_FLOW); fallback: latest annual imports / 12; same staleness rule. The conventional 3-month threshold refers to goods AND services. If only goods imports are mapped, the value is labelled `goods_only`, is shown, and the fixed 3-month override is NOT applied to it (goods-only cover is overstated). |
| USD stocks as % of GDP | stock in USD | X02 nominal GDP in USD | numerator over the latest annual (or four-quarter sum) value with end on or before the numerator date |

Flow-basis guard (round 5, PROPOSED P18; no exception since the fix pass). Quarterly national accounts are often published as seasonally adjusted ANNUALISED rates (SAAR: the quarter's level multiplied up to a yearly pace) instead of the level of the quarter itself [UNVERIFIED which countries and datasets do so; to be set per series at mapping time]. Summing four SAAR quarters gives about four times annual GDP, so a `SUM12_PCT_GDP` ratio would be about a quarter of its true value, silently. Therefore `ref.series.flow_basis` (`PERIOD_FLOW` | `ANNUALISED_RATE` | `STOCK` | `NA`; DDL spec, immutable measurement attribute, taken from source metadata or the `expect.flow_basis` of the series map; `NA` or unknown is treated as not proven and fails closed for sums) is checked by the transform: (a) the four-quarter sum and `imports12` require every summed value to be `PERIOD_FLOW`; (b) an `ANNUALISED_RATE` quarterly denominator fails closed with COMP-05 reason `annualised_denominator` (an `ANNUALISED_RATE` numerator that would be summed: `annualised_numerator`; a `STOCK` used as a flow: `invalid_flow_basis`); (c) there is no exception. The user answered design Q48 (2026-10-24) that a single latest annualised value is NOT allowed as a denominator, so the option `annualised_policy: latest_single` does not exist: `ref.indicator_input.annualised_policy` accepts only `fail` (DDL CHECK) and config validation rejects any other value (source-config rule 28, AC-CFG-10). Annual GDP (A frequency) is `PERIOD_FLOW`. This changes the behaviour of approved transforms for affected entities only by turning a wrong number into n/a. Test AC-AN-21.

Denominator age and inflation-regime guard (review round 3; PROPOSED P10). Per transform config `max_denominator_age_days`: for the four-quarter sum the denominator's last quarter-end must be <= 120 days before the numerator's `ref_period_end`; the annual fallback is allowed only when the entity's trailing-12-month YoY CPI < 10 %, else n/a. `inflation_regime_guard`: entities with YoY CPI > `hi_inflation_threshold` (proposed 25 %) or `ref.entity.fx_regime_flag` set (new optional attribute, proposed values `managed`, `multiple`; default NULL) get n/a for USD-flow over USD-GDP ratios and for LCU ratios that use the annual fallback. COMP-05 (warn) names the reason (`denominator_age`, `high_inflation`, `fx_regime`). This changes the behaviour of approved indicators for those entities, hence P10; the guard is ON with these defaults meanwhile (cautious reading). Reason: a lagged nominal GDP overstates a flow/GDP ratio by tens of percent when inflation is 50 % or more. Test AC-AN-13.

Single-currency rule (M13 and similar). The numerator and the denominator must be in the same currency, chosen at mapping time and declared in `ref.indicator_input.currency_match` (`numerator`, `lcu` or `usd`): either LCU trade with LCU GDP, or USD trade with USD GDP, never USD flows over LCU GDP. A mismatch is not converted and not computed (COMP-05). No FX conversion happens inside a transform, except in `GLOBAL_LCU_YOY`. Inputs must be for the same entity. Calendarisation is not implemented in v1. Which indicators use which input is declared in `indicators.yaml` (`inputs:`); the research does not yet assess the sources of X01 and the other support series (required follow-up, design Q22).

Global series (WLD) translated to per-country local currency (B6, second round). Translation is an analytics transform (`GLOBAL_LCU_YOY`), never stored: the stored series is the global USD series on entity `WLD`; the per-country value is derived at analysis time as `P_lcu,t = P_usd,t * FX_t` with FX the entity's M16 month-average LCU per USD (M16 must be mapped for the entity and not stale; the euro-area members use the inherited euro rate and the US has no translation), then YoY on `P_lcu`. In v1 it is not computed: global series are shown in the explorer only (group `global`); enabling per-country translations is the user's decision (design Q23).

`SPREAD_VS_REF` for M18 (B4, second round): the yield spread of a 10-year government bond over the reference (Germany or the US) measures sovereign credit and liquidity risk only when both bonds are in the same currency. Label rule by `ref.entity.currency_code` of the benchmark bond: euro-area members (EUR vs Bund) and entities whose benchmark bond is USD-denominated and compared with UST use the label "yield spread vs Germany/US (credit and liquidity risk proxy)". All others use "local-currency yield differential (includes inflation and exchange-rate expectations; not a sovereign-risk measure)". The label is carried in `meta/indicators.json.notes` per entity. This relabel changes the meaning of the approved wording of D20 (M18 as the free substitute for sovereign-risk spreads) and is therefore a PROPOSED AMENDMENT (section 9, P4); until the user approves, the cautious label above is used for display and M18 is `descriptive_only` for non-comparable entities (there is no separate sovereign-risk domain; M18 belongs to the `fin` domain, selection scorecard table).

Reference benchmark (round 4, PROPOSED P16). Each entity's reference is declared in `indicators.yaml` (`spread_reference: {entity: DEU|USA}`) and sync-config rejects an M18 mapping without one. Default: DEU for euro-area members, non-euro EU members and the UK; USA for all other non-EU entities. DEU and USA are the benchmarks: their spread is not computed (level only, `spread_reference: self`, n/a in spread views), and they are not counted in `n_defined` for the spread. Spreads against DEU and against USA are never ranked in one list: the spread is `descriptive_only` for ranking (P16), shown with its reference.

## 4. Percentile rank and scorecards (D6, D12, D16)

### 4.1 Rank modes (proposed defaults, user to confirm; `ref.indicator.rank_mode`)
- `monotone_good`: percentile-ranked with a fixed orientation: `good_dir = +1` (higher is better) or `good_dir = -1` (lower is better). Higher percentile = better.
- `target_distance`: ranked on `|transformed_value - target|` (or distance to the nearest edge of a band, 0 inside the band), smaller is better, using `ref.indicator_target` (target or band with source note; for output gap A02 the target is 0). Entities without a target row are n/a for that indicator. `good_dir` is 0.
- `descriptive_only`: shown with value, reference date, age, stale flag and alert level; never percentile-ranked; not counted in `n_available` or `n_defined`. `good_dir` is ALWAYS 0 (round 5: the earlier "or +1/-1 if kept only for colouring" contradicted the DDL check, which requires 0). A colour hint for the display is the separate optional column `display_dir` (-1, 0 or +1, NULL = none), exported in `meta/indicators.json`, never used for ranking, percentiles, `n_defined` or alerts.

`good_dir = 0` means "no better direction exists for the level". It is valid only with `target_distance` or `descriptive_only`; a `monotone_good` indicator with `good_dir = 0` is rejected at seeding (config rule and DDL check). `rank_mode` has no default anywhere (P14): the DDL column has no default and sync-config rejects an indicator without it.

The DDL spec now uses these same names (earlier drafts used `monotone`, `target_deviation`, `none`); the mapping is `monotone` = `monotone_good`, `target_deviation` = `target_distance`, `none` = `descriptive_only`.

### 4.2 Ranking inputs

### 4.3 Per-indicator ranking procedure
Run once on the full set and once on the published set (A8), producing `analytics.indicator_rank` / `scorecard` and `analytics.indicator_rank_published` / `scorecard_published`:
1. Candidates: ranked countries (aggregates and WLD excluded, D1) with a non-stale value, rank mode `monotone_good` or `target_distance`, not `inherited`. In the published run, candidates are further restricted to (indicator, entity) pairs whose headline series belongs to a source with `publish_site = 'public'`; every other pair is treated as unavailable. Percentiles, ranks, `n_ranked`, the rank reference period and the spread of the published set are functions of published values only.
2. Rank reference period (B1, second round; replaces the earlier modal-window rule; arithmetic made exact in round 5, PROPOSED P21). Percentile ranks must not mix reference dates far apart (for example August 2026 against June 2026 unemployment, or annual values up to two years apart). Per indicator and candidate set:
   - Sort the candidates' latest `ref_period_end` values in descending order; `rank_reference_period` = the value at 1-based position `p = (rank_period_coverage_pct * n + 99) // 100` (integer arithmetic; `n` = number of candidates, `n >= 1`; `rank_period_coverage_pct` is an integer percent in [1, 100], default 70). This equals `ceil(coverage * n)` without floating point: a product such as `0.55 * 20` can evaluate to a value just above 11 in binary floating point [analyst arithmetic, not run here], and `ceil` would then pick position 12. Examples: n = 10, pct = 70 gives p = (700 + 99) // 100 = 7; n = 20, pct = 55 gives p = 11; n = 3, pct = 70 gives p = (210 + 99) // 100 = 3. With the default 70 this is the latest period for which at least 70 % of the candidates have data. The choice is deterministic. The config key is stored as the integer `rank_period_coverage_pct` (the earlier fraction 0.70 is rejected by config validation).
   - Alignment states stored in `analytics.indicator_snapshot.alignment`: `aligned` (ranked; latest period on or before `rank_reference_period`, within `max_lag_vs_rank_period`); `ahead` (ranked; latest period later than `rank_reference_period`, compared at its latest value, no back-casting); `lagging` (more than `max_lag_vs_rank_period` behind `rank_reference_period`: shown, no percentile, not counted in `n_available` or `n_ranked`); `unaligned` (fiscal-year basis, below; shown, not ranked); `n/a` (indicator not ranked, or no usable value). Round 6: `indicator_snapshot.ref_offset_days` stores `ref_period_end` minus `rank_reference_period` in days for every entity of a ranked indicator with a usable value.
   - An entity whose latest `ref_period_end` is more than `max_lag_vs_rank_period` behind `rank_reference_period` is `lagging`.
   - Every other entity is compared at its latest value. Entities whose latest period is later than `rank_reference_period` are `ahead` of it and are compared at their latest value too (no back-casting); the resulting spread is reported.
   - Fiscal-year basis (review round 3). Series with `calendar_basis <> 'CAL'` (India; WEO fiscal-year items [UNVERIFIED]; Australia/Japan fiscal items) are `unaligned` in rankings: shown, not ranked, reason `fiscal_year_basis` (stored in `indicator_snapshot.alignment_reason`, round 6), not counted in `n_available`/`n_ranked`, and never treated as "ahead" of a calendar-year peer (a fiscal year ending in March is not later than a calendar year). Calendarisation is out of v1. Test AC-AN-14.
   - Proposed defaults, user to confirm: `rank_period_coverage_pct = 70`; `max_lag_vs_rank_period` monthly 92 days, quarterly 190 days, annual 366 days (about one reference period plus a quarter). Both are configurable globally and per indicator.
3. `reference_period_spread_days` = max - min `ref_period_end` among the ranked entities (`aligned` and `ahead`); stored in `analytics.indicator_alignment` and always exported; `n_unaligned` there counts the `lagging` and `unaligned` entities. The dashboard shows the spread next to every ranking (for example "ranked values span 61 days of reference periods") and marks `lagging` and `unaligned` entities.
4. Percentile definition (round 5: ONE formula, PROPOSED P21; the earlier text "(count of values worse than x + 0.5 * count of ties) / n" did not say whether the entity itself is a tie). Over the ranked set R with `n = |R|` entities and a value `x` of entity e:

   `percentile(e) = (W + 0.5 * T) / n`

   where `W` is the number of entities in R with a strictly worse value than `x` and `T` is the number of entities in R with a value EQUAL to `x`, INCLUDING e itself (so `T >= 1`). This is the mid-rank percentile. "Worse" follows the rank mode: lower values for `good_dir = +1`, higher values for `good_dir = -1`, larger `|transformed - target|` (distance) for `target_distance`. Equality is exact on the stored decimals (the values are compared at the series' published precision, never on floats). Properties: the result lies in [0.5/n, 1 - 0.5/n], never exactly 0 or 1; the mean of the percentiles over R is exactly 0.5; n = 1 gives 0.5; all entities tied gives 0.5 for each. Worked example, unemployment rate (`good_dir = -1`, so higher is worse), R = {A 3.0, B 4.0, C 4.0, D 9.0}, n = 4: A has W = 3 (B, C, D are worse), T = 1, percentile (3 + 0.5) / 4 = 0.875; B and C have W = 1 (D), T = 2, percentile (1 + 1) / 4 = 0.5; D has W = 0, T = 1, percentile 0.5 / 4 = 0.125. Mean = (0.875 + 0.5 + 0.5 + 0.125) / 4 = 0.5. Test AC-AN-2.

### 4.4 Domains
Domain eligibility (B3, second round). A domain with fewer than `min_ranked_indicators` (default 3) active indicators that are ranked (`kind = 'indicator'`, `rank_mode <> descriptive_only`, `indicator_domain.is_ranked`) is `descriptive_only`: no percentiles, positions or scorecard ranks, indicators shown only. Domains with `ref.domain.is_ranked = false` (agri D12; global) are likewise unranked. The former `markets` domain held only M16 (itself `descriptive_only`) after the user's Q30(a) decision moved M16 to External; it was empty, and the user dropped it on 2026-10-27 (stated in session; plan OQ-12). No indicator uses it, so it is removed from the domain lists, enums and checks of the specs (the approved selection document, which the design may not edit, still lists "Markets" in its scorecard table; the user amends it in phase 1a). The rule "fewer than 3 ranked indicators means `descriptive_only`" stays for every other domain (P3).

Concept de-duplication (round 4, PROPOSED P15). Within a domain, indicators with the same `concept_id` (A05 and Q08 gross debt; A04 and Q12 government balance) count once per entity: the entity's percentile for the concept is that of the available indicator with the lowest `concept_priority` (quarterly Q08/Q12 before annual A05/A04), and `n_defined` counts the concept once. Otherwise EU members would carry the same concept twice and other countries once. Test AC-AN-20.

Prices consequence (P13): with all inflation-rate indicators `descriptive_only`, `prices` has fewer than 3 ranked indicators and is therefore `descriptive_only` (rule above) until the target table (R7) allows `target_distance`. This conflicts with the approved wording "G01 ranked inside the Prices scorecard" (D12) and needs the user's decision (design Q45).

Per domain and entity for ranked domains: `n_defined` = number of active indicators of the domain with `kind = 'indicator'`, `rank_mode <> descriptive_only` and `indicator_domain.is_ranked` (D16: "indicators available out of those defined"; defined-but-unmapped counts in N, not n; descriptive indicators are not in N); `n_available` = number of those with a percentile for the entity in the chosen set; the domain figure is the mean percentile of the domain's indicators (stored in `scorecard.percentile_rank`; no imputation, no zero-fill); if `n_available = 0` it is NULL and shown n/a. No composite across domains (D6). Only G01 is ranked inside Prices among agri-related items.

What the domain figure is and is not (round 5, wording PROPOSED P21). `percentile_rank` in `analytics.scorecard` and the exports is the MEAN of the entity's indicator percentiles in the domain, not a percentile of the domain: the mean of several percentiles is not uniformly distributed on [0, 1] (it concentrates around 0.5; for k independent uniform percentiles its standard deviation is about 0.289 / sqrt(k) [analyst arithmetic]), so a mean of 0.62 does not mean "better than 62 % of countries". Column names are kept for compatibility; every label, tooltip and document calls it "mean percentile of the domain's indicators" and shows n/N beside it. `rank_position` is the competition rank on this mean among entities that are not `low_coverage`; it is the only like-for-like comparison across entities.

Minimum coverage for display (B8, second round; proposed default, user to confirm; selection D16 leaves the treatment of low coverage open). A mean over available indicators lets a country with 1 of 10 indicators outrank one with 9 of 10. Therefore if `n_available / n_defined < ref.domain.min_coverage_for_rank` (default 0.5; evaluated with integer cross-multiplication where the threshold is stored as a decimal), `rank_position` is NULL and `low_coverage = true`: the mean percentile is shown unranked with the label "n/N" and excluded from `rank_position` and `n_ranked_entities`. `rank_position` is a competition rank (ties share the best position) among entities that have a domain figure and are not `low_coverage`. The 0.5 threshold is a proposed default requiring user confirmation.

Heterogeneous peer sets (review round 3). Each domain score reports `peer_set_size_by_indicator` = {min, max} of `n_ranked` over its ranked indicators, and sets `heterogeneous_peer_set = true` when max/min > 1.5 (example A02: 25 vs 42 ranked countries). Round 6 storage: `analytics.scorecard.peer_set_size_min`, `peer_set_size_max` and `heterogeneous_peer_set` (and the same columns in `scorecard_published`, computed over the published set); the values are per domain and run, so every row of one domain carries the same three values. A coverage-weighted domain figure is NOT adopted. Instead (PROPOSED P8, optional config) `min_coverage_for_rank` also requires that the available indicators include at least one from each declared `core_pillar` when the domain defines pillars (`ref.domain.core_pillars`, default none = rule off). Bias note: missingness is not random; slow reporters (typically emerging economies) are systematically missing, so the mean percentile is computed on a different, more advanced-economy-weighted panel; see the `missing_not_at_random` report in the validation spec (MON-NMAR). The browser peer-group filter in V2 only filters/sorts the full-universe percentile and never recomputes it; the UI labels it "percentile vs all ranked countries".

Standing caveat (PROPOSED P9): percentiles are relative position in the covered panel, not a judgement of structural quality; advanced and emerging economies share one panel (D6). Optional `peer_group_percentile` (precomputed in Python for G7, euro area, non-euro EU, advanced, emerging, same definition as 4.3 step 4 over the peer subset, never computed in the browser) is an optional export item (see dashboard-export-spec).

Euro-area-inherited values: computed and flagged (`inherited = true`) and EXCLUDED from percentile ranks. Decided by the user on 2026-10-27 (stated in session; design Q7 closed, plan OQ-11): this is the documented default, now recorded as the decision, not as a pending default. They remain visible with the flag and are not counted in `n_ranked`.

Stale-on-arrival diagnostic (B7; restated in round 5, PROPOSED P20): for each indicator, `monitor` computes the share of QUALIFYING entities whose latest value was already stale when first seen, i.e. `first known_at of the latest ref_period - ref_period_end > staleness limit`. An entity qualifies only if the first stored version of that latest period has `load_kind <> 'initial'`: the launch fetch stores the whole history at once, so the first `known_at` of an `initial` row is the launch date, not the publication date, and every old value would look stale on arrival. The diagnostic reports `n_qualifying` (and `n_with_value`) and the state `not_yet_measurable` until `n_qualifying >= cov_min_entities` (proposed default 10); only then is the share reported against the warning threshold (default 25 % of qualifying entities) by validation check COV-01, so that the user can reconsider the D14 limits. Indicators with annual lags need up to a year or more of post-launch arrivals before they become measurable; the dashboard shows "not yet measurable" instead of a share. D14 itself is not changed. Indicators A12, A14 and A22 are listed as known risk [UNVERIFIED, from the review; to be confirmed by the diagnostic] (design R24).

## 5. Alerts (D9, D19)
- Window (B10): 240 monthly, 80 quarterly, 20 annual observations of the transformed headline series (observed only, with a value: `MISS` periods are absent from the window, not imputed), trailing, ending at the PREVIOUS observation. The current (latest) observation is excluded from the window used for its own mean, sd, median and MAD. Effect: a spike cannot dampen its own score. With the current observation included, a single outlier in a sample of n values cannot exceed |z| of about (n-1)/sqrt(n) (about 15 for n = 240 but only about 4.3 for n = 20), so annual and quarterly series are the ones most affected; excluding it removes that cap. The cost is that the first observations after a level shift also score high, and a persistent shift keeps alerting until it has entered the window. `n_obs` counts the observations in that window (excluding the current one).
- The z-score is computed on the transformed series (for example YoY), and the window is built from the same transform applied to the same history, so that the current value and the window values are of the same kind (a YoY value is compared with prior YoY values, never with levels). Where a transform needs an input (section 3) the historical transform values use each period's own input, and periods for which the transform cannot be computed are absent from the window (not imputed).
- Methods per indicator: `z` = (x - mean) / sd; `robust_z` = (x - median) / (1.4826 * MAD) for skewed/fat-tailed series (inflation, spreads, FX, credit growth, food/fertilizer prices); `percentile` of own history; `fixed_only` thresholds from `alert_override` with stored rationale. Inputs, support indicators, A03 and `alert.method = none` indicators are not alerted.
- Fixed overrides per entity group (round 5, PROPOSED P19). `alert_override` is a list of entries keyed by `entity_group` (a `group_id` of `ref.entity_group_member`, for example `advanced`, `emerging`, `euro_area`) each with `watch`/`alert` thresholds, a mandatory `rationale` and a `source_note`. Reasons: a single threshold for all 42 countries is not defensible. The 90 % of GDP public-debt line comes from the Reinhart-Rogoff literature and is contested (a 2013 replication critique by Herndon, Ash and Pollin) [UNVERIFIED, background knowledge, not checked this session]; the 60 % line is the euro-area Maastricht reference value, relevant to euro-area and EU members rather than to every economy [UNVERIFIED]; the 3-months-of-imports reserve cover is a legacy rule of thumb that ignores short-term external debt and capital-account exposure, and the IMF's reserve-adequacy (ARA) metric is the usual alternative [UNVERIFIED]. Behaviour meanwhile (until P19 is approved): an override is applied to an entity only if the entity is a member of a group that has an entry WITH a rationale on the run date; otherwise there is no fixed override for that entity and only the z-score rule applies. An entry without rationale is a config error (source-config rule 20). A `goods_only` cover value never gets the 3-month override (section 3). v1 ships with no override entry at all (Q50, 2026-10-24: z-score only for now; extended on 2026-10-27, stated in session, to the BIS credit-to-GDP gap Q06, plan OQ-15); the mechanism exists and is tested with fixture configurations only (AC-AN-23).
- Levels: `alert` if `|z| >= 2.0` in the adverse direction (D19, approved); `watch` if `|z| >= 1.5` (confirmed by the user per the forecasting amendment record U10, but not yet in an approved selection file: carried as a configurable default `watch_z = 1.5`); `none` otherwise. For `descriptive_only` indicators with no adverse direction, both tails are evaluated (|z|) and the direction is reported as `n/a`. Fixed overrides evaluate independently and the stronger level wins; the rule that fired is recorded.
- Short-series rule (pending user confirmation, proposal from the selection): minimum prior observations for any alert: 60 monthly, 20 quarterly, 10 annual; `confidence = low` below the full window (monthly 60-239, quarterly 20-79, annual 10-19 prior observations); `full` with the complete window (240/80/20 prior observations); below the minimum `level = none`, `confidence = none`, `reason = below_min_obs`.
- Non-stationary, autocorrelated and break-prone series (review round 3; PROPOSED P11; D19 thresholds |z| >= 2.0 and watch 1.5 are unchanged):
  - `stationarity_class` per indicator in `indicators.yaml` (stored since round 6 in `ref.indicator.stationarity_class`): `stationary | trending_level | rate_of_change`. For `trending_level` indicators (debt/GDP, unemployment rate level, policy rate, reserve cover) z is computed on DIFF12 (or YoY change), not on the level; `alert_override` fixed thresholds still evaluate on the level. Fix pass 2026-10-25 (user decision): this is the adopted reading. DIFF12 is applied to the indicator's transformed series for the alert window only; the indicator's `transform` is unchanged and nothing in config requires the `transform` to be DIFF12 or YOY_PCT_POINT_CHANGE (source-config rule 29; indicator-parameters spec section 9).
  - Effective sample: overlapping YoY values are autocorrelated, `n_eff` is about n/12 for monthly YoY (n/4 quarterly). Proposed default: the minimum-observation rule and `confidence` additionally need n_eff thresholds, e.g. monthly: at least 60 observations AND at least 5 non-overlapping years; otherwise `reason = below_min_obs`.
  - Regime breaks: window start = max(1991-01-01, entity `regime_start`, optional config for hyperinflation or transition breaks). Persistent shift: after 3 consecutive alerts on the same series the alert carries the label `persistent_shift` (round 4: the window is NOT re-based; re-basing left a window below the minimum-observation rule and silenced alerts for years). Round 5: the label is stored in the new column `analytics.alert.label` (NULL otherwise) and exported as `label`; the `level` keeps its computed value. Alert levels continue to be computed on the unchanged window; `persistent_shift` is a label, and `fixed_only` overrides or a user-set `regime_start` are the way to start a new regime.
  - Tests AC-AN-16 to AC-AN-18.
- `alert.reason` (B10): NULL when evaluated normally; `mad_zero` when `robust_z` has MAD = 0 (level `none`, `z` NULL); `sd_zero` (round 5) when `z` has a window standard deviation of 0, for example a policy rate that was constant for the whole window (level `none`, `z` NULL; dividing by zero and an infinite z are never produced; a fixed override still evaluates); `below_min_obs`; `stale`; `no_window` (no prior observation).
- Not alerted: stale series, projected values, `MISS` periods, series with prior observations below the minimum.
- Withheld sources (A8): alerts for series of sources with `publish_site = 'withheld'` are still evaluated for internal use and stored with `alert.publish = false`; they are excluded from `alerts.json` (built from `analytics.v_alert_published`), and their z, level and reason never appear in any exported file or in the published scorecards.

## 8. Ranking staleness and the `release_lag_aware` option
Default (approved D14, unchanged): `is_stale = age_days > limit(staleness_class)` with the class limits listed in the validation spec section 3.

Option `release_lag_aware` (per indicator, in `indicators.yaml`, stored since round 6 in `ref.indicator.release_lag_aware`): the global default is `false`; the option is on for a named list of indicators, and the list is pending the user (plan OQ-10; the user switched the option on in design Q31 but has not given the list; the draft list is in the indicator-parameters spec section 7 item 7; on 2026-10-27 the user asked for a row-by-row proposal instead of deciding, which is `docs/specs/release-lag-and-split-proposal.md` section 2 and is a proposal only). When on for an indicator: `stale_limit_days = max(class_limit, typical_publication_lag_days + tolerance_days)`, using the lag and tolerance from `release_calendar.yaml` for the series' group. Rationale: annual indicators with long publication lags (A12 health expenditure about 2 years, A22, A14) would otherwise be stale on arrival (COV-01). When the option is on for an indicator, the snapshot records `stale_limit_days` and `limit_source = 'release_lag_aware'` (column `indicator_snapshot.limit_source`; `'class'` otherwise). Turning it on for an indicator changes the effect of the approved D14 limit for that indicator, which is why each member of the list needs the user's confirmation (PROPOSED AMENDMENT P5).

## 10. Forecast layer (DEFERRED TO v2; nothing in this section is part of v1)
Status (user decision, 2026-10-25): forecasting, nowcasting, forecast evaluation, probability alerts and the model layer are version 2. Nothing in this section is specified, built, tested or exported for v1, and no v1 task may depend on it. The earlier text (rounds 1 to 5) that described "hooks" is withdrawn.

What was removed and why:
- The table name `forecast_vintage` is withdrawn. Two names for one thing existed (this spec versus ADR-011's `forecast.edition` / `forecast.projection`). The storage design, names and keys for forecasts are defined only by ADR-011, which is `proposed`, gated and stays `proposed` until the user approves it in a v2 design round; when that happens this section is rewritten to refer to it.
- The evaluation vocabulary (`first_stored_release`, `mature_after`, `actual_vintage`) belongs to ADR-011 and the forecast evaluation of v2; v1 does not use `first_stored_release` anywhere (the V4 vintage view uses the term "earliest stored version" and fixed text, export spec section 7).

What v1 does keep (these are existing v1 rules, not forecast features):
- WEO projections (A03) are loaded as `PROJ` rows in `curated.observation`, one set of rows per edition, because for `PROJ` rows the comparison row is the latest row with the same `vintage_label` (ADR-002, DDL I-CUR-3). They are excluded from ranks, alerts and the v1 dashboard. Archive imports of older WEO editions are stored with `load_kind = 'import'` (P22). Both rules are interim v1 rules; ADR-011, if approved for v2, would move WEO projections into its own store and retire them by a v2 migration.
- Backtests: any evaluation that uses history reconstructed from the current data (`load_kind = 'initial'`) is labelled "revised-data" (D10, AC-AN-3). A separate `pseudo_real_time` / `real_time` vocabulary is a v2 matter.

Not in v1 (for the record): forecast and nowcast outputs (FT01-FT12), benchmark editions B01-B10, the probability targets, accuracy metrics, the model layer, forecast dashboard pages, inflation target metadata (selection amendment R7; M06/M07 stay `descriptive_only`), and the research follow-ups R1-R9.

## 1. Principles
1. Read-only, derived, rebuildable: the export is a pure function of `(analysis_run_id, known_cutoff)` and the database state. It writes nothing to Neon. Its result (status, durations, bytes read, file counts, budgets) is written to `export-status.json` as part of the workflow artifact (not deployed to the site); a later `finalize` step runs `macro-monitor record-export` under `mm_ingest` and inserts it into the insert-only `ops.export_status` (DDL spec sections 7-8; round 4: the earlier "merge into `run_summary.groups`" is withdrawn). `mm_reader` has no write privilege anywhere.
2. Reads with role `mm_reader` only, and only these objects: `curated.v_headline_obs_published`, `curated.v_revision_history`, `curated.v_input_obs_published` (round 4: support inputs, used only as inputs to the shared transform code that computes `value_default_tf`; never written to a file), `analytics.scorecard_published`, `analytics.indicator_rank_published`, `analytics.indicator_alignment_published`, `analytics.v_alert_published`, `analytics.v_indicator_snapshot_published`, `analytics.v_run_published` (round 6, ADR-012), `ref.v_source_public`, `ref.v_series_export`, `ref.v_unit_public` (CR-5, 2026-11-09, proposed — pending user approval; DDL spec section 2), the `ref` configuration tables for entities, groups, domains and indicators, and `ops.v_*` views (including `ops.v_run_summary_public`). The browser never contacts Neon.
3. Meaning is computed in Python (transforms, percentiles, ranks, n/N, staleness, alignment, alert level; ADR-006) and carried in files. The export neither computes nor filters meaning: published ranks and scorecards are separate tables produced by analytics over publishable data only (A8). The front-end only filters, sorts, selects, plots and applies display-only rebasing.
4. No imputation, no zero-fill: missing is `null` (D16); a source-published missing value (`value_status = 'MISS'`) is also `null` in `value`. Projections (`PROJ`) are excluded in v1 from every file, including the revision files (A03 has no dashboard output in v1; section 7). Comparison-role series (A02b, A02c) are excluded (D18). Archive-import rows (`load_kind = 'import'`) are excluded. Support indicators and auxiliary input series are ONE set (`is_support = true` exactly when `kind = 'input'`; X01-X03) and are excluded from every file: no scorecard, alert, percentile or rank, and also no entry in `meta/*`, no `series/*` or `revisions/*` file and no row in `meta/series.json` (B5; second fix pass). They have no `publish_scope` value (section 1a); their observations reach the export only through `curated.v_input_obs_published`, as inputs of the transform code that computes `value_default_tf`. Global series (`scope = 'global'`, entity `WLD`) appear only in `series/*`, `meta/*` and the `global` informational group (B6, B9).
5. Determinism: same inputs give byte-identical files (sorted keys, fixed Parquet writer settings, wall-clock only in `manifest.json.generated_at`).
6. Every series carries the CLAUDE.md mandatory metadata, directly or through `series_id` joined to `meta/series.json`: source, series id, frequency, unit, seasonal adjustment, vintage/release date.

### 1a. `publish_scope` (set by analytics, read by export)
Every row of the `*_published` tables carries `publish_scope`, computed by analytics (never by the export). Round 6 storage: `analytics.indicator_rank_published.publish_scope`, `indicator_alignment_published.publish_scope`, `scorecard_published.publish_scope`, and `publish_scope` on `analytics.indicator_snapshot` (passed through `v_indicator_snapshot_published`); DDL spec section 6 gives the rule that computes it.
| Value | Meaning | Export treatment |
|---|---|---|
| `ranked` | country/aggregate row of a ranked indicator in a ranked domain, source `publish_site = public`; aggregates carry a null percentile | full scorecard row |
| `info_only` | value shown, never ranked: entity `WLD`, informational indicators and domains (agri, global) | value, no percentile/rank/alert |
| `excluded` | WITHHELD (indicator, entity) pairs only: the headline series belongs to a source with `publish_site = withheld`. The value exists only on `analytics.indicator_snapshot` and in `v_indicator_snapshot_published` (DDL section 6; AC-AN-25); it is never a value of the three `*_published` tables | not in scorecards, alerts or revisions; appears only as a `published = false` placeholder without values (section 5) |
Support indicators (`is_support`; the same set as input indicators, `kind = 'input'`) and comparison-role series (A02b, A02c) have NO `publish_scope` value: they are not rows of the published snapshot, rank, alignment or scorecard tables at all (they are never snapshotted or ranked, analytics spec section 2), so there is nothing to scope or to filter. The `v_*_published` views drop nothing silently for withheld pairs (a placeholder row without values remains); for support, input and comparison series no row exists. `WLD` is always `info_only` and appears only in the `global` domain file.

## 2. Output tree (relative to the site root `data/`)

```
data/
  manifest.json
  meta/entities.json  meta/groups.json  meta/indicators.json  meta/domains.json  meta/series.json
  scorecard/<domain_id>.json              one per ranked domain and per informational domain (about 8-12)
  alerts.json
  status.json
  series/<indicator_id>.parquet           one per active headline indicator with kind = 'indicator' (about 80)
  revisions/<indicator_id>.parquet        only indicators that have revisions
  revisions_recent.json
export-status.json                        outside data/, artifact only, never deployed
```
Partitioning rule: by indicator, because the interactive uses (peer comparison of one indicator across countries, country scorecard of one domain, explorer for chosen indicator and countries) each need one or a few indicators and all countries. Country-partitioned files were rejected: peer views would need 44 requests.

## 3. `manifest.json`
```json
{ "schema_version": "1.1", "build_id": "2026-11-01T04:23Z-r123", "generated_at": "2026-11-01T06:05:00Z",
  "ingest_run_id": 123, "analysis_run_id": 77, "known_cutoff": "2026-11-01T04:23:41Z",
  "code_version": "git-sha", "history_start": "1991-01-01",
  "files": [ {"path": "series/M01.parquet", "format": "parquet", "bytes": 91234, "rows": 12345, "sha256": "..."} ],
  "totals": {"bytes": 0, "files": 0} }
```
Round 4: the stale-build banner (AC-DASH-7) is evaluated on `known_cutoff` (data and analysis time, read from the database clock under the load lock, ADR-002), not on `generated_at` (build time), and EXP-10 refuses to export an analysis run from an older ingest run in refresh mode, so a failed `analyze` cannot be hidden behind a fresh build timestamp. V3 alert markers show only the current run's alerts from `alerts.json` (historical per-period alert levels are not persisted).

Round 6 (ADR-012): `ingest_run_id` is the value supplied by the workflow (output of `plan`); `analysis_run_id`, `known_cutoff` and `code_version` are copied from the row of `analytics.v_run_published` with the greatest `analysis_run_id` whose `ingest_run_id` equals the supplied one. No such row means EXP-10 fails and nothing is deployed. `generated_at` and `build_id` are the only values not taken from the database.

Invariants: every file in the tree appears in `files` with matching bytes and sha256; `schema_version` is semver (major bump on a breaking change; the front-end refuses an unknown major). The `format` field per file lets the series files switch from Parquet to JSON without changing the front-end contract (fallback in ADR-010). Adding the nullable fields of section 5 is a minor bump. Schema 1.1 adds `unit_text`, `unit_scale`, `unit_text_varies`, `transform_units`, `transformed_unit_text` (minor bump; CR-5/CR-6, 2026-11-09, proposed — pending user approval; the JSON Schemas' `schema_version` const changes from "1.0" to "1.1" with it).

Provenance of the `meta/series.json` fields (fix pass, DDL spec section 2, `ref.v_series_export`): every field except two comes from the columns of `ref.v_series_export` (the view lists them, including `reestimating`). `published_precision` and `source_url` are NOT database columns: the export copies `published_precision` from the group's config key in `config/sources.yaml` and `source_url` from the source's `licence.url` (a landing page for attribution), both read from the config tree at the `git_sha` of the selected analysis run (`analytics.v_run_published.git_sha`); a group without the key exports `null`. EXP-03 checks that the config tree used has that `git_sha`.

Provenance of `default_domain` and `tile_headline` (CR-15, CR-14; ADR-034 amendment A1, 2026-11-10, pending user confirmation): both come from the config tree at the same `git_sha` as `published_precision` and `source_url` (`analytics.v_run_published.git_sha`): `default_domain` from `config/dashboard.yaml` (new file, source-config schema section 1, rule 47; validated by `src/macro_monitor/registry/schemas/dashboard.schema.json`), `tile_headline` from the indicator entries of `config/indicators.yaml` (source-config rule 46; key added to `indicators.schema.json`, `additionalProperties: false`). `publish/meta.py` reads them; no database column, view or migration is added. A missing `config/dashboard.yaml` exports `default_domain = null`. Adding the key and the field is a minor schema bump (section 3). CR-15 is phase A; CR-14 is phase B and is not exported before the user confirms amendment A1.

Provenance of `unit_text` and `unit_scale` (CR-5, 2026-11-09, proposed — pending user approval): they come from `ref.v_series_export` joined to `ref.v_unit_public` on `unit_code` (DDL spec section 2), built at export time by one pure Python function in `publish/`, pinned by golden tests: `unit_text(label, dimension, embedded_mult, embedded_base, unit_mult, base_period) -> str`. (1) Start with `label`. (2) If `unit_mult` is not 0, add " (<scale>)"; scale words: 3 "thousands", 6 "millions", 9 "billions", 12 "trillions", any other value "x 10^<unit_mult>" (example "EUR (millions)"). (3) If `dimension = 'index'`, `embedded_base` is false and `base_period` is not null, add ", <base_period> = 100" (example "index, 2015 = 100"). (4) A series with `embedded_mult != 0` and `unit_mult != 0` is a double scale: an EXP-03 failure, not a text case. The strings (the `ref.unit.label` seeds, scale words, the "(millions)" form, "% annualised") are DRAFT (ADR-025 decision 11) and are batched into the R26 wording pass. The export reads `result_unit` from the shared transform registry (analytics spec section 3) and keeps no unit table of its own.

## 5. Scorecard, alert and status JSON (tier T1)
`scorecard/<domain_id>.json` (example for the labour domain, indicator M09 unemployment rate):
```json
{ "domain_id": "labour", "analysis_run_id": 77, "ranked": true, "min_coverage_for_rank": 0.5,
  "percentile_rank_label": "mean percentile of the domain's indicators",
  "heterogeneous_peer_set": false, "peer_set_size_by_indicator": {"min": 38, "max": 38},
  "alignment": [ { "indicator_id": "M09", "rank_reference_period": "2026-08-31", "reference_period_spread_days": 61,
                   "n_ranked": 38, "n_unaligned": 2, "max_ref_spread_days": 92 } ],
  "entities": [ { "entity_id": "DEU", "n_available": 4, "n_defined": 5, "percentile_rank": 0.62, "rank_position": 14, "n_ranked_entities": 41, "low_coverage": false,
      "indicators": [ { "indicator_id": "M09", "series_id": 1234, "value": 3.4, "transformed_value": 3.4, "transform_id": "LEVEL", "rank_mode": "monotone_good",
          "value_kind": "observed",
          "ref_period_end": "2026-08-31", "ref_offset_days": 0, "known_at": "2026-10-02T04:30:00Z", "source_release_at": "2026-10-01T09:00:00Z",
          "age_days": 48, "stale_limit_days": 120, "limit_source": "class", "is_stale": false, "alignment": "aligned", "alignment_reason": null, "inherited": false, "deviation": null,
          "published": true, "publish_scope": "ranked", "percentile": 0.70, "percentile_label": "percentile vs all ranked countries",
          "n_ranked": 38, "alert_level": "none", "alert_confidence": "full" } ] } ] }
```
Sources: `analytics.scorecard_published`, `v_indicator_snapshot_published`, `indicator_rank_published`, `indicator_alignment_published`, `v_alert_published` (DDL spec section 6). The export copies; it does not compute. Rules:
- `percentile_rank` is the MEAN percentile of the entity's indicators in the domain (analytics spec 4.4; round 5 label, column name unchanged). It is not uniformly distributed and is never presented as "the domain's percentile". It is `null` when `n_available = 0` (shown "n/a"); `rank_position` and `n_ranked_entities` are also `null` when `low_coverage` is true (the mean percentile and n/N stay visible; B8).
- Stale values keep `value`, have `is_stale = true` and `percentile = null` (AC-SYS-8). A `lagging` or `unaligned` entity keeps its value, has the matching `alignment` and `percentile = null` (B1); an `ahead` entity is ranked at its latest value. The dashboard shows `reference_period_spread_days` for every ranking and flags `lagging` and `unaligned` entities. Alignment values: `aligned`, `ahead`, `lagging`, `unaligned`, `n/a`.
- Cross-country reference-period fields (nullable, come from analytics; the export never derives them). Per indicator in `alignment[]`: `rank_reference_period` (date: the common reference period of the analytics ranking rule, analytics spec 4.3) and `reference_period_spread_days` (int: max minus min `ref_period_end` among the ranked entities). Per entity indicator: `ref_period_end` (always) and `ref_offset_days` (int: `ref_period_end` minus `rank_reference_period`; stored in `analytics.indicator_snapshot.ref_offset_days`, round 6). The two indicator-level fields are `null` only when the indicator is unranked (`descriptive_only`, a global indicator or an empty candidate set); the entity-level `ref_offset_days` is `null` for the same cases and for withheld placeholders. Round 5: the legacy `modal_ref_period_end` field and the duplicated null fields of the earlier example are removed (the modal-window rule no longer exists; no consumer has been built yet, so no version bump is needed). They exist so the dashboard can show that cross-country ranks mix reference periods (ADR-010).
- Round 6 pass-through fields (each is a stored column, DDL spec section 6; the export never derives them): entity indicator `value_kind` (`observed` or `estimate`; `estimate` for A02, analytics spec section 2) from `indicator_snapshot.value_kind`; `limit_source` (`class` or `release_lag_aware`) from `indicator_snapshot.limit_source`; `alignment_reason` (`fiscal_year_basis` or null) from `indicator_snapshot.alignment_reason`, which the dashboard shows as the fiscal-year notice for an `unaligned` entity; `publish_scope` from the snapshot view; per domain `heterogeneous_peer_set` and `peer_set_size_by_indicator {min, max}` from `scorecard_published.heterogeneous_peer_set`, `peer_set_size_min`, `peer_set_size_max` (identical on every row of a domain; EXP-05 fails if they differ).
- CR-6 (2026-11-09, proposed — pending user approval): every entity indicator row carries `transformed_unit_text` (string or null), filled at export time from the shared transform registry (no stored snapshot column). It is null exactly when `transformed_value` is null (this includes withheld placeholders). Otherwise it is `meta/indicators.json.transform_units[transform_id].unit_text`, or, when `same_as_series` is true, the `meta/series.json.unit_text` of the row's `series_id`. (The example above predates schema 1.1 and omits the field.)
- Indicators with `rank_mode = descriptive_only` have `percentile = null`; `target_distance` indicators export `deviation` and `target` (B2).
- CR-1 (phase B; accepted by the user as phase B, ADR-034 Q5; contract text pending user confirmation of ADR-034 amendment A1, 2026-11-10; gated: not exported before the user approves this edit and the document sync of the layout amendment section 11): every entity indicator row gains a nullable field `recent`: `{ "n": <int, at most 12>, "end": "<ref_period_end of the last element>", "v": [<float or null>, ...] }`, the last at most 12 stored periods of the row's headline series (`series_id`) at its native frequency, oldest first, latest vintage as of `known_cutoff`, the stored `value` column (not a transform), `null` for a missing period (no interpolation, no imputation, D16). It is taken by slicing the published series (selection, not computation; principle 3 holds); a row with `published = false` carries `recent = null`. Minor schema bump (section 3). The size (about 12 values per row) is unmeasured and is checked against section 8 before approval [UNVERIFIED]. Source of the definition: `docs/specs/dashboard-layout-amendment.md` section 9.
- Aggregates (EU27, EA) appear with `percentile = null`; `WLD` (`publish_scope = info_only`) appears only in the `global` domain file, unranked. Support (= input) indicators are absent from scorecards and from every other file (principle 4).
- In a domain with `ranked = false` (agri, global) all percentile, rank and position fields are `null` (D12, B9). There is no `markets` domain (dropped 2026-10-27, plan OQ-12).
- Euro-area-inherited values carry `inherited = true`, keep their `value`, and are EXCLUDED from percentile ranks: `percentile = null`, not counted in `n_ranked` or `n_available`, the indicator row stays visible with the flag (user decision of 2026-10-27, stated in session; design Q7 closed, plan OQ-11).
- Withheld entries (A8): an (indicator, entity) pair of a withheld source is a placeholder: `value`, `transformed_value`, `deviation`, `percentile`, `alert_level`, `ref_offset_days` are `null`, `published = false`, `publish_scope = excluded`. Because every other number comes from the published-scope tables (section 9), the percentiles, ranks, `n_ranked`, `n_available` and spreads of public entities are functions of published values only. `n_available` counts published indicators only; `n_defined` is unchanged.
Size: about 44 entities x about 10 indicators x about 450 bytes = about 200 KB per domain uncompressed; under 2 MB in total.

`alerts.json`: rows with level `watch` or `alert` from `analytics.v_alert_published` for the run: `indicator_id`, `entity_id`, `series_id`, `ref_period_end`, `method`, `z`, `level`, `confidence`, `reason`, `label` (round 5: `persistent_shift` or null), `override_rule`. The published alert view is computed from published pairs only: alerts, z-scores and levels of withheld series do not exist in it and are not exported. Under 100 KB.

`status.json` (feed freshness and quality; no secrets, no connection details, no raw error text, no values):
- `last_run`: `ingest_run_id`, `started_at`, `finished_at`, `mode`, counts (`new_raw_objects`, `new_observations`, `revisions`, `alerts_opened`) copied from `ops.v_run_summary_public` (DDL spec section 7: the view computes PUBLISHED-SCOPE counts itself, so the export neither filters nor recomputes them; projections are not counted). `db_bytes` is not exported. `alerts_opened` counts the published watch or alert rows of the run's analysis (name kept for compatibility) and is `null` when no analysis run exists.
- `groups[]`: per source group the latest `ops.v_freshness_latest` row (`source_group`, `series_group`, `state` in fresh/late/stale/broken, `expected_period_end`, `latest_period_end`, `evaluated_at`) plus the run's load result (`ok`, `warn`, `failed`, `skipped`) and, from `ops.v_backlog`, the number of unloaded raw objects with the age of the oldest. For withheld sources these rows carry state and dates only (they hold no values). Disabled groups (ADR-027) have no freshness row and are omitted from `groups[]`.
- `validation`: counts by `severity` and `check_id` family for the run (`ops.v_validation_counts`), including the coverage diagnostic COV-01 per indicator: either `{state: "not_yet_measurable", n_qualifying}` (the dashboard shows "not yet measurable") or the share of qualifying entities stale on arrival, computed over published pairs (analytics spec 4.4, PROPOSED P20); number and kinds of open drift events (`ops.v_open_drift`; no `old`/`new` JSON, which may contain values).
- `manual_sources[]`: next expected manual download per manual source (for IMF WEO: the configured expected release window and reminder date from `sources.yaml`; release months [UNVERIFIED], see the source-config spec section 2) and date of the last ingested file.
- `schedule_check`: `generated_at` plus the text of the human monthly check (workflows spec section 9).
Size: under 200 KB.

## 6. Series files (tier T2): `series/<indicator_id>.parquet`
One row per `(entity_id, ref_period_start)` of the headline series, latest vintage as of `known_cutoff`, observed only, `ref_period_start >= 1991-01-01`, from `curated.v_headline_obs_published` (withheld sources and input indicators absent). Global indicators have entity `WLD`.

| Column | Parquet type | Null | Note |
|---|---|---|---|
| `entity_id` | dictionary string | no | sort key 1 |
| `series_id` | int32 | no | join to `meta/series.json` |
| `ref_period_start` | date32 | no | sort key 2 |
| `ref_period_end` | date32 | no | alignment and staleness use the end (design 3.4) |
| `frequency` | dictionary string (`D/M/Q/A`) | no | native; no resampling |

## 7. Revision files: `revisions/<indicator_id>.parquet` and `revisions_recent.json`
`revisions/<indicator_id>.parquet`: all NON-PROJECTION versions of every key that has at least two non-projection versions (keys with only one visible version are excluded), read from `curated.v_revision_history` as of `known_cutoff`, ordered by `(entity_id, ref_period_start, known_at)`. The view (DDL spec section 5) is restricted, since round 5, to publishable sources, to the headline mapping (`role = 'headline'`) of indicators with `kind = 'indicator'`, and to rows with `load_kind <> 'import'`: support inputs (X01-X03), comparison-role series and archive imports never appear in the revision files; revisions of withheld sources are omitted entirely, including counts. Second fix pass: the view also excludes every version with `value_status = 'PROJ'`. A projection edition is a new forecast, not a revision of a published value: the WEO group stores every edition's projection rows even when the number is unchanged (I-CUR-3), so A03 (all PROJ) and the projection years of other WEO-fed indicators (for example A04, A05, A25) would otherwise fill the revision files and the edition summaries with rows that are not revisions. Projections have no dashboard output in v1 (principle 4), so an indicator with only projection versions (A03) has no revision file. A key whose earlier versions were projections starts at its first non-projection version (its base version, below).

| Column | Type | Note |
|---|---|---|
| `entity_id`, `series_id`, `ref_period_start`, `ref_period_end` | as in section 6 | |
| `known_at` | timestamp[us, UTC] | our fetch time (authoritative) |
| `source_release_at` | timestamp[us, UTC], null | source's timestamp |
| `vintage_label` | string, null | for example `WEO-2026-10` |
| `value` | float64, null | `null` for tombstones and for `MISS` |
| `value_status` | dictionary string | second fix pass: `OBS`, `EST`, `PROV`, `MISS` or `DEL` (tombstone); never `PROJ`, which EXP-02 asserts on every file |
| `load_kind` | string | the stored load kind: `initial` (only as the first version of a revised key), `new_period`, `revision`, `tombstone`. For a key whose earlier versions were projections the base version carries whatever the loader stored (typically `revision`, a status change from projection to estimate), so `load_kind` alone does not identify a revision: use `is_base_version` |
| `is_base_version` | bool | second fix pass: copied from the view column of the same name; true for the first non-projection version of a key, which is the starting value of the revision history and never a revision (its `revision_abs` and `revision_pct` are null) |
| `revision_class` | string | `regular` or `reestimation` (A4); the revision view lets the user hide systematic re-estimation families. Revisions of the named-edition WEO group are `regular` (ADR-017) and are told apart by `edition_ordered` and `vintage_label` |
| `edition_ordered` | bool | fix pass: copied from the view column of the same name (the series' group is a named-edition group, ADR-017); lets the revision page show an edition rebase apart from ordinary revisions |
| `revision_abs`, `revision_pct` | float64, null | versus the previous NON-PROJECTION version of the key; null for a base version; pct null when the previous value is 0; null when either side is NA |

A REVISION ROW is a row with `is_base_version = false` and `load_kind` in (`revision`, `tombstone`). `revisions_recent.json` and the edition summaries count revision rows only.

Vintages exist only from the project's first fetch (D10), so early months show few revisions; the view must say that earlier history is revised data, not real time (AC-AN-3 wording). Expected size after one year: under 1 MB in the base case; re-estimation families can raise it (DDL spec section 9; budgets in section 8 apply, with `revisions/*` warn at 20 MB).

`revisions_recent.json` (fix pass, user decision on named editions). Problem: a WEO edition that rebases history is stored as ordinary revisions (`revision_class = 'regular'`, ADR-017), possibly thousands of keys at once, so a list ranked by size would be filled by that one edition and the V4 landing view would show nothing else. The file therefore has two parts and the edition rows are never ranked among the ordinary ones:

```json
{ "schema_version": "1.1", "known_cutoff": "2026-11-01T04:23:41Z",
  "revisions": [ { "indicator_id": "M01", "entity_id": "DEU", "series_id": 1234, "ref_period_start": "2026-06-01", "known_at": "...", "previous_value": 1.0, "value": 1.2,
                   "revision_abs": 0.2, "revision_pct": 20.0, "load_kind": "revision", "revision_class": "regular" } ],
  "edition_summaries": [ { "source_id": "imf_weo_manual", "vintage_label": "WEO-2026-10", "first_known_at": "...", "n_series": 25, "n_keys_revised": 8123,
                           "max_abs_pct": 41.7, "median_abs_pct": 0.9, "top_revisions": [ { "...": "same fields as a revisions[] row, at most 10 rows" } ] } ] }
```
- `revisions[]`: the last 12 months of revision rows (`revision` and `tombstone` rows that are not base versions) of series whose `edition_ordered` is false, `revision_class = 'regular'` rows before `reestimation` rows, then by absolute percentage change descending, at most 2,000 rows (about 400 KB), with indicator, entity, previous and new value and dates. Rows of named-edition groups never appear here, whatever their size. Projection versions are not in the view and so are in no part of this file.
- `edition_summaries[]`: one entry per (source, edition) for series whose `edition_ordered` is true and whose revision rows (as defined above, projections excluded) have `known_at` in the last 12 months. The edition identity is the pair (`source_id` from `ref.v_series_export` by `series_id`, `vintage_label`; when `vintage_label` is null the UTC date of `known_at`). Fields: `n_series` (distinct series with a revision row in the edition), `n_keys_revised` (revision rows, that is revision and tombstone rows that are not base versions), `max_abs_pct` and `median_abs_pct` over rows whose `revision_pct` is not null (null when none), `first_known_at`, and `top_revisions[]` (at most 10 rows with the `revisions[]` fields, largest absolute percentage change first). An edition whose only new rows are projections (or whose rows are all base versions) has no revision rows and therefore no entry. The entries are sorted by `first_known_at` descending and are not subject to the 2,000-row cap; a year holds a handful of editions, so the part stays under 20 KB. The summary is a count and a median of published revision rows; it is not analytics meaning and the export does not use it for any rank.
- V4 shows the ordinary list first and, below it, one line per edition ("WEO-2026-10: 8,123 keys revised in 25 series, largest change 41.7 %, median 0.9 %") with a link to the per-indicator revision files for details. The per-indicator files keep every non-projection row, told apart by `edition_ordered` and `vintage_label`.
- Published sources only: a named-edition group of a withheld source has no entry, not even a count (section 9). Tests AC-EXP-13 and AC-EXP-14.

V4 vintage text (round 6, v1; replaces the round-3 text that used `vintage_resolution` and "first stored release", both vocabulary of ADR-011, v2). The vintage view shows this FIXED text, the same for every series, and no per-series field is exported for it: "Vintages are recorded from this system's first fetch and are collected once a month. A revision that happens and is corrected between two fetches is not visible, and the earliest stored version is not necessarily the value the source published first. ## 9. Redistribution gate (source-config field `publish_site`)
Each source entry in `sources.yaml` carries `publish_site: public | withheld`, no default (defined in `docs/specs/source-config-schema.md`, validation rules 5 and 15). Rules: `public` is rejected when `licence.redistribution_of_raw` is `forbidden`; `unclear` requires an explicit user value.

Design (A8): analytics produces two result sets. The full set (`analytics.indicator_rank`, `scorecard`, `alert`, `indicator_snapshot`) is internal; the published set (`analytics.scorecard_published`, `indicator_rank_published`, `indicator_alignment_published`, and the views `v_alert_published`, `v_indicator_snapshot_published`) is computed by the same code over publishable (indicator, entity) pairs only, with the `publish_scope` column of section 1a. The mean percentiles, rank positions, `n_ranked`, `n_available`, rank reference period, spreads, reference-period fields, peer-set sizes and alerts in the published set are therefore functions of published values alone; the rank of a public entity cannot leak information about a withheld value. The export does not recompute or re-rank anything: it copies the published-set rows. The consequence is explicit: when a withheld source is excluded, public entities' ranks in the published set can differ from the internal full set; the dashboard shows only the published set, and the internal set is not exposed. `mm_reader` can read only the published objects (DDL spec section 8), so the export cannot publish internal values even by mistake.

For a `withheld` source: its row stays in `meta/series.json` with `publish = withheld`; its values are omitted from `series/*` and `revisions/*` (absent from `curated.v_headline_obs_published` and `curated.v_revision_history`); in scorecards its pairs are placeholders (section 5) and show "not published"; its alerts, z-scores and revisions are absent from `alerts.json`, `revisions_recent.json` (including `edition_summaries[]`) and `revisions/*`. `n_available` counts published indicators only; `n_defined` is unchanged. Attribution strings are exported per series and shown beside every chart. The public database dump uses the same two fields (ADR-003, ADR-015).

## 11. Acceptance criteria
- AC-EXP-1 EXP-01 to EXP-10 pass on the fixture database in CI (Postgres service container) and the golden manifest matches.
- AC-EXP-2 A forced failure (schema violation or budget breach) leaves the previously deployed site unchanged and opens a `pipeline` issue.
- AC-EXP-3 A revision loaded in a test appears in `revisions/<indicator_id>.parquet` (old and new value, with its `revision_class`) and in `revisions_recent.json` (in `revisions[]` for an ordinary group); the series file shows the new value.
- AC-EXP-4 (leak test, extended) Fixture with source S1 `public` and source S2 `withheld` feeding different entities of one indicator, with the withheld series having a revision, an alert-level z-score, and a distinctive derived value: (a) a byte search over ALL exported files (`scorecard/*`, `alerts.json`, `revisions/*`, `revisions_recent.json`, `status.json`, `meta/*`, `series/*`, `manifest.json`) for the distinctive withheld raw values, z-scores, percentiles and other derived values (rounded at several precisions, as numbers and as strings) finds nothing; (b) no exported row has a `z`, `percentile`, `rank_position`, `deviation`, revision or alert for a withheld pair, and `alerts.json` and `revisions*` contain no row for the withheld source; (c) for public entities, percentile, rank position, `n_ranked`, `n_available`, the alignment spread and `rank_reference_period` / `reference_period_spread_days` equal the published-scope rows computed over public pairs only; (d) perturbation test: changing every withheld value in the fixture (and rerunning analytics and the export) leaves all exported files byte-identical (same hashes), including `alerts.json`, `status.json` counts and `meta/*`; (e) the export role cannot SELECT the full analytics tables (T-DDL-12); (f) `status.json` carries no `old`/`new` drift JSON and no values for withheld groups.
- AC-EXP-5 The export uses one database session per run; its duration and bytes read are written to `export-status.json`, recorded by `record-export` under `mm_ingest` into `ops.export_status`; the `mm_reader` session has no write privilege (T-DDL-10); no connection to Neon happens outside pipeline workflows because of dashboard use (verified by design: the site contains no database credentials, EXP-07).
- AC-EXP-6 Alignment, rank mode and notices: a fixture domain file contains `alignment[]` with `rank_reference_period` and `reference_period_spread_days` and no `modal_ref_period_end`; a `lagging` and an `unaligned` entity have `percentile = null`, an `ahead` entity is ranked; an informational indicator has `rank_mode = descriptive_only`, `good_dir = 0` and no percentile; `meta/indicators.json` for M18 carries the non-euro wording; `percentile_rank_label` is present wherever `percentile_rank` is.
- AC-EXP-7 Scope: `WLD` appears only in the `global` domain file with `percentile = null`; `rank_reference_period`, `reference_period_spread_days` and `ref_offset_days` equal the analytics output when present and are `null` otherwise (never computed by the export).

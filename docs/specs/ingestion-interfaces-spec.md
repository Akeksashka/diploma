## 1. Domain types (`macro_monitor.models`)

```python
@dataclass(frozen=True)
class ResolveSpec:                                           # ADR-028: landing-page discovery of the file URL
    dataset: str; link_pattern: str; expect_matches: int
    allowed_hosts: tuple[str, ...]; expect_format: str | None = None

@dataclass(frozen=True)
class RequestSpec:
    source_id: str; group_id: str; method: str; url: str
    params: Mapping[str, str]; headers: Mapping[str, str]   # secrets only in headers, never logged
    request_key: str                                         # sha256 of canonical (method,url,sorted params,body); for a discovered request over (GET, landing_url, dataset), i.e. the logical dataset, so a rotated file URL keeps the chain (ADR-028)
    resolve: ResolveSpec | None = None                       # landing-page discovery (ADR-028); when set, `url` is the landing page
    fetch_mode: Literal["full", "incremental"]               # incremental = only changed/recent observations (lastNObservations, UpdatedAfter, ...)
    expect_scope: Literal["complete", "partial"]             # RULE: fetch_mode == "incremental" => expect_scope == "partial" (validated in plan; DB CHECK)

@dataclass(frozen=True)
class FetchResult:
    spec: RequestSpec; outcome: Literal["new","unchanged","not_modified","blocked","skipped_robots","rate_limited","error"]
    status: int | None; body: bytes | None; fetched_at: datetime   # UTC, completion time; runner clock corrected by the measured database-clock offset (BB25)
    etag: str | None; last_modified: str | None; content_type: str | None
    update_marker: str | None                                   # source-declared (e.g. Eurostat 'updated')
    resolved_url: str | None = None                             # discovered file URL (ADR-028); None for a plain request
    discovery: Mapping[str, object] | None = None               # provenance of the discovery (ADR-028)

@dataclass(frozen=True)
class ParsedSeriesMeta:   # fields of ref.series that the source publishes
    series_ref: str; entity_code: str; frequency: str; unit_code: str; unit_mult: int
    base_period: str | None; price_basis: str; currency_code: str | None
    seasonal_adjustment: str; calendar_basis: str; title: str
    flow_basis: Literal["PERIOD_FLOW","ANNUALISED_RATE","STOCK","NA"]   # round 5 (P18): a quarterly SAAR must not be summed as a period flow
    published_decimals: int | None                          # source DECIMALS attribute, else None (loader derives from the first load)

@dataclass(frozen=True)
class ParsedObservation:
    series_ref: str; ref_period_start: date; ref_period_end: date; value: Decimal | None   # Decimal keeps the published scale; None iff value_status in (DEL, MISS)
    value_status: Literal["OBS","EST","PROV","PROJ","DEL","MISS"]   # parsers never emit DEL (loader tombstone); MISS = marker declared in the group's missing_markers
    source_release_at: datetime | None; vintage_label: str | None; source_flags: str | None   # for MISS: the marker/flag text

@dataclass(frozen=True)
class RevisionPolicy:      # per group, from config (source-config-schema section 1); persisted as ref.series_group
    compare: Literal["published_decimals", "fixed_decimals"]; decimals: int | None; rel_epsilon: float   # defaults: published_decimals, None, 1e-9
    reestimating: bool                                      # config key `reestimating: true`
    snapshot_mode: Literal["none", "diff_above_tol"]        # diff_above_tol requires reestimating
    materiality_abs: Decimal; materiality_rel: float        # REV materiality and diff_above_tol storage tolerance
    max_revised_rows: int | None
    edition_ordered: bool = False                           # manual groups whose objects carry edition_date (round 5, P22); round 6 (ADR-017): marks a NAMED-EDITION group, mutually exclusive with reestimating
```

## 2. Connector protocol (`macro_monitor.ingestion.base`)

Three steps, as decided in ADR-013 (it amends the four-step protocol of ADR-004; `describe_series` is not a member).

```python
class Connector(Protocol):
    source_id: str
    def plan(self, group: GroupConfig, state: StateStore, mode: Mode) -> list[RequestSpec]: ...
    def fetch(self, spec: RequestSpec, http: HttpClient, state: StateStore) -> FetchResult: ...
    def parse(self, raw: RawObject, series_filter: SeriesFilter) -> ParseOutput: ...   # (metas, observations)
```
Rules:
- `fetch` returns bytes untouched; no decoding, filtering or re-serialisation before hashing and archiving.
- `parse` is a pure function of the bytes, the parser version and `series_filter`; no network, no clock (except `fetched_at` passed in `RawObject`). This makes replay (I-CUR-7) and re-staging from stored raw possible.
- Parsers declare `PARSER_VERSION`; `parser_id = "<module>@<PARSER_VERSION>"` is stored on `raw_object`. Behavioural parser change = new version.
- Parser registry (B12): every historical `parser_id` stays importable. Released parser versions are frozen modules (for example `parsers/jsonstat_v1.py`, `jsonstat_v2.py`) or a registry entry that maps the id to a callable; deleting or editing a released version is forbidden. A unit test (AC-ING-11) fails if any `parser_id` that appears in fixtures or, in the DB-marked test, in `ingest.raw_object`, does not resolve through `macro_monitor.ingestion.registry.resolve(parser_id)`. `rebuild` and re-staging always use the recorded `parser_id`, not the current parser.
- Period parsing is centralised (`models.periods`): `2026-09`, `2026-Q3`, `2026`, `2026-09-30` -> `(start, end)`; A/Q/M/D only; fiscal and marketing-year bases come from series metadata, never guessed.
- Missing values (round 5): a cell whose text equals a marker in the group's `missing_markers` (for example `:`, `..`, `c`) is emitted as `value_status = "MISS"`, `value = None`, with the marker in `source_flags`. Any other non-numeric cell is a rejected row (PARSE-03), never silently a `MISS`.
- `series_filter` contains only mapped series (and `discover: true` groups produce `ParsedSeriesMeta` without observations for review).
- Discovery (ADR-028): `plan` stays pure and offline and returns the landing URL with `resolve`. `fetch` resolves the file URL with the injected `HttpClient`: the robots gate (log-only for `bulk`) and rate limit apply to every request of the sequence, the landing request (which is not archived) and the file request. It extracts `<a href>` values, filters by `link_pattern`, requires exactly `expect_matches` distinct matches within `allowed_hosts` over https (redirects included), then GETs the file. Validators from `request_state` are sent only if the resolved URL equals `request_state.last_url`. There is no fallback to a remembered or date-token URL. Any failure of these steps stops the group's fetch with no partial store and is classified `discovery_failed`. A bot challenge on the landing page or the file stays `blocked` (ADR-005).
- Incremental fetches (fix 8): a connector may issue `fetch_mode = "incremental"` requests (for example Eurostat `lastTimePeriod`, OECD `lastNObservations`/`UpdatedAfter`) only with `expect_scope = "partial"`. The combination incremental + complete is a configuration error (exit code 20 at `plan`, DB CHECK `incremental_is_partial`). Tombstones (`DEL`) are derived only from objects with `fetch_mode = "full"` and `fetch_scope = "complete"`: an absent key in a partial or incremental object means "not in this response", never "dropped by the source". A periodic full fetch of each incremental group is scheduled by `plan` (config `full_refresh_every`, default 12 months) so that dropped values are eventually detected.

## 3. `HttpClient` behaviour (normative)
1. User-Agent from template; never an empty or browser-like one.
2. Per-host token bucket and concurrency from `rate_limit`; hour/day budgets persisted in `ingest.request_state` counters so a catch-up run cannot exceed them.
3. Conditional headers from `request_state` when the change-detection ladder includes `http_validators`.
4. Retries per config; 429/503 honour `Retry-After`; maximum total wait per request 10 minutes; Eurostat async status responses are polled (max 15 minutes, backoff 15 s -> 120 s).
5. Bot-challenge detection: status 403/503 plus body markers (e.g. "Just a moment", "cf-chl") => `outcome = blocked`; never retried within the run; never bypassed (ADR-005). `discovery_failed` (ADR-028) is an error class stored in `ingest.fetch_attempt.error_class` and in `ingest.run` detail, with `outcome = error`; it is handled like `blocked`: one alert per source per month, the group is skipped, other groups continue.
6. Robots gate before the first request to a host (ADR-005).
7. Redirect to a different host is returned to the connector as an error unless the host is listed in the source config.
8. Redaction: secrets removed from `request_url`, logs and exceptions.
9. Clock (round 5, BB25): at job start the client reads the database `clock_timestamp()` once, computes the offset to the runner clock and stamps `fetched_at = runner_now + offset`; the offset is written to `ops.run_summary`. An offset above 5 s is a warning; the loader's META-05 check is the second line of defence.

## 4. Raw archive manifest (`manifest.jsonl`, one object per line; also `ingest.raw_blob` + `ingest.raw_object`)

```json
{"raw_id": 123, "prev_raw_id": 98, "run_id": 45, "source_id": "eurostat", "group_id": "sts_prod", "request_key": "ab12...", "request_url": "https://...",
 "request_params": {"format": "JSON"}, "http_status": 200, "etag": null, "last_modified": null,
 "content_type": "application/json", "fetched_at": "2026-11-01T04:31:22Z", "byte_count": 1234567,
 "sha256": "<64 hex of uncompressed bytes>", "blob_reused": false,
 "asset": "eurostat/ab12cd34ef56ab12-sts_inpr_m.json.zst", "release_tag": "raw-2026-11-01-r45",
 "snapshot_asset": null,
 "parser_id": "macro_monitor.ingestion.parsers.jsonstat@1",
 "fetch_mode": "full", "fetch_scope": "complete", "manual": false, "edition_label": null, "edition_date": null, "import_label": null,
 "robots_decision": "not_applicable_documented_api"}
```
For a `hash_only` source `asset` and `release_tag` are null and the blob has `storage_backend = 'none'` (ADR-003). For an object whose bytes were stored by the local-directory backend (section 4a; tests and development only) `asset` is the store-relative path, `release_tag` is null and the blob has `storage_backend = 'local_dir'`.

Rules and invariants:
- Stored bytes are deduplicated by sha256 (`raw_blob`). When the sha256 already exists in `raw_blob` (a revert, or the same file from another request), no asset is uploaded; the manifest line has `blob_reused: true` and `asset`/`release_tag` point to the release that first stored the bytes. Deduplication applies to bytes only, never to manifest rows.
- A manifest row (`raw_object`) is written for every observed CHANGE against the LATEST object of the same `(source_id, request_key)`, never against "any earlier object". Source A -> B -> A therefore produces three manifest rows (three `raw_id`s with distinct `fetched_at`) and two blobs; the third is a new object that the loader processes like any other. One exception (round 5): when the latest object of the request is a `hash_only` object recorded `rejected` with `detail.reason = 'bytes_unavailable'`, an identical hash is treated as a change so that the data is refetched and loaded (section 6).
- The sha256 is of the bytes as received; the asset decompresses to exactly those bytes; a released manifest is never edited; an `unchanged` fetch (sha256 equals the latest object's) writes no manifest line (only `ingest.fetch_attempt`).
- For groups with `snapshot_mode = diff_above_tol` the fetch leg also writes a normalised Parquet snapshot of the parsed full vintage (series_ref, period, value, value_status), uploads it as `snapshot_asset` in the same release and records `ingest.raw_snapshot` in the same transaction. The snapshot is a pure function of the raw bytes and parser; it is an optimisation of access, not a second source of truth.
- A manifest row and its staging rows are committed in one transaction after the asset upload (I-ING-5). An orphan asset (uploaded, crash before commit) is overwritten when the same asset name is uploaded again to the still-draft release.
- Discovered bulk groups (ADR-028): `request_url` is the RESOLVED FILE URL; `request_params.discovery` holds `{"landing_url", "landing_status", "landing_sha256", "link_pattern_id" (sha256 of the pattern), "matched_href", "resolved_url", "resolved_at"}`; `request_key` is the logical key (landing URL + dataset), so `prev_raw_id`, `request_state` and I-ING-3 are unchanged by URL rotation. `request_state.last_url` records the last resolved URL. A changed URL with identical bytes is not a new object (the ladder stops at the content hash); a changed URL with new bytes is a normal new object in the same chain. No DDL change.
- Manual objects (`manual = true`) carry `edition_label` and, for `edition_ordered` groups, `edition_date` (from the sidecar); `import_label` is null or `archive_import`.

## 4a. `RawStore` protocol and backends (Phase 2 amendment, 2026-10-27; plan OQ-04, user decision stated in session)

The fetch leg stores bytes, and the loader re-reads them (step 4), only through one protocol, so that tests and development need neither GitHub nor the network. Illustrative signatures:

```python
class RawStore(Protocol):
    backend_id: Literal["release_public", "local_dir"]      # value written to ingest.raw_blob.storage_backend
    def put(self, sha256: str, data: bytes, name: str) -> StorageRef: ...   # idempotent per sha256; returns the reference stored in raw_blob.storage_ref
    def get(self, ref: StorageRef) -> bytes: ...                              # verifies sha256 before returning; raises on mismatch or absence
    def exists(self, sha256: str) -> bool: ...
```
Backends:
- `release_public` (production, ADR-003, unchanged): immutable GitHub release assets (`zstd` of the exact bytes), draft-then-publish, continuation releases at 900 assets, upload throttle (ADR-003). `StorageRef` = release tag + asset name. It also owns the release operations of workflows spec section 4 (open draft, publish), which are not part of the protocol because they have no local meaning.
- `local_dir` (tests and development only; accepted by the user on 2026-10-27, stated in session): a directory tree, default `data/raw/` (git-ignored, CLAUDE.md), root overridable by an environment variable. Layout `<root>/<source_id>/<sha256[0:2]>/<sha256>.zst` (the same `zstd` encoding as release assets, so the bytes round-trip identically); `StorageRef` = the path relative to the root. There is no draft or release concept, `release_tag` stays null, and nothing is ever uploaded.

Invariants (both backends):
1. A stored object is immutable: `put` of the same sha256 is a no-op; `put` to an existing name with different content raises; there is no delete or overwrite API.
2. `get` returns exactly the bytes whose sha256 was recorded; a mismatch is an error (`bytes_corrupt`), never a silent return.
3. The manifest, the deduplication rule, the revert rule and the loader algorithm are identical for both backends; the backend changes only where bytes live.
4. `local_dir` is refused in production: the production workflows (`monthly-refresh`, `ingest-manual`, `decide`) set `MM_ENV=production`, and `plan` and `load` exit 20 (config error) when `MM_ENV=production` and the selected backend is not `release_public`. Locally and in `unit` and `db` tests the default is `local_dir`. Rows with `storage_backend = 'local_dir'` therefore exist only in development and test databases and cannot reach the public dump, which is produced from the production database (the `pubdump.v_ingest_raw_blob` view lists all blobs, public-dump-spec section 2, so the guarantee rests on this refusal and not on a filter).
5. The backend is chosen once per process from the environment (`MM_RAW_STORE`: `release_public` | `local_dir`) and recorded per blob; a database may mix blobs of both backends, and `get` dispatches on `raw_blob.storage_backend`, not on the current setting.

Draft-release steps of the production flow (BB18: draft assets downloadable with `GITHUB_TOKEN`) have no local equivalent; the crash scenarios AC-ING-5 (a) to (d) are run on the local backend, and the draft-release variant (BB18, ADR-003 spike) stays a separate network-free mock test of the `release_public` backend.

## 5. Loader algorithm (`macro_monitor.storage.loader`)

The loader works on a queue, not on "the current run": all objects in `ingest.v_raw_unloaded` for the groups it is asked to load, ordered by `(source_id, group_id, fetched_at, raw_id)`. `load --drain` (default) processes the whole queue of the requested groups plus every group that has a backlog (unloaded objects older than the current run); `load --raw-id N` processes one object (used after a human decision), but never out of group order: it refuses with exit 10 if an earlier unloaded object of the group exists, unless that object was decided (`skipped_by_decision`/`rejected`). One transaction per raw object. Objects from the manual inbox are ordinary objects of this queue (`manual = true`); `ingest-manual` has no separate path into `curated`.

For each object X:
1. Acquire `pg_advisory_xact_lock(hashtext('mm-load'))` on a direct connection (`lock_timeout` 10 min; on timeout the object stays unloaded and the next drain takes it). The same lock is used by `monthly-refresh`, catch-up and `ingest-manual`, and, briefly, by the analytics step that reads its cutoffs.
1b. (round 5) Immediately after the lock is held, read `t_load := clock_timestamp()` once. Every observation row of this load and the `raw_load` row use `loaded_at = t_load`. Because the lock is held until the commit, `t_load` lies between lock acquisition and commit, and an analytics run that takes the lock afterwards reads a cutoff above `t_load`, while one that takes it after this commit window never sees a load whose `loaded_at` is above its cutoff (ADR-002, AC-ING-15). `transaction_timestamp()` (transaction start, before the lock) is NOT used.
2. Group-order rule (A5, fix 4): if any other object of the same `(source_id, group_id)` with a smaller `(fetched_at, raw_id)` is still unloaded (it failed, is held, or is waiting for a decision), X is held: no `raw_load` row, check `ORD-02` (warn) names the blocking object. Other groups are unaffected. The held chain is released by a successful load of the predecessor, or by a human decision that sets the predecessor to `skipped_by_decision` or `rejected` (`decide` workflow). Consequence: one failing request blocks the later objects of its whole group, because that is the only way to keep `known_at` strictly monotone per key without comparing series sets before parsing; the cost is bounded by LOAD-01 and the decide workflow.
2a. Edition-order rule (round 5, PROPOSED P22; groups with `edition_ordered`): let E be the greatest `edition_date` among objects of the same `(source_id, group_id)` that have a `raw_load` row with outcome `loaded`. If X has `edition_date < E` and `X.import_label` is null, X is NOT loaded: insert `raw_load` with `outcome = 'skipped_out_of_order'`, `detail.reason = 'older_edition'` (terminal, it does not block later objects), raise `ORD-03`, and stop. A fetch-time order alone would let an older edition committed later become the "latest". An equal `edition_date` (a corrected file of the same edition) is allowed. If X has `import_label = 'archive_import'` it proceeds, and all its rows are inserted with `load_kind = 'import'` (step 7). "Latest edition" for any downstream purpose (A02 estimate boundary) is read from `raw_object.edition_label`/`edition_date` of the latest loaded object, never from `vintage_label` of rows.
3. Out-of-order rule (A5, round 4: per series): each series of X (from `series_meta_load`) that already has a `curated.observation` row (other than `load_kind = 'import'`) with `known_at > X.fetched_at` (for example loaded through another group or the manual inbox) gets a `raw_series_status` row `skipped_out_of_order` and is not loaded from X; the other series of X load normally. Only if every series of X is skipped is the object recorded with `raw_load.outcome = 'skipped_out_of_order'` (reason in `detail`). Check `ORD-01` (warn) is raised with the series count. (The earlier whole-object skip let one conflicting series discard thousands of unrelated series of a bulk file.) Reason: loading it would break I-CUR-4 and the later object already carries the more recent source state. Replay (I-CUR-7) honours the recorded outcome. The intermediate vintage of that object is intentionally not stored; this is logged, not silent.
4. Staged input: use `staging.*` rows with `raw_id = X`. If there are none (swept after 14 days, or the staging run was killed), re-stage from the stored raw bytes: read the bytes through the `RawStore` of `raw_blob.storage_backend` (section 4a; for the production backend this downloads the asset named by `raw_blob.storage_ref`), decompress, verify sha256, run the recorded `parser_id` through the registry with the current `series_filter`. For a draft release of a crashed run, asset download needs the release token [UNVERIFIED that draft assets are downloadable with `GITHUB_TOKEN`; fallback: `finalize` publishes orphan drafts first (ADR-003), then the loader reads the published asset]. For an object of an `archive: hash_only` source there are no bytes: if the staging rows are gone, record `raw_load.outcome = 'rejected'`, `detail.reason = 'bytes_unavailable'` and let the next `plan` refetch the request (section 6).
5. Validate (ADR-007 PARSE/META/SEM/REV/COMP/DB-05). On `error` for the object: roll back (staging rows stay); the object stays unloaded (no `raw_load` row); successors of the same group are held (step 2); the group is marked failed. A mass-revision block (REV-01, REV-06 cap, DB-05) opens an `ops.drift_event` tied to `raw_id`. REV materiality (fix 5; restated in round 5): REV-01 counts only revised keys that are revisions under the comparison rule of step 7 (difference above `max(rel_epsilon * max(|a|,|b|), 0.5 * 10^-d)`, that is half a unit of the derived `published_decimals`) and, where the group sets a materiality, also above `max(materiality_abs, materiality_rel * |old|)` (relative term not applied to ratio-dimension units); smaller differences are not revisions at all (step 7). The revision check family is chosen once per object by the group (round 6, ADR-017): for `reestimating` groups REV-01 does not apply and REV-06 (cap `max_revised_rows`, counted on material changes) does; for `edition_ordered` (named-edition) groups REV-01 does not apply and REV-07 reports the material revisions without ever blocking or raising a drift event; all other groups use REV-01. DB-05 applies to every group.
6. Resolve each `series_ref` to `ref.series` via `(source_id, dataset_id, series_key, max(version))`; compare `staging.series_meta_load` with stored measurement attributes (including `flow_basis`). A difference => `ops.drift_event` (kind per attribute: `unit`, `base_period`, `seasonal_adjustment`, `frequency`, `flow_basis`, `classification`, `composition`) and an `ingest.raw_series_status(raw_id, series_ref, 'deferred')` row; those series are not loaded from X; the rest of X proceeds. If `ref.series.published_decimals` is NULL it is set from `series_meta_load.published_decimals`, else from the maximum scale seen in X (the only `ref.series` UPDATE besides `is_active`). First sight (round 6, ADR-018): if a staged `series_ref` has NO `ref.series` row and is listed in the config series map of the object's group at the run's `git_sha`, the loader creates it in this transaction: `version = 1`, `first_seen_at = X.fetched_at`, measurement attributes and `title` from `staging.series_meta_load`, `group_id`, `entity_id` and `composition` from the series-map entry (`expect.composition`, default `NA`), and inserts the `ref.series_map` rows that the config declares for that series key. Preconditions: the published metadata equals the entry's `expect` block (META-02), META-01/03 pass, the `unit_code` exists in `ref.unit` and the group exists in `ref.series_group`; if any fails no row is created, a drift event is raised and the series is deferred as above. A staged series that is not in the series map is never created. `published_decimals` is then set as described above.
7. For each staged observation compute the latest stored version for the key (rows with `load_kind = 'import'` are ignored) and insert iff absent or different under the group's `RevisionPolicy` (I-CUR-3). Comparison (fix 5): both values are normalised at the series' `published_decimals` `d` (or the group's fixed decimals); they are equal when `|a-b| <= max(rel_epsilon * max(|a|,|b|), 0.5 * 10^-d)`; when `d` is unknown the smaller Postgres numeric scale of the two values is used as fallback and `detail.precision_fallback` is counted. `value_status` compares exactly; two `MISS` rows (both value NULL, same status) are equal, a change from a value to `MISS` or back is a status change and is inserted as a `revision` (never subject to the tolerance). For groups with `snapshot_mode = diff_above_tol`, a revision (key exists, value differs under the rule above) is additionally inserted only if `|a-b| > max(materiality_abs, materiality_rel * |a|)` with `a` the latest stored value; otherwise it is counted in `raw_load.rows_below_tol` and not stored (the full vintage remains in the snapshot). New periods, status changes and tombstones ignore the tolerance. For `PROJ` rows the comparison row is the latest row of the key with the same `vintage_label` (a new edition always inserts). `known_at := raw_object.fetched_at`; `loaded_at := t_load` of step 1b. For an object with `import_label = 'archive_import'` every row is inserted with `load_kind = 'import'` (no comparison against earlier rows; idempotence comes from the `raw_load` row). `published_decimals` `d` is the MAXIMUM decimals over the full first-load history parsed from source text (or the DECIMALS attribute), frozen, and increase-only through an `ops.drift_event` of kind `precision_change`; a decrease is rejected by a DB trigger. A change of a series' euro-area `composition` (FIXED/CHANGING) is a drift event (kind `composition`) and a succession, never an in-place change. `load_kind` per I-CUR-5. `revision_class := 'reestimation'` for revisions of `reestimating` groups, else `'regular'` (named-edition groups: `'regular'`). The applied policy and counts per class are written to `raw_load.detail`.
8. Tombstones: only if `raw_object.fetch_mode = 'full'` AND `fetch_scope = 'complete'`: for stored keys of the requested series whose latest version is not `DEL` and which are absent in the object, insert a `DEL` tombstone (guard: abort and raise `COMP-03` if more than 5 % of a series' keys would be tombstoned). A key present in the object as `MISS` is not absent and is never tombstoned. Never for partial or incremental objects.
9. Insert the `raw_load` row (`outcome = 'loaded'`, `loaded_at = t_load`, counts, detail); update `request_state.last_loaded_sha256`/`last_loaded_raw_id` to X (fix 2); update `ops.run_summary` counters; delete `staging.*` rows with `raw_id = X`; commit. All in the same transaction as the observation inserts.
10. Idempotency: running the drain twice yields identical database state after the second run (the queue is empty).

Deferred series (step 6): when a drift event is `accepted` (the new `ref.series` version exists and the mapping was switched by reviewed config), the loader processes pending `raw_series_status` deferrals in `fetched_at` order, re-stages X from the stored raw bytes for those series only, loads them under the new series version with `known_at = X.fetched_at` and appends `'loaded'` rows. `rejected` appends `'rejected'`. No refetch is needed. (Human-accepted drift => reload from stored raw, ADR-007.)

Held and failed objects are visible: `status.json` lists the number of unloaded objects and the oldest age; check `LOAD-01` (warn after 1 day, error after 40 days) flags a growing backlog.

Concurrency between `monthly-refresh`, catch-up and `ingest-manual` (A3):
- Fetch legs of different runs write only rows carrying their own `run_id` and `raw_id`; nothing truncates or deletes another run's staging rows. `plan` never cleans staging.
- Staging cleanup: (a) the loader deletes rows of an object only in the transaction that commits that object's load; a rolled-back load keeps them; (b) a sweep in `monitor` deletes rows of runs finished more than 14 days ago; (c) a fetch leg that aborts leaves no rows because manifest and staging commit together.
- The only global mutual exclusion is the load lock of step 1, held for one object at a time (seconds to minutes), so a manual ingest waits briefly for a refresh load instead of failing. The manual inbox uses this lock and the same queue.
- Two loaders running at once serialise on the lock; the second finds an empty or shorter queue. Group order (step 2) and the out-of-order rule (step 3) keep I-CUR-4 true regardless of which workflow loads first.
- A manual file for a series that the refresh also fetches (different group) is allowed; whichever object has the later `fetched_at` wins by known-time order, and if the earlier one is loaded after the later one it is recorded `skipped_out_of_order`.

## 6. Change detection and state
- `request_state` has two kinds of pointer. Fetch side (`etag`, `last_modified`, `update_marker`, `last_sha256`) is updated only after the manifest row and staging rows are committed (or after an `unchanged`/`not_modified` outcome is recorded) and describes the latest FETCHED object. Load side (`last_loaded_sha256`, `last_loaded_raw_id`) is updated only inside the load transaction of step 9. Load status of record is `ingest.raw_load` / `ingest.v_raw_unloaded`; the load-side pointer is a cache for reporting and for the `plan` shortcut.
- A fetch that ends `unchanged`/`not_modified` never marks anything loaded. `plan` selects for loading every group whose queue is non-empty, independent of the fetch outcome. Consequently a crash or a failed load cannot hide a change: a later 304 or identical body ends the fetch, and the loader still drains the unloaded object from stored raw in `fetched_at` order.
- The "changed" test compares the new sha256 with the sha256 of the latest `raw_object` of the request key (revert-safe: A -> B -> A is a change at the third fetch). Exception (round 5): if the latest object of the request is a `hash_only` object whose `raw_load` outcome is `rejected` with `detail.reason = 'bytes_unavailable'`, the validators and the hash comparison are bypassed once, the request is refetched and a new `raw_object` is written even when the hash is identical (the earlier object can never be loaded). The DB trigger that rejects a row whose sha256 equals that of its `prev_raw_id` allows exactly this case.
- `update_marker` values are compared as opaque strings.

Workflow inputs (`workflow_dispatch`, such as group lists, `--raw-id`, decision notes) reach the CLI only through environment variables and are validated against an allow-list pattern inside the CLI; they are never interpolated into shell command lines of the workflow (workflows spec).

## 8. Acceptance criteria
- AC-ING-1: each connector has a recorded-bytes fixture test: `parse` output equals a golden file; running `parse` twice yields identical output.
- AC-ING-2: with a mock transport, a second `fetch` returning 304 (or an identical body) creates a `fetch_attempt` and no `raw_object`.
- AC-ING-3: a response containing a challenge signature yields `blocked` with no retry and no parse.
- AC-ING-15 (review round 3, rewritten in round 5; as-of reproducibility, I-CUR-8). Two scenarios against a Postgres service container with two sessions. (A) Load that straddles the cutoff: session L starts a load of object O, acquires the load lock, reads `t_load`, inserts rows and does not commit; session R (analytics) starts its cutoff transaction: it blocks on the lock (assert it has not returned); L commits; R then returns `known_cutoff = load_cutoff = c` with `c >= t_load`. `fn_observation_asof(c, c)` includes O's rows (they were committed before R read its cutoff). Earlier behaviour (loaded_at = transaction start, cutoff = runner clock) returned a cutoff that precedes the commit while `loaded_at <= cutoff` and so included rows R could not have seen. (B) Held-back object: object P is fetched at t1 and held; R takes `c` at t2 > t1; P is loaded at t3 > t2 with the original `known_at = t1`. Then `fn_observation_asof(c, c)` still returns exactly the rows R saw (P's rows have `loaded_at > c`), while `fn_observation_asof(c)` returns more rows. In both scenarios `c` comes from the database clock: a test that skews the runner clock by plus or minus 10 minutes changes nothing in the outcome.
- AC-ING-16 (review round 3, precision; boundary corrected in round 5): a series whose first-load history has 0-decimal old values and 2-decimal recent values gets `published_decimals = 2`; a revision of more than 0.005 (for example 0.01, or 0.3) is stored (not dropped as noise); a change of exactly 0.005 is NOT stored (equality at the half-unit boundary is "equal"); an UPDATE lowering `published_decimals` is rejected; an increase writes a `precision_change` drift event in the same transaction.
- AC-ING-4: the loader satisfies I-CUR-2, I-CUR-3, I-CUR-5, I-CUR-7 on a Postgres service container with a scripted scenario of consecutive fetches of one request: (1) initial; (2) new period; (3) revision; (4) deletion of a key in a complete full fetch; (5) revert: bytes identical to fetch (2)'s source state after fetch (3) changed them (A -> B -> A). For (5): three `raw_object` rows exist for the request key, two `raw_blob` rows, one asset uploaded for the bytes; the loader loads the third object with a new `known_at`; the key's observation rows are `initial` A, `revision` B, `revision` A with three distinct `known_at`; `fn_observation_asof` before, between and after returns A, B, A; a fourth fetch with bytes A inserts no `raw_object`. Further cases in the same suite: PROJ value unchanged under a new `vintage_label` inserts a row; float-noise difference (2.1 vs 2.1000000001) and 2.10 vs 2.1 insert no row; a one-decimal change inserts a revision; replay (I-CUR-7) of the whole scenario reproduces the natural-key rows.
- AC-ING-5 (consistent with A2, fix 2): (a) Kill after the `raw_object`+staging commit and before load, then re-run: the re-run's fetch records `unchanged`/`not_modified`, `request_state.last_sha256` is the new object's but `last_loaded_sha256` is still the previous one, the loader drains the unloaded object, afterwards `last_loaded_sha256 = last_sha256`, and the final `curated.observation` natural-key rows are identical to an uninterrupted run, with `known_at` equal to the original `fetched_at`. (b) Kill after asset upload and before the manifest commit, then re-run: the object is fetched again with a later `fetched_at`; final values and keys equal an uninterrupted run, `known_at` equals the re-fetch time, and no orphan row exists in Neon. (c) Staging rows of the killed run are not touched by the re-run; they are swept after 14 days or deleted when their object is loaded. (d) A load that rolls back (validation error) leaves `last_loaded_sha256` unchanged and the staging rows in place.
- AC-ING-6: rate limiter test: with `min_interval_s = 2`, 5 requests take at least 8 s on a fake clock; hour budget exhaustion defers remaining requests to `catchup` instead of exceeding it.
- AC-ING-7 (A2, failed-load retry): a load that fails validation (`error`) leaves the object unloaded and `request_state` consistent; the next run with an unchanged source (304) still loads the object from stored raw once the condition is gone (for example after a threshold change); no refetch occurs; `known_at` is the original `fetched_at`; catch-up logic selects the group for load only.
- AC-ING-8 (A5, ordering, fix 4): with objects O1 (t1) and O2 (t2) of one group (also when they belong to different request keys) both unloaded, the loader loads O1 then O2; if O1 fails, O2 is held (`ORD-02`) and loads after O1 is loaded or skipped by decision; `load --raw-id O2` while O1 is unloaded is refused. An object whose series already have rows with later `known_at` is recorded as `skipped_out_of_order` (`ORD-01`) and replay honours it.
- AC-ING-9 (A3, concurrency): run `fetch`+`stage` of two workflows concurrently on the DB container (refresh group G1 and manual group G2); `plan` of a third run executes in between; no staging row of another run disappears; both drains complete, the final state equals sequential execution, and no duplicate observations exist.
- AC-ING-10 (A4, fix 5; extended in round 6): a group with `reestimating: true` whose object revises 90 % of keys loads with `revision_class = 'reestimation'` and no block while the material revisions stay below `max_revised_rows`; above the cap the object is blocked with a `mass_revision` drift event; a group with neither flag blocks at REV-01 (> 20 % of keys materially revised) but does not block when 90 % of keys differ only below materiality or below published precision; a named-edition group (`edition_ordered: true`, `reestimating: false`) whose object revises 100 % of keys materially loads without a drift event, with `revision_class = 'regular'` and REV-07 reported (ADR-017). With `snapshot_mode: diff_above_tol`, a release changing every key by less than the tolerance inserts zero revision rows, writes a `raw_snapshot`, and `rows_below_tol` equals the changed key count.
- AC-ING-11 (B12): every `parser_id` found in fixtures resolves through the registry; removing a released parser version from the registry fails the test.
- AC-ING-12 (A2, human decision): a series drift event leaves the series deferred while other series of the object load; after the event is accepted and the mapping switched, the deferred series load from stored raw (no refetch) under the new version with the original `known_at`; a rejected event appends `'rejected'` and loads nothing.
- AC-ING-13 (fix 8): `plan`/`sync-config` rejects a request with `fetch_mode = incremental` and `expect_scope = complete`; a partial/incremental object in which a stored key is absent inserts no tombstone; only a full complete object does.
- AC-ING-14 (fix 8): for a group whose transform is `M3M3_ANN` or `QOQ_ANN`, `sync-config` rejects a headline series with `seasonal_adjustment` outside `('SA','SCA')`.
- AC-ING-17 (round 5, `MISS`): a fixture with `missing_markers: [":"]` and cells `1.2`, `:`, `1.3` stages three observations, the middle one `MISS` with `value` NULL and `source_flags = ':'`; the DB accepts it (`obs_value_presence`), `v_observation_latest` returns it with NULL value, `v_headline_obs_observed` returns it but analytics treat it as no value; a later object with `1.4` for the same period inserts a `revision` row; an identical `:` in a later object inserts nothing; a key present as `MISS` is not tombstoned by a complete fetch that still contains it.
- AC-ING-18 (round 5, edition order, PROPOSED P22): objects E1 (`edition_date` 2026-04-14), E2 (2026-10-13) of one `edition_ordered` group committed in the order E2, E1: E2 loads; E1 is recorded `skipped_out_of_order` with `detail.reason = 'older_edition'` and ORD-03, and does not block a later object E3 (2027-04-13); E1 re-submitted under a new path with `import_label: archive_import` loads with `load_kind = 'import'`, does not change `v_observation_latest`, `fn_observation_asof` or any analytics input, and is absent from `v_revision_history`; an object with the same `edition_date` as E (corrected file) loads normally.
- AC-ING-19 (round 5, `hash_only`): a `hash_only` fixture has no asset (`storage_backend = 'none'`); a forced load failure followed by staging sweep records `rejected` with `bytes_unavailable`; the next `plan` refetches and writes a new `raw_object` even though the sha256 equals the previous object's, and the loader loads it.
- AC-ING-20 (round 6, announced by ADR-013; connector conformance): for every connector class the `Connector` protocol has exactly the members `source_id`, `plan`, `fetch` and `parse` (no `describe_series`), with the signatures of section 2 (checked with `typing`/`inspect`); for every non-discovery fixture, `parse` returns an output that has both `metas` and `observations` (non-empty `metas`; `observations` may be empty only for a series set that has none); for a `discover: true` fixture `metas` is non-empty and `observations` is empty (ADR-013: discovery is `parse` with a filter that yields metadata only). Runs with `unit`, no network.
- AC-ING-21 (round 6, first-sight series creation, ADR-018; `db`): a fixture object with a mapped, unseen series creates exactly one `ref.series` row (version 1, `first_seen_at = fetched_at`, metadata from `series_meta_load`, composition from `expect.composition`) and the config's `ref.series_map` rows in the same transaction as its observations; a rollback of the load leaves no series row; a second drain creates nothing; metadata that differs from `expect` creates no row, raises a drift event and defers the series while other series of the object load; an unknown `unit_code` creates no row; a staged series absent from the series map is never created; rebuild from raw into an empty database after `sync-config` re-creates the same series rows (natural key `(source_id, dataset_id, series_key, version)`).
- AC-DEP-1 (round 6, ADR-016; `unit`): an `ast`-based test walks every module under `src/macro_monitor/` and fails if `pandas`, `pandera` or `statsmodels` is imported anywhere except `analytics/` (all three) and `validation/` (`pandas`, `pandera`); the test lists the allowed packages in one place and has a negative case (a synthetic module outside the allowed set).
- AC-ING-22 (Phase 2 amendment, 2026-10-27, `RawStore` and the local-directory backend, section 4a; `unit` for (a) to (e), `db` for (f)): (a) `put` then `get` of a fixture on a temporary `local_dir` root returns identical bytes and the stored object decompresses to exactly the input; `put` of the same sha256 twice is a no-op (one file), `put` of an existing name with different bytes raises, and the API offers no delete or overwrite; (b) `get` of a file whose content was altered on disk raises `bytes_corrupt` and returns nothing; (c) `exists` is true after `put` and false for an unknown sha256; (d) with `MM_ENV=production` and `MM_RAW_STORE=local_dir`, `plan` and `load` exit 20 and touch no table; with `MM_ENV` unset the same setting is accepted; (e) a mock-transport `release_public` backend (no network) passes the same (a) to (c) cases, so the protocol is exercised by both backends from one parametrised test; (f) the scripted scenarios of AC-ING-4 (including the A -> B -> A revert: three `raw_object` rows, two `raw_blob` rows, one stored object for the bytes), AC-ING-5 (a), (c) and (d), AC-ING-7 and AC-ING-12 run against the `local_dir` backend with identical expected natural-key rows, and the resulting `raw_blob` rows carry `storage_backend = 'local_dir'` and `storage_ref` equal to the relative path.
- AC-ING-23 (ADR-027, ADR-028; `unit`): a mock-transport fetch of a discovered group with a golden landing HTML resolves one URL and records `request_params.discovery` and `request_url` = the file URL; a second run with a rotated URL and the same logical key keeps the `prev_raw_id` chain; zero matches, two matches, an off-list host or a non-HTML landing give `error_class = discovery_failed` and no manifest row; validators are sent only for an equal resolved URL; a disabled group is absent from the `plan` matrix, `fetch` and `ingest-manual` on it exit 20 with the switch named, and `load` of an existing unloaded object of a disabled group still succeeds.

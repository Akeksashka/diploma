## 1. Global rules
- Runner: `ubuntu-24.04` pinned (not `latest`). Python 3.12. Third-party actions pinned to full commit SHA; Dependabot for `github-actions` and `pip`.
- Default `permissions: contents: read`; elevate per job only (`contents: write` for releases/heartbeat, `issues: write` for alerts, `pages: write` + `id-token: write` for the `site` job only). No job holds `actions: write` except the single (a0) step of `finalize`, which uses its own token (section 9).
- Secrets only via `secrets.*` into `env:` of the step that needs them; never echoed, never passed as CLI arguments, never written to artifacts. Fork PRs receive no secrets (GitHub default); no workflow uses `pull_request_target` with checkout of PR code.
- Dispatch inputs and script injection (A11e, second round). Security rule: a `${{ ... }}` expression is never interpolated into a `run:` script (nor into the `script:` of `actions/github-script`) when it carries user-controlled text. This covers `inputs.*`, `github.event.inputs.*` (`groups`, `path`, `mode`, decision ids and notes, `target_version`) and `github.event.*` fields controlled by users (PR titles and bodies, branch names, commit messages, issue text). Such values reach scripts only through `env:` of the step (`env: MM_GROUPS: ${{ inputs.groups }}`) and are read as quoted shell variables (`"$MM_GROUPS"`; never name a variable `GROUPS`, which is a special bash variable that ignores assignment and expands to the runner's group id) or passed to the CLI as a single quoted argument after validation against an allow-list pattern (`^[a-z0-9_,]*$` for groups, safe-path check for `path`, enumerations for `mode`/`decision`, length limit and character class for `note`). The CLI re-validates its arguments (never evaluates them in a shell). Trusted contexts such as `github.run_id` or `secrets.*` into `env:` are allowed. Test AC-WF-7.
- `timeout-minutes` on every job (fetch: default 120, overridden per matrix leg by the group's `job_timeout_min` in `config/sources.yaml`, OECD 300 because its budget of 8 downloads/hour makes ten or more dataflows take well over 120 minutes, BB28; load: 60; others: 30). A job that times out loses nothing committed: each raw object commits on its own and the hour/day budget counters are persisted, so the catch-up continues the remaining requests. `defaults.run.shell: bash` with `set -euo pipefail`.
- Environment variable `MM_REPO_URL` for the User-Agent comes from `github.server_url/github.repository` (no personal e-mail in the UA).
- Raw store and environment (Phase 2 amendment, plan OQ-04): the workflows `monthly-refresh`, `ingest-manual` and `decide` set `MM_ENV=production` and `MM_RAW_STORE=release_public` at workflow level (plain constants, not user-controlled). The CLI then refuses any other raw store (ingestion spec section 4a, invariant 4). `ci.yml` does not set `MM_ENV` and uses the local-directory store for its `unit` and `db` jobs.
- Artifacts: logs/JSON summaries and the export (retention 7 days; Free artifact quota 500 MB shared). Data for the load never travels as artifacts; it moves through Neon staging/manifest and release assets. The export artifact (`data/` plus `export-status.json`) is the hand-off from `finalize` to `site`.
- Exit semantics: any source-group failure yields job result `failure` for that matrix leg but does not cancel siblings (`fail-fast: false`); `finalize` runs `if: always()`.

## 3. Concurrency and locking (A3)

Workflows use different GitHub concurrency groups, so `monthly-refresh`, `ingest-manual`, `decide` and `migrate` can run at the same time. Safety comes from the database design, not from GitHub groups:

| Resource | Contention | Mechanism |
|---|---|---|
| Two runs of the same workflow | duplicate refresh | GitHub `concurrency` group per workflow (`mm-refresh`, `mm-manual`, `mm-decide`, `mm-migrate`, `mm-pages`), `cancel-in-progress: false`; GitHub keeps only one pending run per group, so it is not the only guard |
| `staging.*` | refresh fetch legs, catch-up, manual ingest | staging is per run: every row carries `run_id` and `raw_id`; no job truncates; `plan` does not clean staging; the loader deletes the staging rows of objects it has loaded; a sweep removes staging of runs finished more than 14 days ago (DDL spec section 4); a run never reads another run's staging |
| `ingest.raw_load` / `ingest.v_raw_unloaded` | loader selection | the loader's work queue is the view `ingest.v_raw_unloaded`: every archived raw object without an `ingest.raw_load` row (archived but unloaded), including objects from earlier or failed runs, processed in `fetched_at` order; the `raw_load` row is written in the same transaction as the load |
| `ingest.request_state` | fetch vs load | validators/update markers (ETag, last-modified, last-seen update marker) advance only after the corresponding load commit; a fetch that archives an object but whose load fails therefore leaves `request_state` unchanged, and the next fetch or catch-up repeats or reuses the stored object instead of skipping it |
| `curated.observation` writes and analytics cutoffs | two loaders; a loader and an analytics start | `pg_advisory_xact_lock(hashtext('mm-load'))` per raw object on a direct connection, taken BEFORE the loader reads `loaded_at = clock_timestamp()`; short transactions; `lock_timeout` 10 min, then the object stays queued. Round 5: the `analyze` step takes the same lock in one short transaction and reads `known_cutoff = load_cutoff = clock_timestamp()` (database clock), so a load that started before the cutoff and commits after it is waited for and a later load always has `loaded_at` above the cutoff (ADR-002; AC-ING-15) |
| Load order | manual vs refresh, retries | queue ordered by `fetched_at`; per series group strictly in order; out-of-order objects are skipped and recorded (ingestion spec section 5); an older manual edition is refused (ORD-03) |
| Raw release | refresh vs manual | each run has its own draft release (`raw-<date>-r<run_id>`); `finalize` publishes its own draft and any orphan drafts of finished runs; at 900 assets a continuation release `-p<N>` is opened (all parts published); small blobs are bundled per source and uploads are throttled to 600/hour (ADR-003, review round 3) |
| `migrate` vs pipeline | schema change during a run | `migrate` takes `pg_advisory_lock(hashtext('mm-migrate'))`, refuses to run while an `ingest.run` has `status = 'running'` and `started_at` within 6 hours, and pipeline jobs check the schema version at start (DB-03) |
| Pages deployment | catch-up overlapping refresh | `site` job has its own concurrency group `mm-pages` with `cancel-in-progress: false` [UNVERIFIED: exact behaviour of the deploy action] |
| `decide` vs loader | decision applied while a drain runs | decision updates are single statements; the drain re-reads decisions (and the group flags `reestimating` and `edition_ordered`) per object under the load lock |

## 4. `monthly-refresh.yml`

Triggers:
```yaml
on:
  schedule:
    - cron: "23 4 1 * *"     # refresh (UTC)
    - cron: "23 4 4 * *"     # catch-up: failed/skipped groups and unloaded backlog
  workflow_dispatch:
    inputs:
      mode:   {type: choice, options: [refresh, catchup], default: refresh}
      groups: {type: string, description: "comma-separated group ids; empty = all due"}   # read only through env (rule A11e)
      dry_run: {type: boolean, default: false}   # fetch+parse+validate, no load, no release publish
concurrency: {group: mm-refresh, cancel-in-progress: false}
```
Mode is derived from `github.event.schedule` (`... 4 1 * *` => refresh, `... 4 4 * *` => catchup) or the dispatch input (via `env`).

Catch-up (`catchup`) description: (1) re-fetches only groups whose fetch did not succeed this month or were skipped; (2) drains the load backlog: every archived raw object that is still unloaded (no `ingest.raw_load` row; from earlier runs, failed loads, accepted `decide` decisions) is loaded from stored raw in `fetched_at` order without refetch (objects of `archive: hash_only` sources cannot be re-staged after the 14-day staging window, ADR-003); (3) does not advance `request_state` for an object until its load has committed; (4) is idempotent, so running it twice changes nothing.

Jobs:

| Job | needs | Steps (summary) | Outputs / effects |
|---|---|---|---|
| `plan` | - | checkout; setup Python (lockfile cache); install; Neon warm-up with retry; check schema version == expected; `sync-config` (entities including `WLD`, indicators including support indicators with `is_support`, group flags such as `reestimating` and `edition_ordered`); `plan` (refresh: fetch groups = all enabled and due; catchup: fetch groups = groups whose fetch did not succeed this month or were skipped; load groups = fetch groups plus every group with archived-but-unloaded objects in `ingest.v_raw_unloaded`); open draft release `raw-<date>-r<run_id>`; does not touch staging | `fetch_matrix` JSON of group ids with each group's `job_timeout_min`; `load_groups`; `run_id`; `release_tag` |
| `fetch` | plan | matrix over `fetch_matrix` (`fail-fast: false`, `max-parallel: 4`; `timeout-minutes` per leg from `job_timeout_min`); `fetch --group`; upload new blobs to the draft release; commit manifest and write per-run staging per object (an object without an `ingest.raw_load` row is by definition archived-but-unloaded, see `ingest.v_raw_unloaded`); does NOT advance `ingest.request_state` | per-group status in `ingest.fetch_attempt` |
| `load` | plan, fetch | `if: always() && needs.plan.result == 'success'`; `load --drain` over `load_groups`: take objects listed by `ingest.v_raw_unloaded` in `fetched_at` order (per series group strictly in order), read the run's own staging, validate (ADR-007; REV-01 uses the half-unit materiality rule and skips groups flagged `reestimating` (REV-06) and named-edition groups flagged `edition_ordered` (REV-07, report only, ADR-017)), insert-on-change under the load lock (a mapped series seen for the first time gets its `ref.series` and `ref.series_map` rows in the same transaction, ADR-018), write the `raw_load` row and advance `ingest.request_state` in the same commit; then `analyze` (takes its cutoffs from the database clock under the load lock; full and published sets; analytics only carry the `published_precision` display hint, they do not round values; entity `WLD` and support indicators are handled as in the analytics spec: global series only for `WLD`, support series used only inside transforms) | `curated`, `analytics.*`, `ops.validation_result`, `ingest.raw_load`, `ingest.request_state` |
| `r-analysis` | load | `if: vars.ENABLE_R == 'true'`, `continue-on-error: true`; `r-lib/actions` setup-r + setup-renv; run R modules | `analytics_r.*` |
| `finalize` | plan, load, r-analysis | `if: always()`; steps, each with only its own secret: (1) publish raw release (immutable) and any orphan drafts; (2) `monitor` (`mm_ingest`: freshness, DB size and projection, backlog, staging sweep, issue open/close); (3) `export` (`mm_reader`: writes `data/` and `export-status.json`, uploads artifact `site-export`; values are NOT rounded, `published_precision` is carried as a display hint in `meta/series.json`, export spec section 4; the run is selected through `analytics.v_run_published`, ADR-012); (4) `record-export` (`mm_ingest`: inserts `export-status.json` into the insert-only `ops.export_status`); (5) heartbeat commit (whether `GITHUB_TOKEN` may push to a protected default branch is [UNVERIFIED], BB26); (6) `backup` (monthly, refresh mode only): `--profile public` only; reads only the `pubdump.v_*` views in one `REPEATABLE READ READ ONLY` transaction, writes `manifest.json`, `schema.sql` and one gzipped CSV per view (ADR-015, `docs/specs/public-dump-spec.md`), runs the output self-check (BKP-03) and only then publishes release `db-dump-public-<YYYY-MM>`; round 5: there is no full profile and no private-repository release (no private repository; BKP-01 inactive, BKP-02 lists the sources that are in no dump) | issues; `ops.run_summary`; release `db-dump-public-<YYYY-MM>`; artifact `site-export` |
| `site` | finalize | `if: needs.finalize.outputs.export_ok == 'true'`; download artifact `site-export`; build static site; deploy to Pages (`pages: write`, `id-token: write`); concurrency group `mm-pages` | Pages deployment; on export or build failure the previous site stays and a `pipeline` issue is opened |

Failure alerting: `monitor` opens/updates/closes issues from `ops.validation_result` and run results (ADR-007). In addition a final step `if: failure()` in each job calls the same issue helper with key `[pipeline] <job> failed` and the run URL, so failures that occur before `monitor` can run are still reported.

Runner time budget (analyst estimate, unmeasured): `fetch` matrix about 60-120 min wall clock for most groups; OECD, budgeted to 8 downloads/hour, is the long pole: 8-10 dataflows fit in about 1-2 hours, but a larger dataflow list or retries can pass 120 minutes, hence the 300-minute leg timeout (BB28); `load` about 10-20 min, export plus site a few minutes, total billable minutes across jobs about 150-300 per month; free on public repos; if private, 2,000 min/month Free quota (tooling research, table D).

## 5. `ingest-manual.yml`
```yaml
on:
  push:
    branches: [main]
    paths: ["manual_inbox/**"]
  workflow_dispatch: {inputs: {path: {type: string}}}   # read only through env (rule A11e); validated as a path under manual_inbox/
concurrency: {group: mm-manual, cancel-in-progress: false}
```
Jobs: `ingest` (validate sidecar `*.meta.yaml`, including `edition_label` and `edition_date` for `edition_ordered` groups and an optional `import_label` whose only allowed value is `archive_import`; hash; draft release; archive; stage per run; `load --drain` for the manual group (and any backlog of that group), under which the loader applies the edition-order rule (ORD-03: an older edition is not loaded unless it is labelled as an archive import); publish release; comment on the commit/PR with a row-count summary; failure issue). Staging is per run, so a concurrent refresh is unaffected; the loader's advisory lock serialises only the short per-object load transactions (section 3). A push by `GITHUB_TOKEN` does not trigger this workflow (GitHub default), so heartbeat commits do not re-trigger anything (they touch `ops/`, outside the path filter anyway).

## 6. `preflight.yml`
Schedule `41 5 25 * *` and dispatch. Steps: sync-config; for every enabled group a minimal probe (single series or HEAD/small query) using the production HTTP client; robots/terms review age check (warn at 330 days); manual-download reminders; detection of Eurostat/OECD dataset-code changes via structure endpoints; opens `source-drift` issues. Uses `mm_ingest` read-only paths; writes no raw objects and does not touch `request_state`. Budget: at most 1 OECD request.

Manual-download reminders (A10, round 5): preflight runs only on the 25th of each month, so a reminder fires at the first preflight on or after its configured `remind_on` date, and `remind_on.day` cannot exceed 25 (source-config rule 11; the earlier configuration with day 26 could never fire). The WEO reminders are configured for 25 April and 25 October, after the expected window (which ends on the 24th) of the mid-April and mid-October releases [UNVERIFIED release months; to confirm against https://www.imf.org/en/Publications/WEO]. Preflight text: "WEO <edition> is expected to be published (mid-<month>) [release month unverified]; no inbox file for edition <label> yet: download it and commit to manual_inbox/ (FRESH-03)". The preflight reminder is evaluated only when preflight runs; if scheduled workflows are disabled, the human monthly check (section 9) covers it.

## 9. The 60-day rule, heartbeat and the fallback ladder (A6, second round)
Fact: public repositories have scheduled workflows disabled after 60 days without repository activity; the activity definition is not given by the documentation (accessed 2026-10-17). When it happens, all scheduled workflows of the repository are disabled together.

Review round 3 correction: the earlier "self-enable" step was withdrawn as "circular". That holds only AFTER disablement; a PREVENTIVE call by the monthly run before day 60 is not circular, so it is restored as rung (a0). Not relied on: a heartbeat produced by a non-scheduled path (`ingest-manual` on push, or `workflow_dispatch`): those paths only run when a human acts, so they cannot guard the unattended case, and it is unverified which of them count as activity.

Fallback ladder (use the first level that is verified to work; levels (b) and (c) are not alternatives to (a) but successive safety nets):
- (a0) Preventive enable call: a late step of `finalize` calls `PUT /repos/{owner}/{repo}/actions/workflows/{id}/enable` for `monthly-refresh`, `preflight` and `restore-test` with a fine-grained token `WORKFLOW_ENABLE_TOKEN` (permission `actions: write` only; `GITHUB_TOKEN` may lack it [UNVERIFIED]; the token's expiry date is checked in the monthly human check). A missing token or a failed call logs a warning and never fails the run. Whether the call resets the inactivity counter is [UNVERIFIED] (third-party claim only: https://github.com/PhrozenByte/gh-workflow-immortality, accessed 2026-10-18). Only this step holds the token.
- (a) Heartbeat commit by the schedule itself: the last step of `finalize` commits `ops/heartbeat.json` (run id, UTC time, group statuses; no data values) to `main` with `GITHUB_TOKEN` (`contents: write`; Actions must be allowed to push to `main`, no required reviews on `ops/`). Because the refresh (1st) and catch-up (4th) run monthly, an effective heartbeat resets the clock at least every 31 days. Whether a bot commit counts as repository activity is [UNVERIFIED]; AC-OPS-4 measures it. Round 5 (BB26): if `main` is protected (required reviews, required status checks, or a ruleset), a push with `GITHUB_TOKEN` is rejected; the first scheduled run records the push result in `ops.run_summary`, and the fallbacks are a ruleset bypass entry for the GitHub Actions app on `ops/**`, or a push by the (a0) fine-grained token with `contents: write`; a failed heartbeat push warns and never fails the run.
- (b) Documented monthly human check on the 2nd of each month (about two minutes), written in the repository docs (`docs/ops/monthly-check.md`, created in the implementation phase): (1) open the Actions tab and confirm a `monthly-refresh` run for the 1st; (2) confirm `ops/heartbeat.json` has a commit from that date; (3) confirm the site stale banner is absent; (4) confirm that no `pipeline` issue is open; (5) every April and October confirm the WEO file was committed (reminder issue). 0. (review round 3) The first scheduled `finalize` log shows (a0) executed (or a warning naming the missing token); at day 65 the owner records whether the workflows stayed enabled, as evidence for the [UNVERIFIED] effects of (a0) and (a) separately where possible.

## 10. Acceptance criteria
- AC-WF-1: `actionlint` passes on all workflow files in CI.
- AC-WF-2: a dispatched `monthly-refresh` with `dry_run: true` completes end to end against a Neon dev branch or the production DB without modifying `curated`, without advancing `request_state` and without publishing a release.
- AC-WF-3: when one matrix leg is forced to fail, the other legs, `load` and `finalize` still run, the failed group is reported in an issue, and the `catchup` run retries only that group (fetch), while any group with archived-but-unloaded objects is loaded from stored raw without refetch.
- AC-WF-4: two concurrent dispatches of `ingest-manual` and `monthly-refresh` produce a consistent database (per-object load lock, per-run staging) and no duplicate observations; neither run deletes the other's staging rows (AC-ING-9).
- AC-WF-5: no secret value appears in any log of a test run (grep of run logs for the secret prefixes in a controlled test with dummy secrets).
- AC-WF-6: a scheduled run on the 1st completes within 6 h per job; measured durations and compute hours are written to `ops.run_summary`.
- AC-WF-7 (A11e): a CI scan fails when `${{ inputs.* }}`, `${{ github.event.inputs.* }}` or user-controlled `github.event.*` expressions appear inside any `run:` block or `github-script` `script:`; a test dispatch with `groups` set to `x; echo INJECTED` fails pattern validation and executes nothing; each dispatch input of every workflow is shown by the scan to be consumed only through `env:`.
- AC-WF-8 (A6, revised in review round 3): the only workflow-enable call is the (a0) step of `finalize`, which uses `WORKFLOW_ENABLE_TOKEN` (not `GITHUB_TOKEN`), is non-fatal, and no other job holds that token or an `actions: write` permission; the monthly human check is written in the repository docs; AC-OPS-4 (section 9) is executed on days 7, 55 and 65 and its outcome recorded.
- AC-WF-9 (A7): in `finalize`, the `export` step sees only `NEON_URL_MM_READER`, `record-export` only `NEON_URL_MM_INGEST`, and `site` no database secret (checked by a workflow lint test over `env:` blocks).
- AC-WF-10 (A9, revised in round 5 and round 6; PROPOSED, design Q46): with a fixture source `archive: hash_only`, the public dump files (decompressed CSV, `schema.sql`, `manifest.json`) contain none of its observation values and the config is valid; with a fixture source `archive: private` and `archive_policy.private_repo: null` the config is invalid; no workflow references `RAW_PRIVATE_TOKEN` and no job writes a full or restricted dump (the `backup` step accepts only `--profile public`).
- AC-WF-11 (T1 alignment): a fetch whose load fails (forced error) leaves `ingest.request_state` unchanged and the object listed in `ingest.v_raw_unloaded` as archived-but-unloaded; the next `catchup` loads it from stored raw in `fetched_at` order and only then advances `request_state`.

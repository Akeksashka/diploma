# ADR-008: Neon operating model: roles, connections, cold starts, limits budget, migrations

Revision note (review fixes): complete grant matrix and reconciliation of the read-only export role with export status (A7); run-scoped staging replaces "truncate per run" (A3); published-only access for `mm_reader` (A8); spikes for CU-hour measurement and `btree_gist`/role creation (D). See the change log at the end for the 2026-10-18 fixes. Round 5 (2026-10-24): the analytics step shares the load lock; dumps are public only (no private repository).

## Context
- Neon Free (https://neon.com/docs/introduction/plans, accessed 2026-10-17): 1 GB storage per project; 100 CU-hours per project per month; autoscaling up to 2 CU; compute suspends after 5 minutes of inactivity and this cannot be disabled; 6 hours of change history (up to 1 GB-month); egress 5 GB per project per month (shared across services); 10 branches; 1 manual snapshot. When CU-hour or egress limits are hit, compute is suspended until the next billing period; the page states none of the limits delete data. The page states nothing about inactivity deletion or cold-start time.
- Connections (tooling research G; https://neon.com/docs/connect/connection-pooling): `max_connections` 104 at 0.25 CU (97 usable); the PgBouncer pooler accepts up to 10,000 client connections.
- Cold start: current Neon docs describe activation as "a few hundred milliseconds" excluding network and other factors; older text gave 500 ms to a few seconds (search results read 2026-10-17: https://neon.com/docs/introduction/scale-to-zero and https://neon.com/docs/connect/connection-latency; primary pages not fully read). Not measured for this project.
- Neon terms permit plan changes by continued use (tooling research, finding 17); Neon is now under Databricks.
- `pg_advisory_xact_lock` works inside a transaction through a transaction-mode pooler (the lock lives with the transaction); only session-level locks (`pg_advisory_lock`) and session `SET` do not [general PgBouncer behaviour, UNVERIFIED for Neon's configuration]. Corrected in review round 3.
- How CU-hours are measured for the project (console, API, or neither) was not verified; role creation and `CREATE EXTENSION btree_gist` by SQL on Neon were not verified.

## Options considered
1. Neon Free as the single Postgres, with a role-per-purpose model, direct connections for writers and a pooled connection for read-only/short sessions.
2. Supabase Free: pauses after about one week of inactivity and has 500 MB (tooling research G): worse for a monthly job.
3. Self-hosted Postgres: no free always-on host.
For the export status (added 2026-10-18): (a) merge it into `ops.run_summary` via `mm_ingest` (previous design; mixes loader and export writes in one row); (b) separate `mm_export` role with INSERT on one table (a sixth secret for one INSERT); (c) insert-only `ops.export_status` written by `record-export` under `mm_ingest` (chosen); (b) remains a drop-in alternative if the user prefers stricter separation.

## Decision
Option 1.
- Roles (created by the migration runner as the owner role): `mm_owner` (DDL only, used solely by the `migrate` workflow), `mm_ingest`, `mm_analytics`, `mm_r`, `mm_reader`. The complete cell-by-cell privilege matrix is normative in `docs/specs/ddl-neon-schema.md` section 8 and is enforced by test T-DDL-10. Per-role grant matrix (summary; the DDL spec wins in case of conflict):

| Role | SELECT | INSERT | UPDATE (column-restricted unless stated) | DELETE / TRUNCATE |
|---|---|---|---|---|
| `mm_owner` | n/a (DDL only; owns all objects) | DDL | DDL | DDL |
| `mm_ingest` | `ref.*`, `ref.config_history`, `ingest.*`, `staging.*`, `curated.*`, `ops.*`, `analytics.run` | `ref.*` config tables (no DELETE; rows closed by `valid_to`/`enabled`), `ref.series`, `ingest.run`, `request_state`, `raw_blob`, `raw_object`, `raw_snapshot`, `raw_load`, `raw_series_status`, `fetch_attempt`, `staging.*`, `curated.observation`, `ops.validation_result`, `freshness_state`, `run_summary`, `export_status`, `drift_event`, `drift_decision`, `quality_override` | `ref.*` config tables; `ref.series(is_active, published_decimals)`; `ingest.run(status, finished_at)`; `ingest.request_state` (all columns); `ops.run_summary`; `ops.drift_event(status, decided_by, decided_on, note)` | DELETE on `staging.*` only (per raw_id and sweep); no TRUNCATE anywhere; nothing on `curated.observation`, `ingest.raw_*`, history tables |
| `mm_analytics` | `curated.*` views and `observation`, `ref.*`, `ref.config_history`, `ingest.run`, `ops.*` | `analytics.*` (full and published sets) | none | none |
| `mm_r` | curated views (not the base table), `ref.*`, `ref.config_history`, `analytics.*` | `analytics_r.*` | none | none |
| `mm_reader` | only: `curated.v_headline_obs_published`, `curated.v_revision_history`, `curated.v_input_obs_published` (round 4), `analytics.*_published`, `analytics.v_alert_published`, `analytics.v_indicator_snapshot_published`, `ref.v_source_public`, `ref.v_series_export`, `ref.entity`, `entity_group_member`, `domain`, `indicator` (non-sensitive columns), `indicator_domain`, `ops.v_*` views | none | none | none |

  - Why `mm_ingest` holds these: it runs `sync-config` (ref writes), the fetch leg (manifest, staging, request_state), the loader (curated, raw_load, staging cleanup, run counters), monitoring (validation results, freshness), `record-export` (export status) and the `decide` workflow (decision rows). Each write is INSERT-only except the state rows listed; the database cannot prevent the loader from also acting as `decide` (same role), which is accepted and mitigated by workflow design.
  - Role creation by SQL on Neon is assumed supported [UNVERIFIED; spike AC-OPS-7]. One connection-string secret per role, named `NEON_URL_<ROLE>`.
- Export status without a write privilege (A7, revised): `mm_reader` never writes and never touches base tables (the revisions export reads `curated.v_revision_history`, not `curated.observation`). The `export` step returns `export-status.json` (inside the workflow artifact, not deployed); a following `finalize` step runs `record-export` under `mm_ingest`, which INSERTs one row into `ops.export_status`. `ops.run_summary.groups` is written only by the loader. Each step sees only its own secret.
- Who applies decisions (A7): `ops.drift_event` decisions and `ops.quality_override` rows are applied by the dispatch-only `decide` workflow under `mm_ingest` (column-level UPDATE grant on `drift_event`, INSERT on `drift_decision` and `quality_override`), recording the GitHub actor. Workflow inputs are passed through environment variables, never interpolated into shell. `mm_owner` stays DDL-only. The database cannot distinguish the `decide` workflow from the loader; the separation is by workflow design.
- Configuration history (fix 9): `ref.config_history` is fed by triggers whose function is owned by `mm_owner` (SECURITY DEFINER), so `mm_ingest` cannot write to it directly or bypass it. Round 5: the trigger set also covers `ref.domain`, `ref.entity` and `ref.source` (publish and archive flags).
- Connections: writers (`fetch`, `load`) use the direct (unpooled) endpoint because of session settings, the migrate session lock and predictable connection behaviour (the per-object `pg_advisory_xact_lock` alone would not require it); `analyze`, `r-analysis`, `export` may use the pooled endpoint. All sessions set `application_name` to the workflow/job, `statement_timeout`, and `idle_in_transaction_session_timeout`. Maximum 6 simultaneous connections from the pipeline (matrix 4 + load 1 + monitor 1), plus at most 2 from a concurrent `ingest-manual` or `decide` run. Round 5: the `analyze` step opens one short transaction (direct endpoint recommended, `lock_timeout` 10 min) in which it takes `pg_advisory_xact_lock(hashtext('mm-load'))` and reads `known_cutoff`/`load_cutoff` from `clock_timestamp()` (ADR-002); it then continues on its normal connection. No extra privilege is needed (advisory-lock functions are executable by every role).
- Cold start: the `plan` job runs `SELECT 1` with retry (up to 5 attempts, 1/2/4/8/16 s backoff, 30 s connect timeout) before any fetch. Every job opens its own connection through the same helper. Cold-start latency is recorded to `ops.run_summary.neon_connect_ms` so the first months produce the measurement the research lacks.
- Budget: monthly run expected at 1-3 compute hours at 0.25-2 CU, i.e. well below 100 CU-hours [analyst estimate; dashboards or R jobs that keep compute awake count too]. No live dashboard queries hit Neon; the site is built from exports. Egress: loaders write into Neon (not egress); `analyze` reads curated latest values only (tens of MB); the monthly dumps are about tens of MB. Alerts if monthly CU-hours or database size exceed 70 % of limits. Measurement source for CU-hours: candidate sources are the Neon console usage page or the Neon API [UNVERIFIED]; spike AC-OPS-6 verifies this after the first production run; if neither is usable, a proxy is recorded (sum of connected compute seconds measured by the pipeline x assumed CU) and labelled as a proxy. Database size via `pg_database_size`, with a 12-month linear projection (DB-02) and a per-object insert cap (DB-05). Storage worst case from re-estimating families and its mitigation (Parquet snapshots, tolerance-only loading) are in ADR-002 and DDL spec section 9 (round 5: about 1.7 GB/year without mitigation, 80-250 MB/year with it, at 220-300 bytes per row); spike AC-OPS-8 measures the real share of keys above tolerance.
- Staging hygiene (A3): `staging.*` is shared by all workflows and is run-scoped (`run_id`, `raw_id` on every row). Nothing truncates it. The loader deletes the rows of an object only in the transaction that commits that object's load; `monitor` sweeps rows of runs finished more than 14 days ago; `plan` does not clean staging; TRUNCATE is granted to nobody; the manual inbox uses the same tables, queue and load lock. A swept but unloaded object is re-staged from stored raw by the loader (not possible for `hash_only` objects: ADR-003). This keeps size well below 1 GB (whitelist-filtered rows) without any cross-run race.
- Migrations: forward-only SQL files `storage/migrations/NNNN_name.sql`, applied by `macro-monitor migrate` (workflow `migrate`, manual dispatch, runs under `mm_owner`, takes the migrate advisory lock, refuses to run while a pipeline run started within 6 hours is `running`, records checksum in `ops.schema_migration`). Pipeline jobs check that the applied version equals the version the code expects and fail fast otherwise.
- Recovery: Neon's 6-hour history is treated as a convenience only; real recovery is ADR-003 (rebuild from raw under the stated prerequisites in ADR-002, the monthly public dump, quarterly restore test). Round 5: there is no private repository (user decision 2026-10-18), so there is no full dump; values of sources outside the public/public partition have no backup (ADR-003, R34).
- Vendor-change plan: all SQL is plain Postgres (no Neon-only features); migration to another Postgres (or Supabase) is a restore of the dump. Extension use is limited to `btree_gist` for the one-headline exclusion constraint, with loader enforcement plus test as the fallback if unavailable.

## Consequences
- Secrets: five connection strings (only the roles actually used by enabled workflows). Fork pull requests get no secrets (GitHub default), so integration tests that need Neon do not run on forks; CI uses a Postgres service container instead (ADR via design doc, testing).
- Free-tier terms can change; the exit plan above bounds the risk.
- Inactivity deletion is not documented either way; the monthly dump makes it survivable for public/public sources only.
- The grant matrix is large but checked mechanically (T-DDL-10); any new table must add its row to the matrix and the expected-matrix fixture.
- Spikes before the first migration/run (cheap, [UNVERIFIED] assumptions): AC-OPS-7 (`CREATE EXTENSION btree_gist`, role creation and grants on a Neon dev branch, SECURITY DEFINER trigger functions) and AC-OPS-6 (CU-hour measurement); after the first real releases AC-OPS-8 (tolerance calibration for re-estimating groups).

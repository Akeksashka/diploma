# ADR-001: Orchestrate the pipeline with GitHub Actions and a single Python CLI (no orchestrator, no n8n)

Revision note (review fixes): the "self-enable" call is removed as a mitigation (circular, A6); concurrency story made explicit (A3); catch-up also drains the unloaded backlog (A2). Second round (2026-10-18): explicit fallback ladder for the 60-day rule; load queue and `request_state` semantics aligned with `ingest.raw_load` / `ingest.v_raw_unloaded` (see change log). Round 5 (2026-10-24): queue naming corrected everywhere; heartbeat push to a protected branch registered as BB26.

## Context
- Refresh is monthly on day 1 (indicator selection, "Refresh design principle"); the project is non-commercial, public, strictly free, no card on file; collection, storage and the future dashboard must run on the web, not on the user's Mac (tooling research, "User constraints").
- The user agreed on R/Python + Neon + GitHub Actions and wants Actions to run both the scheduled automation and the web collection.
- GitHub Actions facts (accessed 2026-10-17): `schedule` runs in UTC, minimum interval 5 minutes, can be delayed at high load (start of each hour is a peak), queued jobs may be dropped, runs only on the default branch, and in a public repo scheduled workflows are disabled after 60 days without "repository activity" (the page does not define activity). Job limit 6 h, workflow run 35 days, 20 concurrent jobs on Free, matrix max 256 jobs, `GITHUB_TOKEN` 1,000 REST requests/hour/repo. Source: https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows and https://docs.github.com/en/actions/reference/limits. Standard runners are free for public repos (tooling research, table D).
- Runners are ephemeral, so any state (last ETag, last-seen update marker, load status of fetched objects) must live outside the runner.

## Options considered
1. GitHub Actions + one Python CLI (`macro-monitor plan|fetch|load|analyze|monitor|export`); state in Neon. Zero extra components.
2. n8n Community Edition. Needs an always-on host; the only free host checked (Render) sleeps and has no free cron/worker; Python Code node cannot import project libraries; no Git versioning of workflows in Community Edition (tooling research, findings 21-22). The user stated n8n is not required.
3. Prefect Cloud Hobby (free, 5 deployments, 7-day retention) or Dagster/Airflow self-hosted. Adds a service and an agent/runtime for one monthly job; Dagster+ has no free tier (tooling research, finding 8).
4. cron on a self-hosted machine. Violates "runs on the web".

## Decision
Option 1. Specifically:
- One Python package, one CLI entry point, one workflow per concern (see `docs/specs/workflows-spec.md`): `monthly-refresh`, `ingest-manual`, `preflight`, `ci`, `migrate`, `restore-test`, `decide` (human decisions, dispatch only).
- `monthly-refresh` topology: `plan` -> `fetch` (matrix by source group, `fail-fast: false`, `max-parallel: 4`; archives raw objects and per-run staging) -> `load` (single job; drains the queue of archived-but-unloaded raw objects, that is the raw objects without an `ingest.raw_load` row, listed by the view `ingest.v_raw_unloaded`, in `fetched_at` order, validates, loads, then analyses) -> optional `r-analysis` -> `finalize` (publish raw release, monitor, export, record export status, heartbeat, backup) -> `site`. Failure of one source group never blocks the others.
- Schedules (UTC, minute not 0 to avoid the hourly peak): refresh `23 4 1 * *`; catch-up `23 4 4 * *` (re-fetches only source groups that failed or were skipped and loads any unloaded raw objects from stored raw without refetch; idempotent); preflight `41 5 25 * *` (tiny live probes, robots/terms re-check, to catch API drift before the 1st).
- Every stage is idempotent and re-runnable; state between runs lives in Neon: validators and update markers in `ingest.request_state`, which advance only after the load of the corresponding object has committed (a failed load never makes the next fetch skip data), run status in `ingest.run`, and the load status of every archived object in the append-only `ingest.raw_load` (absence of a row = unloaded; view `ingest.v_raw_unloaded`; ADR-003). Staging is per run; no job reads or deletes another run's staging.
- Concurrency (A3): GitHub `concurrency` (`cancel-in-progress: false`) per workflow avoids duplicate runs of the same workflow, but different workflows (`monthly-refresh`, `ingest-manual`, `decide`) can overlap. Mutual exclusion for writes is done in Postgres: a per-object advisory transaction lock in the loader (which the analytics step also takes, briefly, to read its cutoffs; ADR-002), per-run staging that no job truncates, and a migrate lock (details: workflows spec section 3, DDL spec section 4). A concurrency group keeps at most one pending run and drops older pending ones, which is why it cannot be the only guard.
- Workflow security: user-controlled text (dispatch inputs and `github.event.*` fields) reaches scripts only through `env:`, never by `${{ }}` interpolation into `run:` (workflows spec section 1).
- No orchestrator, no n8n.

## Consequences
- Cost zero on a public repo; if the repo becomes private, the 2,000 min/month Free quota applies (tooling research, table D) and the monthly run (estimated 1-3 runner-hours across matrix jobs, analyst estimate, unmeasured) plus CI must be re-budgeted.
- Scheduled workflows can be delayed or dropped and can be silently disabled after 60 days of inactivity. Review round 3 correction: a self-enable call is useless only AFTER the schedule is disabled (then nothing runs to make it); a PREVENTIVE call made by the monthly run about 30 days in, before day 60, is not circular. It is therefore restored as rung (a0) below. A heartbeat from a non-scheduled path (`ingest-manual`, dispatch) is not a protection either: it runs only when a human acts. The explicit fallback ladder is: (a0) the scheduled `finalize` calls the enable-workflow API (`PUT /repos/{owner}/{repo}/actions/workflows/{id}/enable`) with a fine-grained token that has `actions: write` (`GITHUB_TOKEN` may lack it [UNVERIFIED]; the token is a repository secret and its expiry is checked in the monthly human check); a failure or missing token is a warning, not a run failure; whether the call resets GitHub's inactivity counter is [UNVERIFIED] (third-party claim only: https://github.com/PhrozenByte/gh-workflow-immortality, accessed 2026-10-18); (a) heartbeat commit by the scheduled `finalize` (monthly; whether a bot commit counts as repository activity is [UNVERIFIED]; whether `GITHUB_TOKEN` can push to a protected default branch is [UNVERIFIED], register BB26); (b) a documented monthly human check on the 2nd, the only level independent of GitHub's scheduler; (c) an optional external free dead-man ping [OPTION, UNVERIFIED, not adopted; needs a new ADR and the user's decision, design Q15]. The dashboard stale banner (browser-side, on `known_cutoff`) is a further non-workflow signal. AC-OPS-4 is time-boxed (checks at day 7, 55, 65, 125 after the first scheduled run; workflows spec section 9) and decides whether (c) is needed. The catch-up cron covers delays and drops, not a disabled schedule. See ADR-007.
- Observability is limited to GitHub run logs (retention not stated on the limits page), Neon `ops.*` tables and GitHub Issues.
- Lock-in to GitHub is accepted; the CLI is runnable locally for development and disaster recovery.

- Review round 3: rung (a0) preventive enable call restored (the "circular" argument applied only after disablement); AC-OPS-4 additionally checks that (a0) runs in `finalize`, that its failure only warns, and records on the first real 60-day window whether the workflow stayed enabled.
- Decision: `load` described through the append-only `ingest.raw_load` and the view `ingest.v_raw_unloaded`; `request_state` advances only after the load commit; per-run staging; workflow security rule for user-controlled text.
- Consequences: circular self-enable and non-scheduled heartbeat paths rejected; explicit fallback ladder (a)/(b)/(c) and time-boxed AC-OPS-4.
- Round 5 (2026-10-24): the former load-state table name is replaced by `ingest.raw_load` / `ingest.v_raw_unloaded` in the decision and the revision note; the analytics step shares the load lock (ADR-002); stale banner basis `known_cutoff`; heartbeat push to a protected branch noted as BB26 (design section 13a).

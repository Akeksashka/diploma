# ADR-034: Analytics-dashboard layout (sticky filter bar, KPI tiles, ranked comparison cards, heatmap and small multiples, indicator tables with sparklines, section bands, card surface) (amends ADR-030 and ADR-025)

Date: 2026-11-09 (amendment A1: 2026-11-10). Labels: [REPO] read in this repository this session; [USER] stated by the user in session 2026-11-09 (the reference screenshots were described to me, not seen by me: sticky top filter bar with dropdown filters and a date-range chip, section header bands, KPI tiles, donut charts with legend and percentages, a horizontal funnel, weekly bar charts, comparison tables with a Total row, white cards on a light grey background); [UNVERIFIED] not checked. No web source was used. How Metabase itself behaves (filter wiring, card interactions) was not checked; this ADR adopts visual and structural patterns from the user's description only.

## Context
- [USER] Feedback 2026-11-09: (1) data is incomplete (handled separately: real data for 44 entities = 42 countries + EU27 + euro area); (2) the dashboard is hard to read and needs a better UI/UX in the style of a Metabase analytics dashboard.
- [REPO] Today's pages are built (ADR-030, redesign R1-R23): `index` is two static link lists plus three links; `country/<id>` is a stack of per-domain sections (figure line, dot strip, long table); `indicator/<id>` is a facts list, controls, value bars, dot plot and a long table; `explorer` is a left-rail control panel plus chart; `domain/<id>` is the V1 heatmap. Pages are single-column text-and-table flows on a white background (`site/src/style.css`: `--mm-bg #ffffff`, `--mm-surface #f6f8fa`, per-view table styles). Each page has its own controls; no control is shared, no filter survives navigation, and there is no global frequency, domain or date-range selection. The header is static HTML (`observablehq.config.js` `header`), so a filter bar that needs `meta/*` must be rendered by page code.
- [REPO] Data model facts that bound the patterns: scorecards carry latest values only (one value per entity x indicator, with `ref_period_end`, percentile, state fields); series history exists only in `series/<indicator_id>.parquet` (Parquet reader about 1.8 MB gzipped, AC-RD-53); `meta/indicators.json` has `frequency_set[]`, `priority`, `unit_label` (CR-5 `unit_text`, `unit_text_varies` proposed, not approved), `domain_ids`; `meta/entities.json` has `kind` (country, aggregate) and `group_ids`; `meta/groups.json` has members. Mixed frequencies exist across indicators and within an indicator (`frequency_set`). Aggregates EU27 and EA are stored entities with `percentile = null`. `meta/domains.json` is written in `domain_id` order (alphabetical: `agri` first in the real export, an unranked domain); `ref.indicator.priority` is the `core | ext | opt | dropped` selection class of the config, not a display rank.
- Fixed rules that the new layout must keep: static site, read-only export, no off-origin request (ADR-010, ADR-023 decision 4); Observable Framework 1.13.4 + Plot 0.6.18 + d3 7.9.2 and no new npm dependency (ADR-024 decision 1, AC-RD-52); browser never computes rank, percentile, mean, sum, count of entities, position, n/N or overall status (D6, ADR-010 decision 1, spec 1.1, AC-RD-50), with the single exception of ADR-036 (hidden-rows disclosure: count plus list); neutral percentile scale and no good/bad colour (ADR-025 decision 2, ADR-026); data-only rule: no explanatory pages or prose (ADR-030, spec 1.6); WCAG 2.2 AA (ADR-025 decision 8); landing set at most 1.5 MB gzipped (internal target 600 KB), one interaction at most 5 MB (ADR-023 decision 6); CSS at most 20 KB gzipped (AC-UX-12); hash-based shareable state with `replaceState` (spec 1.5).

## Options considered
1. Adopt the reference patterns literally (donut with percentages, funnel, Total row, KPI deltas coloured green/red). Rejected for the quantities involved: donut percentages and a Total row are counts, sums or means computed in the browser (D6); a funnel needs an ordered process with stage counts, which no stored quantity is; coloured deltas need a computed change (CR-11 is not approved) and imply good/bad (ADR-026). Details in "Pattern adoption table".
2. Restyle only (grey canvas, cards, bands) and leave per-page controls. Cheap, but does not deliver the filter bar the user asked for, and navigation still discards context. Rejected.
3. One interactive dashboard page with a shared filter bar and cards, plus the same bar and cards re-used on the entity pages, state in the URL hash, all stored data (chosen).
4. Filter-bar implementation: (a) native controls (`<select>`, checkbox lists inside `<details>`, year selects) with plain DOM code (chosen); (b) a combobox, multi-select or date-picker library (rejected: new dependency, ADR-024 rule 1; accessibility risk of custom popovers); (c) hand-built ARIA combobox (rejected: cost and WCAG risk without a benefit for lists of 44 and about 80 items).
5. Sparklines: (a) read `series/*.parquet` for every visible row (rejected: loads the Parquet reader and up to 80 files on a profile page; breaks the 600 KB first-load target); (b) store a short recent-values array per scorecard row (CR-1, existing, optional), the browser only draws it (chosen as phase B); (c) omit sparklines until (b) (phase A fallback, used if CR-1 is not approved or exceeds its weight budget).
6. Where the filter state lives: (a) `sessionStorage` (rejected: hidden state, not shareable, not in the printed page); (b) URL hash only, links built by the bar carry the hash to other pages (chosen; extends spec 1.5).

## Decision
1. Shell and surface. Page canvas is light grey; content sits in white cards (`--mm-canvas`, `--mm-card` tokens, dark-theme equivalents, contrast checked by AC-UX-1). Content is grouped under section bands (a full-width band carrying the section name, one `h2`). Layout is a 12-column CSS grid of cards with three width classes (ADR-025 decision 7). Own classes (`mm-grid`, `mm-card`, `mm-band`), not Framework's `.card`/`.grid`, to avoid coupling to Framework variable names (ADR-025 risk). No shadows required; a 1 px card border token is used.
2. Sticky filter bar (shared component, rendered by page code under the static header, `position: sticky`). Controls: Group (a `<select>`: "All countries" or a group of `meta/groups.json`), Country (a multi-select chip: a `<details>` with a text filter and a checkbox list, up to 5 selected, default "All countries", i.e. nothing selected; aggregates listed under an "Aggregates" sub-list), Domain, Indicator, Period (date-range chip), Frequency, and a Reset button. There is no single "Scope" control (amendment A1 item 3; the earlier text of this ADR named one). All are native controls; the period chip is two year `<select>`s with presets. State is in the URL hash (extends spec 1.5 with `d`, `f`, `from`, `to`); the bar writes it with `replaceState` after a user change only, and builds its links so that a click on a country or indicator name carries the current hash. Each page shows only the controls that act on it (applicability matrix in the spec); a control that does nothing on a page is not shown. On compact screens the bar collapses to a row of summary chips and a "Filters" disclosure. Focus is never obscured by the sticky bar (scroll padding; WCAG 2.4.11). In print the bar is hidden and replaced by one line stating the active filters.
3. Filters only filter, select and clip (D6). Group selects the comparison set (via `group_ids` / `meta/groups.json`; "All countries" = entities with `kind = country`); Country selects the focus entities (up to 5; none selected = no focus, the whole comparison set); Domain selects `domain_ids`; Indicator selects one indicator; Frequency keeps indicators whose stored `frequency_set` contains it and series whose stored `frequency` equals it (no resampling); Period clips the x-domain of time-based cards and sparklines (as a range; no row is hidden there) and hides scorecard rows whose latest `ref_period_end` is outside the range on the ranked comparison card and the indicator table only (user answer Q3; ADR-036), and does not alter any value. The hidden-rows disclosure (count plus list) is the one D6 exception (ADR-036).
4. Home becomes the dashboard (PG-HOME). Defaults: Group = "All countries", Country = none, Domain = the configured `default_domain` of `meta/domains.json` (CR-15; recommended value `growth`; not "first domain": the first domain of the real export is `agri`, an unranked domain), Indicator = first indicator of that domain in `indicator_ids` order. Page `h1` = "Macro dashboard" (DRAFT string). Cards, in section bands: (1) Overview: KPI tiles, only when the Country filter resolves to one entity; otherwise a "Choose a country" placeholder card; (2) Ranked comparison for the selected indicator; (3) Domain heatmap for the selected domain; (4) Indicator table with sparklines; (5) Time series / small multiples (loads history on demand). The static country and indicator link lists (spec C-HOME-2, C-HOME-3) are kept, moved into a collapsed "Browse" section at the bottom so that AC-RD-02/03/05 still hold without JavaScript.
5. KPI tiles show stored values only: indicator name, big stored `value` with its unit, reference period (with offset flag), the percentile bin chip with the stored number or the state code and sentence, estimate mark, and (phase B) a sparkline. A second tile type shows a ranked domain's stored `percentile_rank_label` / `percentile_rank` with the stored "n_available of n_defined" and `rank_position` rules (spec C-CTRY-1). Tiles that would need a change, delta or arrow are not offered (CR-11 not approved); no good/bad colour; no tile combines domains. Tile selection: one tile per indicator the user has pinned through the Indicator filter, then the indicators of the selected domain with `tile_headline = true` (CR-14, phase B) in `meta/domains.json` `indicator_ids` order, or, when none is flagged or the field is absent, all indicators of the domain in that order; at most 8. `priority` does not select tiles (it is the `core | ext | opt | dropped` class, not a display rank).
6. Ranked country comparison card (replaces the standalone value-bar block on the dashboard; the indicator page keeps its full table). Horizontal bars, one row per entity in scope that has a stored value, in a scroll container, sorted by the user's choice of Country A-Z (default), Value or Percentile, nulls last; bar length is the stored value on one axis only when all rows share one unit (`unit_text_varies = false` after CR-5; until then when `unit_label` has a single code), otherwise the card shows the percentile dot plot and the values as text. Bar fill is the percentile bin token, no percentile = neutral. No top-N cut: the whole list scrolls (a top-N cut by percentile would select by rank). Stored aggregate entities (EU27, EA) are pinned as a separate "reference" row group beneath the countries, styled apart, because they are stored values. There is no Total row and no average row (it would be a computed sum or mean).
7. Heatmap and small multiples. The V1 heatmap (HTML table, ADR-025 decision 4) is shown on the dashboard for the selected domain and scope; Frequency hides columns; there is no overall column and no cross-domain composite (U1 stays). Small multiples (Plot facets, one per entity, shared y-axis unit, max 12 facets per page view before "Show more" extends in blocks) are drawn for one indicator over the entities in scope from the sparkline arrays (phase B) or, until then, from the series Parquet file loaded when the user activates "Load history" (one file per activation, as spec AC-RD-14). The cap of 5 overlaid lines (ADR-025 decision 6) is unchanged.
8. Indicator tables with sparklines. Country and dashboard tables gain a Trend column: a small inline SVG of the last stored values (d3 scale and line; no Plot instance per row), latest point marked, estimate hollow, y-range per row, no colour by direction, accessible name giving unit, first and last stored value and period. Phase B depends on export change CR-1 (spec section 9). Without CR-1 the column is absent and nothing else changes.

## Consequences
- Positive: one shared place for filtering; context survives navigation; the value of the first screen rises (KPI tiles, ranked bars, heatmap) while D6 and the data-only rule are kept; a 44-entity export is handled by scroll containers and sticky columns rather than longer pages; sparklines and small multiples without the Parquet reader once CR-1 exists.
- Negative: more client-side code (filter store, bar, cards) and more states to test; the home page now needs `meta/*` and one scorecard on load (it was static before) so no-JS users see only the notice and the link lists; the user's donut, funnel and Total row are not delivered, which may disappoint (alternatives are stated); CSS growth against a 20 KB gzipped budget is unmeasured; CR-1 enlarges scorecards (estimate in the spec, unmeasured); sticky bar plus sticky table headers need careful offsets to keep focus visible; the D6 exception adds one browser-side count that must stay confined to one tested function, always shown with the list it counts (ADR-036).
- Risks: the Framework produces no server-rendered cell content (so the dashboard is blank without JS); reactive wiring of the filter store through Framework's `Generators` has to be proved on one card before all cards are built [UNVERIFIED]; defaults that show a single domain may hide a domain the visitor wants; filter semantics for Period (rows hidden, with the count and the list shown) may surprise users; CR-15 is an export change needed by phase A of the home page, so the default domain is a fallback until the user approves it.
- Reversal: the filter bar and cards are components over unchanged entity pages and an unchanged export; reverting restores the link-list home (ADR-030 decision 2) without touching the entity pages.

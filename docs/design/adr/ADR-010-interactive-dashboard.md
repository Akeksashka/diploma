# ADR-010: Interactive dashboard as a static GitHub Pages site with client-side interactivity (no live database queries)

Access date for every URL: 2026-10-17. Labels: [DOC] read on the primary page this session; [SEARCH] search-result summary only; [UNVERIFIED] not checked; "analyst estimate" = unmeasured arithmetic.

Revision note (review fixes): status corrected to `proposed` (only the user may approve); the withheld gate now uses separately computed published result sets (A8); export status is recorded by `mm_ingest`, not by the read-only role (A7); stale-banner wording tied to the non-circular dead-man detection (A6); alignment, informational domains and notices added to the displayed semantics (B1-B4). Round 5 (2026-10-24): stale banner basis is `known_cutoff`; decision 10 no longer refers to a modal window; domain-level percentile label.

## Context
- The user requires an interactive dashboard (use case U1: domain scorecards, no composite rank, where each country stands against peers; D6, D12, D16 of the approved indicator selection). The first design draft listed it as a non-goal; this ADR brings it into scope.
- Constraints: free, no card, runs on the web (not on the user's Mac), monthly refresh (day 1), 42 countries plus EU27/EA aggregates (and WLD for global series), mixed frequencies (M/Q/A), vintages preserved (ADR-002), no live dashboard queries against Neon (ADR-008: 100 CU-hours/month, compute suspends after 5 min idle, cold start unmeasured). Public repo assumed (ADR-001; research open question 2 on public vs private is still open, and Pages on the Free plan needs a public repo [UNVERIFIED for the current plan terms]).
- Data are published once a month, so the dashboard content is identical for all visitors between runs. There is no need for per-request computation.
- Facts:
  - GitHub Pages: published site at most 1 GB; soft bandwidth limit 100 GB/month; soft limit of 10 builds/hour, which does not apply to sites built and published with a custom GitHub Actions workflow; deployment times out after 10 minutes; prohibited: sites "primarily for commercial transactions or commercial SaaS" [DOC] https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits
  - DuckDB-Wasm runs DuckDB in the browser, can query remote Parquet using HTTP byte ranges via its JavaScript httpfs implementation (the built-in extension may download whole files, issue #2153), single-threaded by default, WebAssembly memory capped at 4 GB and browsers may impose lower limits [DOC] https://duckdb.org/docs/current/clients/wasm/overview.html
  - Streamlit Community Cloud: apps sleep after 12 hours of inactivity per forum staff statements; a post dated October 2026 reports apps stuck at startup after waking [SEARCH] https://discuss.streamlit.io/t/web-apps-keeps-on-sleeping-after-30-minutes-or-a-day-of-inactivity/97350 , https://discuss.streamlit.io/t/all-apps-on-my-account-stuck-at-startup-after-waking-from-sleep/122744 (docs page does not list limits: tooling research finding 15)
  - Posit Connect Cloud Free: public GitHub repos only; free allowance in usage credits; enforcement on Free accounts starts with the first usage period on or after 2026-11-01, after which apps stop running (published documents keep being served) until the next period; credit amount for Free not found [DOC] https://docs.posit.co/connect-cloud/user/usage.html (tooling research table I)
  - shinyapps.io Free: 5 apps, 25 active hours/month, 15 min idle timeout [SEARCH snippet, possibly outdated; support page returned HTTP 403] (tooling research table I)
  - Grafana Cloud free: 10,000 active metric series, 14-day retention, 3 users [DOC] https://grafana.com/pricing/ ; reading Parquet/CSV needs plugins or a SQL server [UNVERIFIED]
  - Quarto to GitHub Pages: render to `docs/`, `quarto publish gh-pages`, or a GitHub Action; `freeze: auto` stores computed results; interactive widgets/Observable JS inside static pages not verified by the research [DOC for publishing] https://quarto.org/docs/publishing/github-pages.html
  - Shinylive/webR: static, in-browser Shiny; only precompiled wasm packages; webR API "under active development"; mobile browsers restrict WebAssembly RAM [DOC] https://posit-dev.github.io/r-shinylive/ , https://docs.r-wasm.org/webr/latest/
  - Observable Framework: official page returned HTTP 429 this session (tooling research also failed to fetch it). From search summaries only: data loaders can be written in any language and their output is static files; its SQL support is built on DuckDB (DuckDB-Wasm) and reads CSV/JSON/Arrow/Parquet [SEARCH] https://observablehq.com/framework/lib/duckdb , https://observablehq.com/blog/data-loader-examples-r-python-shell-scripts-julia . Its GitHub Pages deployment steps were not found: [UNVERIFIED].
  - Evidence (Core, MIT): static BI site from SQL+Markdown, Node-based; DuckDB support not confirmed [DOC] https://docs.evidence.dev/ (tooling research table F)
  - Hugging Face: only Static Spaces are free [DOC] https://huggingface.co/docs/hub/spaces-overview (tooling research finding 15)

## Options considered
A. Static site on GitHub Pages, interactivity in the browser, fed by exported files (JSON for small tables, Parquet for series, optionally DuckDB-Wasm). Sub-options for the front-end toolkit:
  - A1 Observable Framework + Observable Plot (JS; Node build step; built-in DuckDB-Wasm/Parquet reading per [SEARCH]; Pages deployment unverified).
  - A2 Quarto website/dashboard with Plotly or Observable JS (Python/R-friendly, documented Pages route [DOC]; the interactive-widget support was not verified by the research; Observable JS inside Quarto and Plotly are [UNVERIFIED] here).
  - A3 Hand-written static HTML + ES modules with a charting library (Observable Plot or Plotly.js) and DuckDB-Wasm only for the explorer (no framework; the most boring, most code to own).
  - A4 Shinylive/webR (R Shiny in the browser): rejected inside A for this scope because package availability as wasm is unchecked and webR is unstable (above).
B. Hosted server app (Streamlit Community Cloud, Posit Connect Cloud, shinyapps.io, Dash): the app either queries Neon live (violates ADR-008, adds cold start, consumes the 100 CU-hour budget with visitors) or reads the same exported files (then a server adds nothing over A). Sleeping apps (Streamlit 12 h), start-up failures, Posit enforcement from 2026-11-01 (apps stop when credits are exhausted), shinyapps.io 25 active hours.
C. Grafana (Cloud free or OSS): built for operational metrics; free cloud tier has 14-day retention and 10k series; needs a SQL datasource, i.e. live queries against Neon (ADR-008) or a plugin for files [UNVERIFIED]; hosting OSS Grafana needs an always-on server (no free host found; ADR-001 option 2 reasoning). Weak fit for cross-country percentile scorecards and vintage views.
D. Static pre-rendered report only (Quarto/Plotly HTML, no client data loading). Cheapest, but selectors (country, indicator, transform) would need all combinations pre-rendered or large embedded data; this is A2 without the interactive data layer. Kept as the fallback if A fails the spike.

## Decision
Option A: a static site deployed to GitHub Pages by a custom Actions workflow (exempt from the 10 builds/hour soft limit [DOC]), built from files exported by the `export` stage from Neon in the `finalize` job. The browser never contacts Neon or any data source. Specifically:
1. Architecture rule: the dashboard reads only the files described in `docs/specs/dashboard-export-spec.md`. All arithmetic that defines meaning (transforms, percentile ranks, coverage n/N, staleness, reference-period alignment, alert levels) is computed in Python (ADR-006) and exported; the browser only filters, selects, sorts, plots and applies display-only rebasing (index = 100 at a chosen period).
2. Two data tiers: (T1) small JSON files for scorecards, peer ranking, alerts, status, metadata, which need no query engine; (T2) per-indicator Parquet files for series and revisions, read lazily on demand. T1 makes the main views work even if T2 or DuckDB-Wasm fails.
3. Front-end toolkit: the preferred candidate is A1 (Observable Framework + Plot), because it is static, uses data loaders and DuckDB-Wasm/Parquet natively [SEARCH], but its official documentation could not be read here. Therefore the toolkit choice is gated by a time-boxed implementation spike (acceptance criterion AC-DASH-0): build one scorecard page and one explorer page from fixture exports and deploy to Pages from Actions. If A1 fails, fall back to A2 (Quarto), then A3. The export contract is identical for all three, so the toolkit can change without touching the pipeline. This is the only toolkit decision left open and must be recorded in an update of this ADR (not by the implementer alone).
4. Node.js is a build-time dependency only (in the `site` job); it is not needed if A2 or A3 is chosen with a Python build. It runs on the Actions runner, never on the user's Mac.
5. Deployment: `finalize` runs `export` (role `mm_reader`, read-only, published views only), uploads the result and `export-status.json` as a workflow artifact, a `finalize` step with `mm_ingest` records the export status (`record-export`), and a separate `site` job builds and deploys the site with `actions/deploy-pages` or an equivalent official action [UNVERIFIED: exact action and environment-protection settings to check at implementation]. The `site` job has no database secret. Export files are not committed to git (avoids binary history bloat; Pages deployment artifact is the only copy). The previous site stays live if export or build fails (deploy only on success).
6. Vintages: the site shows the latest vintage as of the run plus a revision view built from `curated.v_revision_history`, with ordinary and systematic re-estimation revisions distinguishable (`revision_class`). Browsing whole historical snapshots of the site (time travel) is out of scope for v1; the source of truth for as-of queries stays Neon and the dump (ADR-002, ADR-003).
7. Redistribution gate (A8): a source marked `publish_site: withheld` (config field defined in `docs/specs/source-config-schema.md`) exports metadata only. The gate is enforced in the data layer: analytics computes the full result set (internal) and a second, publication-scoped result set (`analytics.scorecard_published` and the other `*_published` objects, with a `publish_scope` column) over publishable data only, so ranks, percentiles, `n_available`, alignment, reference-period fields and alerts shown on the site are functions of published values; the export reads only the published tables and views (the read role cannot see the rest) and never computes, re-ranks or filters meaning. Alerts, z-scores and revisions of withheld sources are omitted from every published file. Consequence: public entities' ranks on the site can differ from the internal full-set ranks; only the published set is shown. The leak test (AC-EXP-4) covers scorecards, alerts, revisions, status and metadata, and includes a perturbation test. Entity `WLD` and support indicators (`is_support`) are not exported as scored. The user must set the field for sources with unclear licences (design question 1/4). Pages must stay non-commercial (prohibited-use clause [DOC]).
8. Data freshness on the site (A6; basis corrected in round 5): the manifest carries `known_cutoff` (the data and analysis time) and `generated_at` (the build time), and the dashboard shows a banner when `known_cutoff` is older than 45 days. The basis is `known_cutoff`, not `generated_at`: a failed `analyze` must not be hidden behind a freshly built site (EXP-10 additionally refuses to export an analysis run from an older ingest run). The check runs in the visitor's browser, so it does not depend on a scheduled workflow and is a non-circular dead-man signal (design risk R1). The status view also lists the unloaded raw backlog and the human monthly check text.
9. Displayed semantics added by the review: every ranking shows the reference-period spread of the ranked entities and marks unaligned entities (B1); informational indicators and domains (Agri, Markets by proposed default, Global) show values without ranks (B2, B3, B9); the M18 spread is labelled "local-currency yield spread (includes inflation/FX expectations), not sovereign credit risk" for non-euro countries (B4); domains with low coverage show the mean percentile and n/N without a rank position (B8). The domain-level figure is labelled "mean percentile of the domain's indicators" (round 5; it is not uniformly distributed, analytics spec 4.4). Projections (A03) have no dashboard output in v1 (B9).
10. Cross-country ranks mix reference periods (dashboard question Q, T2-6): a ranking compares entities whose latest observations refer to different periods. This is handled by two per-indicator export fields produced by analytics under its common-reference-period ranking rule, `rank_reference_period` and `reference_period_spread_days`, plus the per-entity `ref_period_end` and `ref_offset_days`, shown beside every ranking. They are nullable only for unranked indicators; the export never derives them. (Round 5: the earlier fallback to a modal-window spread is withdrawn; the modal rule no longer exists in the analytics spec or the DDL.)

## Consequences
- Positive: zero added hosted services (Pages is already in the design for the status page); zero Neon load from visitors (ADR-008 budget unchanged); no sleeping app; deterministic, testable exports (golden files); the dashboard is reproducible from a database restore; works for any number of visitors within 100 GB/month soft bandwidth (about 20,000 full visits at 5 MB each; analyst estimate).
- Negative: no ad hoc SQL over the full vintage table in the browser, only over exported slices; every change to what the dashboard can show requires an export contract change and a re-run (acceptable for monthly data); the site is public (all exported values are public; licence gate required); the browser memory limits apply to the explorer (kept small by per-indicator files and size budgets); DuckDB-Wasm behaviour (range requests, memory) depends on the library version [DOC: caveat issue #2153].
- Risks: Observable Framework unverified (spike AC-DASH-0, two fallbacks); GitHub Pages terms and free-plan availability can change (design risk R14; the export files can be hosted on any static host, e.g. Cloudflare Pages or Hugging Face Static Spaces, not researched beyond the tooling research note); Pages requires a public repo on Free [UNVERIFIED]; the 10-minute deployment timeout [DOC] bounds site size in practice (budgets in the export spec are far below).
- Pages deployment mechanics remain [UNVERIFIED]: the exact deploy action, environment-protection settings, and whether Pages serves gzip and `Accept-Ranges` for JSON and Parquet files are not confirmed. Compression and range-request behaviour are measured in AC-DASH-0; until then size budgets assume whole-file, possibly uncompressed fetches.
- Work created: `export` stage (specified in `docs/specs/dashboard-export-spec.md`), `site` job in `monthly-refresh` (now in the workflows spec), `publish_site` field in source config (now in the source-config spec), published analytics tables, new tests (export contract, golden files, browser smoke test, withheld perturbation test), new design sections 3.1, 3.2, 8a, 11, 13.
- Superseded wording: design draft non-goal "interactive dashboard" and open question 8 (Posit/Streamlit versus static).
- Reversal: choosing B later is possible without changing the pipeline if the app reads the same exports (not Neon); choosing C requires a new ADR and revisits ADR-008.

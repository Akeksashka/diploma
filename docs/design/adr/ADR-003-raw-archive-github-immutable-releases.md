# ADR-003: Raw archive in GitHub immutable Releases, manifest in Neon, rebuild-from-raw as the recovery path

Revision note (review fixes): stored bytes are deduplicated separately from the manifest, so a source that reverts to earlier content (A -> B -> A) is loadable (A1); load status is tracked per raw object (A2); the public database dump honours licences (A9); the prerequisites of rebuild-from-raw are stated (B12). Round 5 (2026-10-24): reconciled with the user decision of 2026-10-18 that there is NO private repository (the restricted dump partition, the `private` archive mode and `RAW_PRIVATE_TOKEN` are inactive); meaning of `hash_only` stated. The round-5 reconciliation was CONFIRMED by the user on 2026-10-24 (design Q46): there is no private repository and the consequences are accepted.

## Context
- CLAUDE.md: raw data is immutable and stored with source URL, fetch timestamp and content hash. `data/` is git-ignored, and runners are ephemeral, so `data/raw/` cannot be the archive.
- Neon Free has 1 GB and a 6-hour history; it is not a backup (https://neon.com/docs/introduction/plans, accessed 2026-10-17).
- GitHub: release assets under 2 GiB each, up to 1,000 assets per release, no total size or bandwidth limit stated; repo files over 100 MiB are blocked and repos should stay under 1 GB (tooling research, G; https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases, accessed 2026-10-17).
- GitHub immutable releases (generally available 28 Oct 2025): once a release is published, its assets cannot be added, replaced or deleted and its tag is locked; the feature is enabled per repository or organisation and does not affect releases published earlier; the recommended flow is draft, attach assets, publish. Source: https://docs.github.com/en/code-security/concepts/supply-chain-security/immutable-releases and https://github.blog/changelog/2025-10-28-immutable-releases-are-now-generally-available/ (search-result summaries read 2026-10-17; primary pages not fully read). A community report that the release itself may still be deletable is [UNVERIFIED].
- Raw sizes: the OECD Key Economic Indicators dataflow alone was a 35 MB response in one call (data-sources research F5/F13). Compressed raw per monthly run is estimated at 100-300 MB (analyst estimate, unmeasured), i.e. roughly 1-4 GB/year.
- The repo is public, so raw files become public. Licences differ: Eurostat, BIS, ECB (unmodified), FAO, World Bank, EC are permissive with attribution; OECD (third-party data possible), ILOSTAT (licence text unconfirmed), FRED (third-party series need owner permission) and IMF (automated download clause) are not clearly redistributable (data-sources research F2).
- User decision of 2026-10-18: no private repository for now (design section 14a, item 5). Everything below that formerly relied on a private repository is therefore inactive (round 5).
- Defect found in the first draft: a manifest unique on `(source_id, request_key, sha256)` made a source that changes A -> B -> A unloadable, because the third fetch has the same hash as the first and was treated as "already stored". Storage deduplication and change detection must be separate concerns.
- Defect found in review (T2-2): the monthly public dump contained all curated data, including values of OECD, ILOSTAT, FRED and IMF series, bypassing the `archive` and `publish_site` gates. The dump must be partitioned by the same gates as raw archives and the site.

## Options considered
1. GitHub Releases with immutable releases enabled (one release per run), manifest rows in Neon.
2. Commit raw files to git. Binary/XML churn bloats history; 1 GB soft limit.
3. Cloudflare R2. 10 GB free, but whether a payment method is required was not verified, and object immutability is unverified; the user forbids a card on file.
4. Hugging Face dataset repo. Free public storage is "best-effort"; squash can destroy history.
5. Store bytes in Neon (`bytea`). Exhausts 1 GB quickly.
6. Hash-only (no bytes) for every source. Fails "raw data is stored"; kept only as a per-source mode for sources whose licence does not allow a public copy.
7. A second, private repository for restricted raw and a restricted dump (round 5: not available, user decision 2026-10-18; kept as a reserved extension, see "Reserved: private repository").

## Decision
Option 1, with per-source archive mode in `config/sources.yaml` (`archive: public | hash_only`; `private` is reserved and rejected by config validation while no private repository is configured; no default for sources with unclear licence; see the source-config spec rules 5 and 17), and a two-level manifest.

Archive modes (round 5):
- `public`: zstd-compressed bytes in the public repository's immutable release; full byte-level reproducibility.
- `hash_only`: no bytes are stored anywhere. The manifest keeps source URL, request parameters, `fetched_at`, HTTP validators, `sha256`, byte count, parser id (CLAUDE.md: URL, timestamp, content hash are kept). Blob `storage_backend = 'none'`. Consequences, all documented in `ref.source` and in the monthly status: (a) no byte-level reproducibility and no `rebuild` of that source; (b) no re-staging from raw: the object must be loaded from the staging rows its own fetch run wrote; if the load fails, it can be retried from those staging rows for as long as they exist (14 days, S-5); an unloaded `hash_only` object whose staging rows were swept is recorded `raw_load.outcome = 'rejected'` with `detail.reason = 'bytes_unavailable'` and the next `plan` refetches the request; (c) a hash comparison with the latest object still detects change; (d) the source's observations are in no database dump (see Recovery) and therefore have no backup beyond Neon's 6-hour history; (e) a parser bug cannot be fixed by re-parsing old raw.
- `private` (reserved, inactive): bytes in a second private repository's releases with token secret `RAW_PRIVATE_TOKEN`. It becomes available only after the user creates a private repository, sets `archive_policy.private_repo` in `config/sources.yaml`, adds the secret and approves an update of this ADR. Until then config validation rejects `archive: private`.
- Sources with `licence.redistribution_of_raw = unclear`: the rule is `archive: hash_only` unless the user records an explicit `public` decision with a rationale; `publish_site` is also an explicit user value (`withheld` is the cautious choice). The alternative is not onboarding the source. The loss of byte-level reproducibility for such sources is accepted knowingly, not by default (design Q46, confirmed by the user on 2026-10-24).

Two-level manifest (A1, A2):
- `ingest.raw_blob` (primary key `sha256`): the stored bytes, one row per distinct content, with `storage_ref` (release tag + asset name). Bytes are uploaded only when the sha256 is not yet in `raw_blob`; a revert to earlier content reuses the existing blob and uploads nothing. Review round 3: reuse is allowed only when the release named by `storage_ref` is PUBLISHED (immutable); a blob whose `storage_ref` points to a still-draft release is not durable (the draft could be lost or never published), so it is re-uploaded into the current release and the new location is recorded as a new append-only row (never an UPDATE of `storage_ref`).
- `ingest.raw_object`: the manifest of fetches that changed something. A new row is written when the sha256 of a fetch differs from that of the LATEST `raw_object` of the same `(source_id, request_key)`; it carries `fetched_at` (the future `known_at`), `prev_raw_id`, the parser id and a reference to the blob. It is unique on `(source_id, request_key, fetched_at)`, not on the hash. Unchanged fetches (same hash as the latest object, or HTTP 304) write only an `ingest.fetch_attempt`. Result for A -> B -> A: three manifest rows, two blobs; the loader loads the third object with its own new `known_at` and the observation store records a revision back to the earlier values (ADR-002).
- `ingest.raw_load` (append-only): one row per object once it is dealt with (`loaded`, `skipped_out_of_order`, `skipped_by_decision`, `rejected`). An object without a row is unloaded (view `ingest.v_raw_unloaded`) and is processed by the next loader run from stored raw, per request key in `fetched_at` order; catch-up does not refetch it (for `hash_only` objects see above). `ingest.request_state` is only a cache of validators and the latest hash and never records load status.

Release layout:
- Each run creates a draft release `raw-<YYYY-MM-DD>-r<run_id>`; fetch jobs attach assets for new blobs; `finalize` publishes (immutable). Assets are `zstd`-compressed files named `<source_id>/<sha256[:16]>-<basename>.zst`, plus `manifest.jsonl` (one JSON line per raw object: url, request params, HTTP status, ETag/Last-Modified, `fetched_at`, `sha256` of the uncompressed bytes, `blob_reused`, byte count, content type, parser id, `prev_raw_id`). Orphan drafts left by crashed runs are published by the next `finalize` (so nothing fetched is lost).
- Release limits (review round 3): (a) at most 1,000 assets per release [DOC per tooling research G]: when the current release holds 900 assets a continuation release `raw-<date>-r<run_id>-p<N>` (N = 2, 3, ...) is opened and `finalize` publishes all parts; `manifest.jsonl` lists every part. (b) `GITHUB_TOKEN` allows 1,000 REST requests/hour/repo and each asset upload is a request: blobs below a proposed 256 KB (user to confirm) are bundled into one `tar.zst` per source and run (manifest maps sha256 to bundle member), larger ones are throttled to at most 600 uploads/hour, and the request count is written to `ops.run_summary`. (c) The first run can create hundreds of blobs; its request count is a planning spike item.
- Raw assets of a source go to the public repository only when `archive = public`. A source with `redistribution_of_raw = unclear` or `forbidden` can never reach a public release by default: the config validation (source-config spec rules 5 and 15) requires an explicit user value for `unclear` and rejects `public` for `forbidden`. The same two fields (`archive`, `publish_site`) gate every public release type: raw releases, the public dump and the site. No release type has its own bypass.
- IMF WEO manual files are archived through the same path (ADR-005).

Recovery model:
- (a) Neon is rebuildable by replaying raw objects in `fetched_at` order (command `macro-monitor rebuild`). The replay is exact only under the prerequisites below (B12) and only for sources whose bytes are archived (`archive = public`).
- (b) Monthly database dump, public only (A9, T2-2). A source belongs to the partition `P-public` exactly when `archive = public` AND `publish_site = public`. Release `db-dump-public-<YYYY-MM>` (immutable) contains: `ref`; `ingest` manifest tables (URLs and hashes only; no bytes); `ops` decision tables with value-bearing columns redacted for sources outside `P-public` (`ops.drift_event.old/new`, `ops.quality_override` values, `ingest.raw_load.detail` carry values; they are exported only for `P-public` sources, and for the others only ids, kinds, timestamps and decisions); the published analytics tables (`*_published`; computed over publishable pairs only, so they carry no restricted values); and `curated` observations only through `curated.v_observation_public`, i.e. rows of `P-public` sources, including all vintages. The full internal analytics tables (`analytics.indicator_rank`, `scorecard`, `alert`, `indicator_snapshot`) are never in the public dump. Observations, vintages and revisions of sources outside `P-public` are excluded (their metadata, hashes and manifest rows remain).
- (b2) No restricted dump (round 5; inactive items removed: the `P-restricted` partition, the release `db-dump-restricted-<YYYY-MM>`, the `db-dump-full` profile and its token). Consequence, accepted by the user on 2026-10-18 and confirmed on 2026-10-24 (Q46): the observations of every source outside `P-public` have no database backup. For `archive = public` sources with `publish_site = withheld` the values can be re-derived by rebuild-from-raw (approximate for decision columns that were redacted); for `hash_only` sources there is neither a dump nor a replay. Option offered to the user (design Q46) and not taken up: include `archive = hash_only` sources whose `publish_site = public` in the public dump, because their derived numbers are already public on the site (the dump would then need rule changes in `curated.v_observation_public` and in AC-BKP-GATE).
- (c) `restore-test` workflow (quarterly) restores the latest public dump into a Postgres service container and runs the invariant suite; its checks cover `P-public` sources.
- Enabling "immutable releases" in repository settings is a prerequisite (manual, one-time) and must be done before the first release; verification is an acceptance criterion.

Acceptance test for the dump gate (AC-BKP-GATE, in addition to AC-SYS-5; revised in round 5): a fixture database has four sources covering the combinations (`public`/`public`, `public`/`withheld`, `hash_only`/`public`, `hash_only`/`withheld`), each with distinctive observation values, a revision, a drift event whose `old/new` JSON contains a distinctive value, and an alert with a distinctive z-score. After the dump job: (a) a byte search over every file of `db-dump-public` (decompressed) finds none of the distinctive values of the three non-`P-public` sources and none of their drift `old/new` values or z-scores; (b) the public dump contains the `P-public` values; (c) the dump job fails (non-zero exit, no release published) if the public output contains a row whose source is not `P-public` (self-check on the produced file, not only on the query); (d) restoring the public dump reproduces the `P-public` part of the fixture on the natural keys; (e) a source with `redistribution_of_raw = unclear` and no explicit `archive`/`publish_site` makes the config invalid, so it cannot reach any public release; (f) a source with `archive: private` while no private repository is configured makes the config invalid (source-config rule 17); (g) a `hash_only` fixture object whose load is forced to fail and whose staging rows are swept is recorded `rejected` (`bytes_unavailable`) and is refetched by the next `plan`.

Prerequisites for rebuild-from-raw (B12; the claim "replay reproduces curated exactly" holds only if all are met):
1. Parser versions: every `parser_id` ever written to `ingest.raw_object` stays importable through a registry of historical parser versions (released versions are frozen); a unit test (AC-ING-11) and the database test T-DDL-14 check that every `parser_id` in the manifest resolves. Behavioural parser changes require a new version, never an edit.
2. Decisions are inputs: `ops.drift_event` decisions, `ops.quality_override`, `ingest.raw_load` outcomes (skips and rejections) and the series succession (`ref.series` versions) are part of the dump and are read by `rebuild`; the loader's `raw_load.detail` records the comparison rule applied. Value-bearing decision columns of sources outside `P-public` are redacted in the public dump and are not recoverable (rebuild of those sources is approximate).
3. Config history is an input: whitelist (`series_map`), group revision policies and expectations come from git. Each `ingest.run` stores `git_sha`; `rebuild` checks out the config of the recorded sha for each object's run. Rebuilding with today's config would load more or fewer series than originally and is allowed only as a labelled "approximate" mode.
4. The raw archive must hold the bytes: `hash_only` sources and releases lost or deleted cannot be replayed.
5. Time is reproduced from `fetched_at` of the manifest; no clock is used by parsers.
AC-SYS-5 therefore reads: rebuild from raw into an empty database, using the recorded parser versions, the config at the recorded git shas and the restored decision tables, reproduces `curated.observation` on its natural key (for archived sources).

## Consequences
- Raw is public for `public` sources: attribution notices are generated into each release body; legal review per source is a user decision. The public dump no longer carries values of sources that may not be redistributed (A9), and the partition rule closes the earlier bypass (T2-2).
- Storage growth is bounded by content deduplication; if releases approach several GB the policy can move to targeted queries or `UpdatedAfter` windows (OECD) with periodic full refresh; this needs no schema change.
- Parser changes can be re-applied to old raw files without refetching, which allows fixing parser bugs without losing knowledge-time fidelity (`known_at` stays the original fetch time), except for `hash_only` sources.
- A failed or interrupted load never loses a change for archived sources: the object remains unloaded and is retried from stored raw. For `hash_only` sources the retry window is the staging retention (14 days), then the request is refetched and the original `known_at` is lost.
- Dependence on GitHub as sole host of raw: if the repo is lost, only the Neon copy of values remains. A second mirror (e.g. periodic copy of release assets to Hugging Face) is deliberately not added now; revisit if the data proves valuable.
- Release count grows by about 24-36 per year (raw + public dump); acceptable. With no private repository, sources outside `P-public` have no backup of their values (user decision of 2026-10-18, confirmed 2026-10-24; accepted risk R34; reopen when the first such source is enabled, Q46).
- Maintaining frozen parser versions adds code that is never deleted; accepted as the price of exact replay.
- The dump job needs a value-redaction step and a self-check on its output; this is added code, justified by the licence risk.

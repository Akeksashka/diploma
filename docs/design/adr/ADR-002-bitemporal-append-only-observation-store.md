# ADR-002: Bitemporal, append-only observation store in Neon Postgres

Revision note (review fixes): revision tolerance and re-estimation handling (A4) with a worst-case storage estimate and size guard; ordering rules for the loader (A5); projection series store every edition (C1); replay compares on the natural key (A11c); config as a replay input (B12). See the change log at the end for the 2026-10-18 fixes. Round 5 (2026-10-24): `loaded_at` and the analytics cutoffs are now defined against the load lock and the database clock; explicit-missing status `MISS`; `import` load kind; drift kinds; row-size rescaling; configuration history covers entities and sources.

## Context
- CLAUDE.md: preserve vintages; never overwrite published values; every series carries source, series id, frequency, unit, seasonal adjustment, vintage/release date.
- D10: retain every release/revision as fetched from the first run; NO backfill of historical real-time vintages; backtests on pre-launch history use latest-revised data and must be labelled so. D10 also requires a "projected" flag per observation, projections never mixed with observed values in ranks or alert windows.
- Neon Free: 1 GB per project, 100 CU-hours/month, 6 h change history only (not a backup); plain Postgres, no native bitemporal tables (https://neon.com/docs/introduction/plans, accessed 2026-10-17; tooling research G).
- Data volume, base case (analyst estimate, unmeasured): 2,000-3,500 series, about 0.5 M initial observation rows, about 20 k new rows per month (new periods + ordinary revisions); about 220-300 bytes per row including the primary key, the unique key and the `obs_raw` index (round 5: corrected from the earlier 150-200; DDL spec section 9), i.e. about 110-150 MB initially and about 60-70 MB/year.
- Worst case (analyst estimate, unmeasured): some source families recompute history by design: BIS credit-to-GDP gap (one-sided HP filter, whole history each quarter), OECD CLI (revised monthly), source-published seasonally adjusted series (re-estimated, often over many years). With exact insert-on-change every changed value is a new row. Earlier figures (OECD CLI about 227 k rows/year, BIS gap about 22 k, SA series revised over 3 years about 650 k, total about 1.1 M rows/year = about 240-330 MB/year at 220-300 bytes) assumed only 3 years of SA history are revised. If about 1,300 monthly SA series x 400 observations are re-estimated in full at each release, the result is about 520 k rows/month = about 6.2 M rows/year = about 1.7 GB/year (1.4-1.9 GB at 220-300 bytes per row), i.e. the free tier is exhausted within the first year. Detail: DDL spec section 9.
- Source re-estimation events (WGI 2.0, HICP classification and base-year change from January 2026 data, PWT 11, BIS reclassification) change meaning or units, not just values (data-sources research F4).

## Options considered
1. Append-only vintage table keyed (series, reference period, knowledge time); latest and as-of views; revisions are new rows.
2. System-versioned table with `tstzrange` validity, closing the previous row on update. Needs UPDATEs on published values (violates the convention) and is harder to make idempotent.
3. Parquet file per vintage + DuckDB catalogue. No always-on DB, but the user requires a persistent queryable store and R/Python access over one protocol.
4. Current-value table plus trigger-maintained history table. Two sources of truth; "current" is mutable.
For re-estimating groups only (added 2026-10-18):
5. Exact insert-on-change for everything: simple, but unaffordable in the worst case (above).
6. Option 1 plus, for re-estimating groups, the full vintage kept as a Parquet snapshot in the raw release and only above-tolerance changes loaded into Neon (chosen).
7. Retain only the latest vintage of re-estimating groups (overwrite): violates the preserve-vintages convention; rejected.

## Decision
Option 1, with option 6 for re-estimating groups.
- `curated.observation` is append-only. UPDATE and DELETE are revoked from every application role and blocked by trigger. Natural key of a version: `(series_id, ref_period_start, known_at)`.
- Two time axes: valid time = reference period (`ref_period_start`, `ref_period_end`); knowledge time = `known_at` = fetch timestamp of the raw object that introduced the value (always available, monotone per key, replayable). `source_release_at` holds the source's own release/update timestamp when it is exposed (nullable). `vintage_label` holds named editions (e.g. `WEO-2026-10`, `AMECO-2026-05`). `known_at` is stamped by the runner clock corrected by a measured database-clock offset (round 5; black box BB25 in the design document).
- Insert-on-change with a tolerance (A4, revised): a row is inserted only when `(value, value_status)` differs from the latest row for the key. Values are compared at the SOURCE'S PUBLISHED PRECISION: `ref.series.published_decimals` (the source's DECIMALS attribute, else the MAXIMUM number of decimals over the FULL first-load history, parsed from the source text and never from a trailing-zero-stripped JSON number; frozen once set; it may only be INCREASED by an explicit logged change that raises an `ops.drift_event` of kind `precision_change`, never silently decreased: a trigger rejects a decrease; review round 3), with a relative epsilon (default 1e-9); two values are equal if they differ by at most half a unit of the last published digit. The earlier "smaller scale of the two values" rule remains only as a fallback while `published_decimals` is unknown and is counted. `value_status` compares exactly; two rows with `value IS NULL` are equal when their statuses are equal (round 5). The rule is per series group (`ref.series_group`) and is recorded in `ingest.raw_load.detail` for each loaded object. (`published_decimals` is the derived series attribute used for comparison; the config key `published_precision` is only a display hint for the export and never enters a comparison.)
- Projection series (C1): for rows with `value_status = 'PROJ'` the comparison row is the latest row of the key with the same `vintage_label`. A new edition (for example WEO-2026-10) therefore always stores its own row even if the projected number equals the previous edition's. This is the minimal change needed now; the full forecast storage proposal is ADR-011 (proposed, gated on the unapproved forecasting amendment).
- Re-estimating groups (A4, revised): a series group declared `reestimating: true` (BIS credit gap, OECD CLI, source-SA families such as Eurostat SA) is a recorded class, not an exception to blocking only. Its revisions are labelled `revision_class = 'reestimation'`, are reported (REV-06) instead of blocked by the mass-revision rule REV-01, and are bounded by `max_revised_rows`. Groups with `snapshot_mode: diff_above_tol` (default for reestimating groups) additionally: (i) write the full parsed vintage as a Parquet snapshot into the immutable raw release (`ingest.raw_snapshot`), and (ii) load into Neon only new periods, status changes and revisions whose size exceeds the tolerance `max(materiality_abs, materiality_rel * |stored value|)` (round 4: the floor is half a published unit, the comparison rule; for ratio-dimension units such as rates and % of GDP only `materiality_abs` applies, because a full-unit floor would drop typical 0.1 pp revisions of one-decimal rates), compared with the LATEST STORED value so sub-tolerance drift accumulates and is stored once it crosses the tolerance. REV checks use a materiality rule that is the same half-unit rule as the loader (round 5): only changes beyond the group's comparison rule and materiality count as revised keys for REV-01, so a regular group where 90 % of keys move by rounding noise is not blocked. Changes of unit, base period, SA flag or classification metadata are never "expected re-estimation": they go through the drift/succession path below.
- Honest trade-off of option 6: Neon no longer contains every re-estimated vintage of those series. `fn_observation_asof` returns the last stored value, which can differ from the value the source published at that time by up to the tolerance (the difference is bounded, not zero). Exact vintage reconstruction requires the Parquet snapshots (outside the database). Revision statistics for those groups understate small revisions and are labelled so; groups with `reestimating: false` keep exact history. Tolerance defaults (relative 0.001; absolute floor half a published unit, the comparison rule) are proposed, to be set from the AC-OPS-8 measurement on the first three real releases.
- `load_kind` is one of `initial` (first ever fetch of the series: history is latest-revised, not real-time), `new_period`, `revision`, `tombstone` (source dropped a value in a complete full-history fetch; never from partial or incremental fetches), and, round 5 (P22, confirmed by the user on 2026-10-24, design Q47), `import` (rows of a manual object labelled `import_label: archive_import`, an older edition loaded after a newer one; stored and labelled, never "latest", never used for ranks, alerts, exports or real-time claims; see the manual-edition rule in ADR-005). Backtests must filter on `load_kind` and `known_at` and label `initial` rows as revised-data.
- `value_status`: `OBS`, `EST`, `PROV`, `PROJ`, `DEL`, `MISS` (round 5). `DEL` is our tombstone (the source dropped a value in a complete fetch). `MISS` is a value the source itself publishes as missing, confidential or not available (marker such as `:`, `..`, `c`, `NA` declared per parser), stored with `value NULL` and the marker in `source_flags`; it is data (a revision value to MISS or from MISS is a status change and is stored), it is returned by the latest and as-of views as NA, and it is never ranked, alerted or used as a window value. `is_projection` is a generated column (`value_status = 'PROJ'`). Analytics exclude `PROJ` from ranks and alert windows.
- Series measurement attributes (frequency, unit, unit multiplier, base period, price basis, currency basis, seasonal adjustment, calendar basis, flow basis) are immutable per `ref.series` row. If the source changes any of them (rebase, new classification, new SA treatment), the loader does not rewrite history: it creates a new `ref.series` row (`version + 1`, `supersedes_series_id`), records an `ops.drift_event` (kinds are listed in the DDL spec section 7: `unit`, `base_period`, `seasonal_adjustment`, `frequency`, `flow_basis`, `classification`, `composition`, `dataset_moved`, `mass_revision`, `schema_drift`, `precision_change`), and the mapping to indicators is switched only by an explicit, reviewed config change (ADR-009). A change of euro-area membership of a `CHANGING` series is a `composition` event. Quality overrides never edit curated rows; they go to `ops.quality_override`.
- Ordering (A5, restated): per key, `known_at` is strictly increasing in insertion order. The loader processes unloaded raw objects of one `(source_id, group_id)` strictly in `(fetched_at, raw_id)` order, holds a successor while a predecessor is unloaded, and, per series (round 4; was per object), records `raw_series_status = skipped_out_of_order` for each series that already has rows with a later `known_at` (cross-group or manual-inbox interleaving) while the other series of the object load; the object is `skipped_out_of_order` as a whole only if every series is skipped. Replay honours the recorded outcomes. Detail: `docs/specs/ingestion-interfaces-spec.md` section 5 and I-CUR-4.
- Transaction time (review round 3, corrected in round 5): `curated.observation` also carries `loaded_at timestamptz NOT NULL`, never updated. Reason: `known_at` is the fetch time, but an object fetched before a cutoff can be loaded after it (held-back successors, `decide` reloads that keep the original `known_at`, the day-4 catch-up), so `known_at <= cutoff` alone returns more rows when re-run later than the run originally saw. Round 5 correction: the earlier definition `loaded_at = transaction_timestamp()` is the START of the load transaction, which is taken before the advisory lock is acquired. A load that started before an analytics cutoff and committed after it then had `loaded_at <= load_cutoff` although the analytics run could not see its rows, and the later reproduction would include them. New rule: `loaded_at = clock_timestamp()` read once AFTER the loader holds `pg_advisory_xact_lock(hashtext('mm-load'))` and used for every row of that load (and for its `raw_load` row); the lock is held until the commit, so the value lies between lock acquisition and commit. The analytics run takes its cutoffs from the DATABASE clock, not the runner clock: in one short transaction it takes the same lock (waiting for any in-flight load to commit) and reads `known_cutoff = load_cutoff = clock_timestamp()`. Consequence: every load that committed before the cutoff has `loaded_at <= load_cutoff` (it read its clock while holding the lock, before the analytics run got the lock) and every load that commits later has `loaded_at > load_cutoff` (it acquired the lock after the analytics run released it). Test AC-ING-15.
- Latest and as-of access: views `curated.v_observation_latest` and function `curated.fn_observation_asof(known_cutoff, load_cutoff DEFAULT NULL)`: latest row per key with `known_at <= known_cutoff` AND, when `load_cutoff` is given, `loaded_at <= load_cutoff`, excluding tombstones (`DEL`) and rows with `load_kind = 'import'`; `MISS` rows are returned (value NULL). Recomputing with only `known_cutoff` answers "what would we know now about then" and is labelled so; the pair `(known_cutoff, load_cutoff)` reproduces what a past run actually saw.
- Reproducibility of analytics (2026-10-18, revised in review rounds 3 and 5): observations are reproducible on the live database through `known_at <= known_cutoff AND loaded_at <= load_cutoff` (both stored in `analytics.run`, both read from the database clock under the load lock). On a rebuilt database `loaded_at` is not replayed exactly, so only `known_cutoff` results are reproducible there. Configuration is reproducible only if its history is kept, so configuration tables that change results (`ref.series_map`, `ref.indicator` incl. parameters, targets, inputs, domains, series groups, global translation, and, round 5, `ref.domain`, `ref.entity` and `ref.source` with `publish_site` and `archive_mode`) are mirrored into the append-only `ref.config_history` (valid time stays in `valid_from`/`valid_to`; recorded time is `recorded_at`), and `ops.quality_override` and `ops.drift_decision` are insert-only with `recorded_at`. `analytics.run` stores `config_asof`, `config_sha256` (also inside `params`), `mapping_sha256` and `overrides_sha256`, so a run for an earlier `known_cutoff` is recomputed from the data as known then and the configuration as recorded then, and a mismatch of the hashes is detected rather than silently accepted.
- Migrations: forward-only plain SQL files applied by a small runner, version recorded in `ops.schema_migration`, applied only by the `migrate` workflow under an owner role (ADR-008).

## Consequences
- Idempotency is a property of the loader: re-loading the same raw object inserts zero rows (a `raw_load` row exists, and insert-on-change finds no difference).
- Rebuild from raw (what it honestly requires). Replaying all raw objects in `(fetched_at, raw_id)` order into an empty database reproduces `curated.observation` on its natural key only if ALL of these hold: (1) the raw assets and manifest are intact (ADR-003; not possible for `hash_only` sources, which store no bytes); (2) every `parser_id` used remains importable, i.e. released parser versions are never edited or deleted (registry test AC-ING-11) and their third-party dependencies stay installable (pinned lockfile history; a parser that cannot run any more means that object cannot be replayed and the gap must be documented); (3) the configuration at load time is available: `ref.config_history` plus the git history of `config/` at each `ingest.run.git_sha` (series groups' comparison rules and tolerances, series_map, published_decimals); (4) the recorded load outcomes in `ingest.raw_load` and `raw_series_status` are replayed as recorded (skipped and rejected objects stay skipped), which needs the ingest tables, not only raw bytes; (5) human decisions (drift accept/reject, `skipped_by_decision`, quality overrides) are kept in `ops.drift_decision`/`ops.quality_override`/`raw_load`, because they cannot be re-derived from bytes; (6) for snapshot groups, the same tolerance and the same order produce the same above-tolerance set (deterministic by construction, tested by I-CUR-7); (7) Neon-side ids (`series_id`, `obs_id`, `raw_id`) and `loaded_at` are regenerated and are not compared. Anything lost among (2)-(5) turns "rebuild" into "best-effort rebuild" and must be reported by `rebuild` as such. Without the `ingest` and `ops` tables (for example only raw assets survive), values can be re-derived with the current parser and config, but `known_at` of each object is still known from the manifest while human decisions and outcomes are not.
- The first load of every series is flagged `initial`; real-time revision statistics start only from the first update, which is accepted under D10.
- Disk grows by revisions only; no per-run copy of unchanged values. For re-estimating groups the growth is bounded by the tolerance, not by the number of keys: unmeasured planning figure about 80-250 MB/year in the SA worst case if 5-15 % of keys cross the tolerance (about 0.3-0.9 M rows/year at 220-300 bytes; DDL spec section 9), versus about 1.7 GB/year without it. A size monitor alerts at 70 % of the 1 GB limit and also on a 12-month linear projection reaching 900 MB (DB-02); a per-object insert cap (DB-05) and the `max_revised_rows` cap bound a single bad load. Further options if the measurement disagrees: disable ext/opt re-estimating families (M05 OECD CLI is `ext`), or a retention ADR. Open question Q18 for the user.
- Series succession adds modelling work when sources re-estimate, but avoids silently mixing units or bases.
- A deleted-then-restored source value yields tombstone then a new row; both are retained.
- A source that reverts to earlier bytes (A -> B -> A) yields a third manifest object and a revision back to the earlier value with a new `known_at`; nothing is overwritten (ADR-003); only the bytes are deduplicated.
- The analytics step now waits briefly for an in-flight load (seconds to minutes) before reading its cutoffs; if the load lock cannot be taken within `lock_timeout` the analysis run fails rather than reading unreproducible cutoffs.
- Detail: `docs/specs/ddl-neon-schema.md`, `docs/specs/ingestion-interfaces-spec.md` (loader algorithm).

# ADR-011: Forecast and projection storage (proposal, gated on the forecasting amendment)

Access date for facts: 2026-10-18. This ADR does not change the current design except for the one small rule recorded in ADR-002 (projection series store every edition). Everything else here is a proposal to be implemented only after the user approves the amendment and a design round for it.

## Context
- `docs/research/indicator-selection-g20-eu-forecasting-amendment.md` is a DRAFT (front matter `status: draft`) that records user decisions FD1-FD11 of 2026-10-17 but is not approved as a whole. Under the project's phase gates it is therefore not a design input. The current design (`docs/design/macro-monitor-platform-design.md`) covers monitoring, scorecards, alerts and a dashboard of observed data; it lists forecasting and nowcasting as a non-goal.
- What the amendment adds that the design does not cover (gap list): (1) forecast and nowcast outputs per target (FT01-FT12) with horizons (h = 0 nowcast, 1-4 quarters, 1-12 months, current and next year); (2) official benchmark forecasts as vintages (B01-B10: IMF WEO April/October only, OECD EO, EC, ECB/Eurosystem projections, ECB SPF, central banks) with edition dates; (3) forecast evaluation against the first release and a mature vintage (FD5) with the metric list (bias, MAE, RMSE, relative RMSE, Diebold-Mariano, hit rate, Brier score, calibration; FD10), with and without 2020-2021; (4) probability targets and probability alerts (FT11 recession probability, FT12 inflation above band, FD8) with calibration display and event counts; thresholds to be set in design; (5) a model layer (nowcast news, derived series N03, N11, N12, N13, forecast errors) and the model-depth tiers F-A, F-B, F-C (FD3); (6) a one-off import of official benchmark forecast archives (FD6) as a named exception to D10; (7) release calendars and first-release timestamps per series (N15); (8) pages for forecasts and track records in the dashboard.
- What exists now: `curated.observation` stores values by `(series, reference period, known_at)` with insert-on-change; `value_status = 'PROJ'` marks projections (WEO A03 would be loaded with `vintage_label` per edition), which are excluded from ranks, alerts and the v1 dashboard. Problems for forecasting: (a) insert-on-change drops a projection value of a later edition when the number is unchanged, losing the fact that the edition re-published it; (b) a forecast has an origin (information date), a horizon and a target period, which the observation key does not express; (c) own-model forecasts are not source data and have no raw object; (d) evaluation needs the first release and a mature vintage of the realised value, which must be derivable from `known_at`; (e) imported benchmark archives are not our own vintages and must be labelled.

## Options considered
1. Keep forecasts in `curated.observation` with `value_status = 'PROJ'` and extra columns (origin, horizon). Mixes two different keys in one table; every consumer must filter; own-model output has no raw object, violating `raw_id NOT NULL`.
2. A separate `forecast` schema with its own append-only tables (edition-based, insert always per edition) next to `curated`; evaluation as views joining to `curated` vintages.
3. Store forecasts only in `analytics_r` (R outputs). No provenance contract for benchmark editions; ties benchmarks to an optional language layer.
4. Do nothing until the amendment is approved. The only change now is the edition rule for PROJ rows already in ADR-002.

## Decision (proposed; gated)
Option 4 now, Option 2 on approval of the amendment. The proposal for Option 2:
- Edition-based storage, not insert-on-change: `forecast.edition` (`edition_id`, `producer` such as `IMF_WEO`, `OECD_EO`, `EC`, `ECB_BMPE`, `ECB_SPF`, `SYSTEM_MODEL`, `edition_label` such as `WEO-2026-10`, `published_at`, `forecast_origin` = information date, `known_at` = our fetch time or run time, `raw_id` NULL for system models, `imported boolean`, `import_label`, `definition_note` for average versus end-period inflation, fiscal year, etc.). `forecast.projection` (`edition_id`, `series_id` of the target series or a target id, `target_period_start/end`, `horizon_code`, `value_kind` in `point | quantile | probability`, `value`, unit attributes by reference to `ref.series`). Primary key `(edition_id, target, target period, value_kind, quantile)`. Every edition stores every value it publishes even if unchanged from the previous edition (the opposite of ADR-002 insert-on-change), because the pair (edition, target period) is the unit of evidence. Append-only, same privilege rules as `curated.observation`.
- Interim rule in force now (ADR-002, I-CUR-3): for `PROJ` rows in `curated.observation`, the comparison row is the latest row of the key with the same `vintage_label`, so WEO editions with unchanged numbers still store a row. If ADR-011 is approved, WEO projections move to `forecast.*` and the interim rule is retired.
- Latest-edition determination and edition order (round 5 note, P22 in ADR-005, confirmed by the user on 2026-10-24). Which WEO edition is "the latest" (for the A02 estimate boundary and for ordering) is read from `ingest.raw_object.edition_label`/`edition_date` of the latest LOADED manual object of the group, never from `vintage_label` of observation rows: only `PROJ` rows are re-inserted for every edition, whereas `EST`/`OBS` rows unchanged across editions keep the older label. A manual object whose `edition_date` is older than the latest loaded edition is refused unless its sidecar sets `import_label: archive_import`; such objects are stored in `curated.observation` with `load_kind = 'import'` (never latest, excluded from real-time claims). The same label is `forecast.edition.import_label` / `imported = true` here, so an approved ADR-011 moves WEO archive imports into `forecast.*` and retires `load_kind = 'import'`.
- Evaluation: `forecast.evaluation` per `(edition, target, horizon)` and realisation vintage in {`first_stored_release`, `mature`} (review round 3, finding 6: the label `first_release` is NOT used for the stored marker, see the vintage-resolution limit below). The `first_stored_release` marker is derivable from `curated.observation`: the earliest stored version of a key whose `load_kind` is `new_period` (the first version of that period our pipeline stored after launch); keys loaded as `initial` have no first stored release (they are revised data, labelled "pseudo-real-time on revised data" for backtests, FD5). The `mature` vintage is the latest version with `known_at` at least the configured maturity after `ref_period_end` (about 4 quarters for monthly/quarterly, the following spring for annual; FD5 definition). Both are views (`curated.v_first_stored_release`, `curated.fn_mature_vintage`; the earlier name `v_first_release` is retired) so no new marker column is needed; the release lag per series (N15) comes from `known_at - ref_period_end` and source calendars.
- Vintage-resolution limit (design limitation, review round 3). Fetch-time quantisation: the pipeline fetches on a schedule (monthly day-1 runs for most sources), so the first stored version of a key is the version current at the first fetch after publication. If the source revised the value before that fetch, the first stored version is a later estimate (a second or third print), not the true first print, and revisions inside one fetch interval are invisible. Consequences: (a) every evaluation output states `actual_vintage = 'first_stored_release'` and never "first release" unqualified; (b) each series carries `release_cadence_note` / `vintage_resolution` (for example `monthly_fetch`, `daily_fetch`, `source_vintages`, `archive_import`) in `ref.series` metadata or `meta/indicators.json`, set from the source's fetch cadence and, where applicable, its release frequency (a series released weekly and fetched monthly has coarser resolution than one released monthly); (c) FD5 evaluations that claim to use the TRUE first print must take actuals from benchmark archives (FD6 imports) or from source-provided vintages where they exist (ALFRED real-time vintages for US series; OECD Main Economic Indicators original-release data [UNVERIFIED availability and coverage; research R4]), labelled `actual_vintage = 'source_vintage'` or `'archive_import'`; (d) the monthly cadence limit is recorded as a design limitation, with a mitigation option (raising the fetch cadence for series used in evaluation to release-day runs) left to the design round of the forecast layer. The dashboard view V4 (vintage view) states the resolution in text (dashboard-export-spec).
- Imported benchmark archives (FD6): rows carry `imported = true`, `import_label = 'archive_import'`, `published_at` = original edition date, `known_at` = import time; they are never counted as the system's own vintages (D10 stays true for observation data) and are excluded from any claim about the pipeline's real-time record.
- Probability alerts: FT11 and FT12 probabilities are `value_kind = 'probability'` rows of a system edition; alert thresholds are config set in the design round (FD8); calibration data (forecast probability bins versus outcomes and event counts) come from `forecast.evaluation`.
- Model layer: own-model editions are written by R modules into `forecast.*` through a dedicated role (not `mm_r` writing curated); derived inputs (N03 yield-curve slope, N11 slack gap, N12 real rates) are transforms in analytics or first-class derived series, decided in the design round.
- Dashboard: forecast and track-record pages need a new export contract version (major bump) and published-set rules for forecasts (the licence gate of ADR-010 applies to benchmark editions).

## Consequences
- Nothing is implemented from this ADR. It prevents an avoidable data-model mistake: loading WEO editions with insert-on-change and later discovering that edition-level comparison is impossible. The interim edition rule costs a few rows per edition.
- Storage: editions x targets x horizons is small (WEO twice a year for about 42 countries x 6-10 variables x 2-6 years is under 10 k rows per edition [analyst estimate]), but own-model fan-outs (monthly, 12 horizons, 12 targets, 44 entities, quantiles) are about 50-250 k rows per run [analyst estimate] and would need a size guard like DB-02; to be sized in the design round.
- Research follow-ups required before design (from the amendment, not done): R1 (access and licences of N01-N15 and B01-B10), R2 (coverage matrix, tier membership), R3 (release calendars), R4 (first-release vintages availability; now also the source-provided vintage question above), R7 (inflation target metadata), R8, R9 (benchmark archives). The same target metadata overlaps with the target-deviation ranking in the analytics spec (B2).
- Evaluation against the true first print is limited to series with source vintages or imported archives; elsewhere the evidence is `first_stored_release`, which understates revision size (bias toward smaller measured revisions and forecast errors against an already-revised actual).
- Open questions for the user are recorded in the design doc section 14 (Q26): approve or amend the forecasting amendment; whether v1 shows projections.
- Reversal: because the store is separate, dropping forecasting later removes the `forecast` schema without touching `curated`.

# ADR-028: Bulk-file sources whose file URL changes are resolved by landing-page discovery under a fail-closed assertion, with a manual-inbox fallback (amends the `bulk` request template of the source-config schema; refines ADR-004 and ADR-013 for `kind: bulk`)

Date: 2026-11-05 (Phase 2). Repository facts were read from files on 2026-11-05 (code read, not executed). External facts come from live page fetches on 2026-11-05 made through a summarising fetch tool (the tool's model extracted the quoted text, so each is "observed once, not independently verified" and is marked [OBSERVED-ONCE]); anything else external is [UNVERIFIED].

## Context
- Repository facts (T58, `docs/plans/macro-monitor-v1-implementation-plan.md` T58 note, "Left / open" item 4; `config/sources.yaml`):
  - `worldbank_pinksheet`, group `pinksheet_monthly`: `request_template.path` is `en/doc/PROBE_REQUIRED_HASH/related/{dataset}.xlsx` under `base_url: https://thedocs.worldbank.org/`. The hash segment is a placeholder.
  - `fao`, group `fao_csdb`: `path: worldfoodsituation/csdb/{dataset}.xlsx`, `datasets: [csdb-data-2026-10]`, a placeholder month "advanced by hand until a design decision on a stable URL".
  - Both sources are `enabled: false`; all URLs are [UNVERIFIED] in the repository.
- How `BulkConnector.plan` works today (`src/macro_monitor/ingestion/connectors/bulk.py`): a pure function; one `RequestSpec` per `request_template.datasets` entry, `url = base + path.format(dataset=...)`, `request_key = request_key("GET", url, {})`. `fetch` sends validators stored under that `request_key` and sets `update_marker` from `Last-Modified` only (XLSX).
- Why a changing URL is more than a config nuisance. `ingest.request_state` and `ingest.raw_object` key everything on `request_key`, "canonical hash of method + URL + sorted params + body" (`docs/specs/ddl-neon-schema.md`, `ingest.request_state`, `ingest.raw_object`). `prev_raw_id` is "the latest object of this request_key" (invariant I-ING-3), the change ladder reads validators per `request_key`, and `raw_object_latest` is indexed on it. If the URL is part of the key, each rotation starts a new chain: no `prev_raw_id`, no validators, and the loader's per-request-key `last_loaded_sha256` has no predecessor. This must be designed, not left to happen.

## Options considered
1. Status quo: hand-edit the hash or month in `sources.yaml` before each release.
   - Pro: no code. Con: a monthly human step on two sources that are otherwise automatic; a stale value makes the connector fetch an old file or a 404 and nothing in the config says which; the placeholder path for FAO is already wrong; a silent re-fetch of an old URL looks like "no change", so freshness (ADR-020) becomes the only detector. Rejected as the standing answer. (It stays available to the operator for any single run via the manual fallback below.)
2. Date token in `request_template` (for example `{dataset}` built as `csdb-data-{yyyy}-{mm}`), the connector computing the name from the run date.
   - Pro: no discovery request, `plan` stays pure and offline, keeps one request per file. Con: cannot work for the Pink Sheet at all (the hash segment is not derivable from a date); for FAO it must guess the month (current month, falling back to the previous one on 404, since releases fall on varying days, for example 6 November, and the month in the name may not equal the release month [UNVERIFIED]), still has to hard-code a directory path that is already wrong in the repository and may move, and does not know about the `sfvrsn` query. A guessed name proves nothing about being the newest file; a 404 probe doubles requests to the host. Rejected as the single mechanism. It could serve FAO alone but would leave two mechanisms for two sources in one connector.
3. Landing-page discovery: the connector fetches a configured landing page, extracts the link to the file with a strict pattern, asserts that exactly one link matches, and fetches the file at the resolved URL.
   - Pro: one mechanism for both cases; follows what the publisher itself links, so a hash or `sfvrsn` rotation costs nothing; the assertion (exactly one match, host and extension allow-list, expected file name) fails closed; the resolved URL is recorded for provenance. Con: one extra request per run per group; `plan` can no longer know the file URL (resolution moves into `fetch`); a page redesign breaks the pattern (handled by the fail-closed path and the fallback); a new page-parsing surface (small: `lxml` is already approved for ADR-005 web parsing [from ADR-005; confirm it is a declared dependency]) and a cross-host request for the Pink Sheet (landing on `www.worldbank.org`, file on `thedocs.worldbank.org`).
4. Manual-inbox fallback only (ADR-005): a human downloads the file monthly.
   - Pro: no automated access question, no URL guessing. Con: a monthly human step for ten to twelve releases a year per source, which is the exact burden the project wanted to avoid for files that an automated route can serve; the reminder mechanism (rule 11) is built for twice-a-year WEO, not monthly; `manual` sources are a different kind, so the same group cannot switch route without a second source entry (see Decision 9). Rejected as the primary route, kept as the fallback.

## Decision
Option 3 as the primary route for `kind: bulk` groups that declare it, Option 4 as the documented fallback, Options 1 and 2 rejected.

1. Config shape. A `kind: bulk` group may replace `request_template.path`/`datasets` addressing by a `discover` block inside `request_template`:
   ```yaml
   request_template:
     discover:
       landing_url: https://www.worldbank.org/en/research/commodity-markets
       link_pattern: '^https://thedocs\.worldbank\.org/en/doc/[0-9a-f]{32}-[0-9]+/related/CMO-Historical-Data-Monthly\.xlsx$'
       expect_matches: 1            # exactly one distinct URL, else fail closed
       allowed_hosts: [www.worldbank.org, thedocs.worldbank.org]
     datasets: [CMO-Historical-Data-Monthly]   # the logical file name; also the series_map dataset key
   ```
   For FAO: `landing_url: https://www.fao.org/worldfoodsituation/csdb/en/`, `link_pattern` anchored on `https://www.fao.org/media/docs/worldfoodsituationlibraries/wfs-library/csdb-data-\d{4}-\d{2}\.xlsx(\?sfvrsn=[A-Za-z0-9_]+)?$`, `datasets: [csdb]`. The `{dataset}` placeholder and `path` are not used with `discover`; a group has either `path` or `discover`, not both. The patterns above are drawn from the single observation above and are [UNVERIFIED] until an operator probe.
2. The logical dataset, not the URL, identifies the request. For a discovered group the `RequestSpec` that `plan` returns is a pure function of config: `url` = `landing_url`, plus a marker `discover` in `params`-free form (a `RequestSpec.resolve` field carrying `link_pattern`, `expect_matches`, `allowed_hosts`), and `request_key = sha256(GET, landing_url, dataset)`. Rotation of the file URL therefore does not start a new chain: `prev_raw_id`, `request_state` and invariant I-ING-3 keep their meaning with the logical key. `plan` stays pure and offline (ADR-013 is unchanged).
3. Resolution happens inside `fetch`, with the injected `HttpClient` (ADR-013 holds: connectors do not build clients). Steps: (a) `RobotsGate` and rate limit apply to the landing request as to any request of this source; (b) GET landing page (no validators needed, it is small; it is not archived as a raw object); (c) extract `<a href>` values with `lxml`, resolve them against the page URL, normalise, de-duplicate; (d) keep only those matching `link_pattern`; (e) require exactly `expect_matches` distinct matches, else raise a classified failure (`discovery_failed`, see failure modes); (f) require scheme `https`, host in `allowed_hosts`, and the response after redirects to remain in `allowed_hosts`; (g) GET the resolved URL through the same `HttpClient`, so the file host gets its own per-host throttle (ADR-004); (h) conditional request validators from `request_state` are sent only when the resolved URL equals `request_state.last_url`; otherwise unconditional. The bytes returned are untouched.
4. Manifest provenance, no DDL change. `ingest.raw_object.request_url` already means "full URL as sent" (DDL); for a discovered group it holds the RESOLVED FILE URL. `request_params` (jsonb NOT NULL) gains a `discovery` object: `{"landing_url", "landing_status", "landing_sha256", "link_pattern_id" (sha256 of the pattern), "matched_href" (as found, before normalisation), "resolved_url", "resolved_at"}`. `request_state.last_url` records the last resolved URL. `request_key` stays the logical key (Decision 2). The ingestion-spec section on the manifest and its example row (line 96 of `docs/specs/ingestion-interfaces-spec.md`) are amended to say so. No migration: `request_params` is existing jsonb. Because the hash and the version query are part of `request_url`, a changed URL with identical bytes is not a new raw object (the ladder stops at the content hash, A1), and a changed URL with new bytes is a normal new object in the same chain.
5. Fail-closed assertion. Zero matches, more than `expect_matches`, a match outside the host allow-list, a landing response that is not HTML 200, a redirect off the allow-list, a resolved file that is not the expected format (`is_xlsx` for xlsx; the frozen parser's own layout assertions remain the second wall, `PARSE-01`), all stop that group's fetch with no partial store. Classification `discovery_failed` is recorded in `ingest.run` detail and handled like ADR-005's `blocked`: one alert per source per month, the group is skipped, other groups continue. A bot challenge on the landing or the file is `blocked` exactly as in ADR-005; no challenge solvers, proxies or headless browsers are added.
6. No guessing fallback. When discovery fails the connector never falls back to the last known URL or to a date-token URL. A fetch of a remembered URL would look like "unchanged" and hide staleness.
7. Staleness is still detected by the release calendar (ADR-020): a source that discovers the same old file for a month yields no change and the freshness state goes `late` then `stale`. For FAO, `freshness` may be tightened to the published release dates once confirmed (see open question 4).
8. robots.txt and terms.
   - Both sources are `kind: bulk` (documented/published bulk file, not `web`), so `RobotsGate` runs in log-only mode on every request including the landing request, and the Disallow-escalation rule of ADR-004/ADR-005 applies (the agent never sets `robots_override_reason`). On the observed robots files (see Context) neither the landing pages nor the file paths are disallowed [OBSERVED-ONCE]. FAO's `/*?id=*` rule does not match `?sfvrsn=` (pattern-matching inference, to be confirmed by the gate's own evaluation in the first probe).
   - Reading an HTML landing page is a lightweight form of the page access that ADR-005 regulates. This ADR treats it as part of a published-bulk-file fetch, not as a `web` source, because it extracts one link, makes one request per run, and no content from the page is stored or published; a change to extract page content would be a `web` source with a terms review. The user must confirm this reading (open question 1).
   - `terms_review` is recommended for `bulk` (schema section 1); this ADR asks that the two sources get one recorded before enabling: the Pink Sheet terms conflict is already in the config (`redistribution_of_raw: unclear`, `archive: hash_only`), so enabling is gated on the user's licence decision, unchanged by this ADR.
   - Politeness: the landing request adds one request to the 1-per-5-s source budget (so two requests per group per run); no extra retries beyond the source's `http.retries`.
9. Manual fallback (ADR-005) for these groups. `ingest-manual` refuses a source whose `kind` is not `manual` (`cli.py` line 597), and a manual source may not carry `base_url`/`rate_limit`/`http`/`change_detection` (rule 4). The fallback is therefore a separate `kind: manual` source entry per file, for example `worldbank_pinksheet_manual` and `fao_manual`, with one group each whose `parser` is the SAME frozen parser as the automated group (same file layout), sidecars `edition_label` (for example `PINKSHEET-2026-11`) and `edition_date`. Both entries stay in `sources.yaml`; the manual entry is `enabled: true` with no reminders, used only by an operator when a `discovery_failed` alert fires. Series ids are stored under the series keys of the group that owns the `series_map`; whether two groups may feed one series (same `(source_id, group_id)`-keyed `ref.series` rows are not shared across source ids) is open question 2, and until resolved the manual fallback loads under its own source id and its rows are not merged with the automated ones (an inference from ADR-018, to be confirmed). The hand-downloaded file does not need `discover`.
10. Scope. The mechanism is available to any `bulk` group, but only the two groups named in the Context use it in this ADR. No other source is changed. Where a bulk URL is stable (BIS, FAOSTAT FFPI path) `path` stays.

## Consequences
- Pro: the two T58 placeholders are replaced by one reviewed mechanism; no monthly hand edit; the config holds a pattern, which is easier to review than a hash.
- Pro: chain continuity (`request_key`) survives URL rotation, so `prev_raw_id`, validators and revision tracking behave as for every other source.
- Pro: provenance is complete (landing URL, matched href, resolved URL, landing page hash) with no DDL change.
- Pro: fail-closed by construction; the existing parser layout assertions remain a second line of defence.
- Con: `plan` no longer lists the final URL; `plan` output and dry runs show the landing URL, and the resolved URL appears only after `fetch`. Documented in the spec and the CLI help.
- Con: one extra request per run per group, and a cross-host sequence for the Pink Sheet (two throttles). The "one host per source" rule is about the `base_url`; this ADR adds `allowed_hosts` to name the extra hosts explicitly.
- Con: a landing-page redesign breaks discovery until the pattern is updated. Accepted: it is detected (zero match), alerted, and the manual route covers the gap.
- Con: the cereal brief remains a single-copy vintage; if one monthly run is missed and FAO replaces the file before the next successful run, that month's vintage is lost. This is a pre-existing risk of the source (config comment), not a new one; the freshness alert is the only mitigation, and a missed month cannot be recovered from the page.
- Risk: the `sfvrsn` version query may be required or may be volatile per request [UNVERIFIED]; the pattern keeps it as published. If it changes without the bytes changing, the content-hash rung treats the object as unchanged.
- Risk: a link-extraction pattern that is too loose could resolve an attacker-controlled or wrong file; the allow-list, the anchored pattern, `expect_matches: 1` and the format check bound this.
- Reversal: remove the `discover` block and return to `path` in a config change; `request_key` of discovered groups differs from the earlier URL-keyed one, so a reversal starts a new chain (documented in the migration note below).

## Migration and backfill impact
- No data migration and no DDL. Both sources are disabled and have no stored raw objects [inference from the T58 note, "all five stay disabled"; not checked against the database], so no `request_key` chain exists to break. If a probe object had been stored under the old URL-keyed key, enabling the new mechanism starts a new chain for that group; the old objects stay immutable and loadable.
- Backfill: none possible for FAO (the page keeps only the newest file; older files are not linked [OBSERVED-ONCE]); our archive from the first successful fetch onward is the vintage history. Older Pink Sheet history is inside the current workbook (full history file), so a first fetch covers it.
- Rollout order: this ADR approved by the user; spec and schema amendments approved; code and tests implemented; operator probe (network marker); the user's licence decision for the Pink Sheet; only then `enabled: true`.

## Open questions for the user
1. Do you accept that fetching one HTML landing page per run to extract a file link belongs to a `bulk` source (robots gate in log-only mode, no `terms_review.decision: permitted` gate as for `web`), or should such groups require the full `web` gate of ADR-005 (terms and robots review per site, which would turn on the 12-month review rule and `enabled` forcing)?
2. Manual fallback shape (Decision 9): a separate `kind: manual` source per file loading under its own source id, versus allowing `ingest-manual` to target a `bulk` group (a change to ADR-005/rule 4 and `cli.py`). Should the manual rows be allowed to feed the same series as the automated group, and how are they ranked against the automated ones (ADR-009 authoritative source)?
3. Is a cross-host `allowed_hosts` list under one source acceptable (Pink Sheet: landing on `www.worldbank.org`, file on `thedocs.worldbank.org`), or should the landing host be modelled as a second source entry despite ADR-004's one `HttpClient` per host?
4. FAO states its release dates on the page (6 November, 4 December, and so on). Should `fao_csdb` freshness be driven from those dates in `release_calendar.yaml` (a monthly manual config update) or stay on `typical_lag_days`?
5. The Pink Sheet link label read "October 2026" on 2026-11-05 although the research notes a release on 3 November [OBSERVED-ONCE; the cause is [UNVERIFIED]: page lag, label meaning the data month, or tool error]. Please confirm at the first operator probe which month the file contains before the freshness numbers are set.
6. Do you want the agent-visible rule "never fall back to the last known URL" (Decision 6) written into the spec as a testable invariant? It is proposed here as such.

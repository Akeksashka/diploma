## Context
- User problem statement (2026-11-06, stated in session): the dashboard is hard for an analyst to understand: too many series on one chart, unclear naming, units not shown, n/a everywhere, no hover values, scorecards are tables without charts, no way to pick one country and see all its data, no way to compare one indicator across countries.
- Current pages [REPO: `docs/design/briefs/dashboard-ux-brief.md` section 1]: `index` (domain list, caveat, status block), `domain/<id>` (V1 heatmap), `peers/<id>` (V2 peer comparison within one domain), `explorer` (V3), `revisions` (V4), `status` (V5). The domain is the organising unit: to see one country the user must open each domain page and find the row; to compare one indicator the user must know its domain and open `peers/<domain>`. There is no country page and no indicator page.
- Data reality [REPO: `docs/ops/dashboard-ux-baseline.md`, "(e) Real export density"]: the current real export is Eurostat-only; 3 of 42 countries have a percentile, in one domain (labour, M09); all other domain scorecards are empty. "n/a everywhere" is therefore partly a data-coverage fact, not only a design fault. The redesign cannot create values; it can only say precisely why a value is absent and stop empty rows from hiding the rows that have data.
- Hard constraints that bound the design (all approved, all respected; see "Constraints respected"): static site on GitHub Pages and a read-only export (ADR-010 decisions 1, 2, 5); no off-origin request and no Google Fonts (ADR-023 decision 4); toolkit Observable Framework 1.13.4 with Plot 0.6.18 and no further dependency (ADR-023, ADR-024 decision 1); stored values only, no recomputation of ranks, percentiles, means, n/N or an overall status in the browser (ADR-010 decision 1, user decision D6, ADR-025 principle 1); neutral sequential percentile scale with the orientation sentence (ADR-025 decision 2, ADR-026 decision 1-2); WCAG 2.2 AA, no-JS notice, print, states (ADR-025 decisions 8-10); landing set at most 1.5 MB gzipped (internal target 600 KB), one interaction at most 5 MB gzipped (ADR-023 decision 6, ADR-025 AC-UX-12); projections have no dashboard output in v1 (ADR-010 decision 9; export spec principle 4).
- Survey observations that inform (not prove) the design. Each is text-level evidence from one or two sites:
  - A country page as per-theme tables with indicator, most recent value, trend, year per value [SURVEY #1]; a per-row table with unit, last, previous and a reference month [SURVEY #7]. Both support "one country, all indicators, with reference period per value" [ANALYSIS §1 row 1]. Failures seen on the same pages: mixed scales in one column and a "(Millions)" label against current US$ [SURVEY #1, #2]; reference month without a header, `Last` and `Previous` without dates [SURVEY #7]; empty trend cells [SURVEY #1].
  - An indicator page with an all-country table (most recent year, most recent value) and a chart-type control [SURVEY #2]; a builder with multi-select countries and a unit-mismatch warning [SURVEY #3]. Support "one indicator, all countries" [ANALYSIS §1 row 2]. No opened example offers a country-by-indicator matrix with ranks [ANALYSIS §1 last line], so our percentile views have no direct precedent in the evidence.
  - Reference period shown per value, not per page [SURVEY #12, #1, #7]; unit as its own field plus subtitle [SURVEY #4, #5]; source and last-updated next to the data [SURVEY #4, #8, #10]; explicit legend of missing-value codes [SURVEY #13] and prose explanations of breaks [SURVEY #5] [ANALYSIS §2]. Under the data-only rule the legend and prose become a short inline marker or sentence beside the value, not a separate page.
  - Forecast handling is inconsistent: a separate forecast column [SURVEY #6]; years not marked [SURVEY #8, #2] [ANALYSIS §2]. Not applicable to v1 data (no projections exported), see Decision 7.

## Options considered
1. Structure.
   a. Keep the domain-centred structure and fix the surface problems (labels, units, tooltips) only. Cheapest. Does not give "one country, all data" or "one indicator, all countries" without learning the domain tree. Rejected: two of the user's eight complaints are structural.
   b. Three entity-centred page types (country, indicator, series) plus the domain pages as a secondary overview (chosen).
   c. One generic query page (country x indicator x time, like a report builder) [SURVEY #3]. Powerful, steep, and the survey notes the steep layout of that tool; the export is partitioned by indicator and domain, so arbitrary country-first queries are costly. Rejected for v1.
2. Page generation for entities.
   a. One `country` page and one `indicator` page, selected by a URL hash. Fewer files, and no stable path per country.
   b. One generated page per country (44 countries and aggregates, excluding `WLD`) and per indicator (about 80), as `domain/<id>` and `peers/<id>` are generated today [REPO baseline]. Stable shareable paths, printable, a static `h1` and static link lists work without JavaScript (chosen). Cost: about 125 small pages; build time and `dist` size are expected to be small [UNVERIFIED; measured by AC-RD-53].
3. Country picker. a. A `<select>` only (needs JavaScript). b. Static link lists generated at build time on the home page, enhanced with a text filter (chosen): works with no JavaScript, which the Framework cannot otherwise provide for cell content [REPO baseline (d)].
4. No-JS content. a. Bake data tables into the static Markdown at build time. Rejected: a second rendering path for the same numbers, needing its own tests and formatting, for a fallback that ADR-025 decision 10 already limits to a notice. b. Static names, links and notice only (chosen).
5. Missing data. a. Print `n/a` as today. b. Keep the confirmed state codes and add a plain sentence per state, using only stored fields and the stored series list; request an explicit stored reason in the export (CR-3) (chosen, in that order). c. Hide rows without values. Rejected: an analyst must see what is missing (the Eurostat precedent keeps the code visible with a legend [SURVEY #13]).
6. Explanatory pages. a. Keep a Guide page (legend of states, units, sources) and a Status page (pipeline health). b. Remove both; the dashboard shows only data (chosen, user instruction 2026-11-06). The legend is replaced by the inline sentence of Decision 5; sources by the per-value source name and the footer sources line; pipeline health is not shown to readers.

## Decision
1. Journeys and primary structure. The dashboard is organised around three entity pages: PG-COUNTRY (J1), PG-INDICATOR (J2), PG-SERIES (J3). They link to each other (every country name goes to its profile, every indicator name to its page, every profile row to the series page with country and indicator preselected). The domain is demoted to a grouping inside those pages and to a secondary overview. All journeys remain hypotheses until the user confirms them (Q1).
2. Page structure and entry points. Header navigation on every page: Home, Time series, Domains, Revisions. (Guide and Status are removed from the header and from the site.) The home page is an entry page: the standing caveat (one line), the freshness line with the export cut-off date, a list of countries (static links to PG-COUNTRY), a list of indicators grouped by domain (static links to PG-INDICATOR), each list with a text filter. Secondary pages (domain heatmaps, revisions) are reached from the header and from links in context. Page list, URLs and components: spec section 2.
3. Pages kept, merged, dropped.
   - Kept unchanged in behaviour: `revisions` (V4), now secondary; the standing caveat (one line), freshness line, footer sources line. The stale banner stays as a data-currency marker and no longer links to a status page. Confirm: the banner wording fixed by ADR-025 decision 10 contains no link; if it does, the link is removed.
   - Kept with additions: `domain/<id>` (V1 heatmap): country and indicator labels become links; it is the secondary overview. `explorer` (V3) stays at the same URL and becomes PG-SERIES with the changes of Decision 6.
   - Merged: `peers/<id>` (V2) is merged into PG-INDICATOR. Its peer-group filter, sort, standing caveat, orientation note (one line), reference-period spread and dot plot move to the indicator page, so the user no longer has to know the domain.
   - Dropped: the `status` page (V5) and the planned `guide` page (PG-GUIDE); the home page's domain list moves to a new `domains` page; the conditional landing heatmap (ADR-025 decision 4, Stage 2, plan T114-T116 not built [REPO baseline, open item 2]) stays unbuilt unless the user asks; the old `peers/<id>` URLs stop existing (Q6). Dropping `status` removes an existing page of ADR-010/ADR-025 (amended below).
   - New: PG-COUNTRY, PG-INDICATOR, `domains`.
4. What each page shows (summary; detail in the spec).
   - Country profile: per domain, a chart of the stored percentiles of that country's indicators (a dot strip, one dot per ranked indicator) and the table beneath it: indicator name with direction label, latest value with unit, reference period, percentile bin and number or the state, source. History for an indicator opens on demand as a line chart for that country. No composite across domains (U1, ADR-010 decision 9).
   - Indicator page: chart of the latest value by country (in the indicator's unit) with the percentile dot plot, and the all-country table with value, unit, reference period and offset, percentile or state, source; the stored reference-period spread is printed above the ranking.
   - Series page: one indicator per chart (stated in the chart title), at most 5 overlaid lines, direct labels carrying the unit, a hover tip with name, period, value, unit and status, and a table alternative.
5. Missing data. Every absent value shows the confirmed state code AND one short plain sentence; `n/a` never appears alone. The sentence is chosen from stored fields only: the existing state (stale, lagging, unaligned, not published, descriptive, not ranked, aggregate) or, for `n/a`, whether `meta/series.json` lists a series for the country and indicator ("a series is defined but this export holds no value for it" versus "no series is defined for this country and indicator"). Rows without a value are grouped after rows with a value and are never dropped; a filter can hide them. Where the cause cannot be read from stored fields, the page does not guess; CR-3 asks analytics to store a reason (Q4).
6. Series page changes. Default selection: the country carried in the URL (or the country in focus), at most 5 overlaid lines, small multiples above 5 (ADR-025 decision 6, unchanged limit); picking a country group no longer overlays a group on one chart by default and opens small multiples (the reason is one short line) (Q2). Titles use indicator names, never bare identifiers like "M09"; every axis, end label, tip and table header carries the unit. Hover tip via Plot's pointer/tip marks [UNVERIFIED in this repository for Plot 0.6.18; to be confirmed in the first implementation task]; the "View as table" disclosure remains the keyboard and screen-reader route (ADR-025 decision 6).
7. Forecast. v1 exports no projections (export spec principle 4 and section 7) and ADR-010 decision 9 gives projections no dashboard output. Pages show no forecast values. Under the data-only rule no sentence about projections is added to any page; estimates and provisional values are shown with the existing estimate mark. If the user wants forecasts, that is export change CR-2 and depends on the v2 forecast store (ADR-011); it is not decided here (Q5).
8. Units. Every number is displayed with its unit text from `meta/indicators.json` `unit_label` (indicator level) or `meta/series.json` `unit_code` and `unit_mult` (series level), in the column header, the chart axis, the end label, the hover tip and the table. Percentiles are labelled as percentiles (existing labels). The browser never converts units or rescales values for display other than the approved display-only rebase to 100. The survey shows the failure mode being avoided: bare numbers and mixed scales [SURVEY #1, #8, #12]. Whether `unit_label` states the scale, and which unit applies to `transformed_value`, are not confirmed by the specs read; CR-5 and CR-6.
9. Reference dates and sources. Each value row shows its own reference period (formatted from the stored `ref_period_end` and frequency; formatting only), the offset against the common period when stored, and a source name; "About this value" is a compact field list (series id, frequency, seasonal adjustment, `known_at` (vintage), `source_release_at`, attribution, link to the source page, flags), with no prose. The page-level line is the export's `known_cutoff` (freshness line), not a substitute for per-value dates [SURVEY #12 shows per-card periods; #2 shows the failure of a page with no update date].
10. Naming. Names come from `meta/*`; the identifier is secondary text. Long names wrap and are never truncated without the full name in the accessible name. If the existing names are the "unclear naming" the user means, the fix is in the indicator configuration and, optionally, a `short_name` in the export (CR-7); the dashboard does not invent names (Q3).
11. No change to the export in this ADR. Everything above is built from files that exist. Where a page needs more, the spec lists a change request (CR-1 to CR-10); none is made here and none is needed for the acceptance criteria except where a criterion says "when CR-n is approved".
12. Amendments. This ADR amends, without editing them: ADR-010 (decision 9: the displayed semantics for rankings and informational domains now live on PG-INDICATOR and PG-COUNTRY as well as on V1; the Status view V5 and any Guide page are removed; the "views V1-V5" vocabulary of its consequences and the design document sections that use it), ADR-025 (decision 4: landing heatmap not on the home page; decision 7 and AC-UX-6 and AC-UX-12 page lists extended to the new pages and without `status`; decision 12 stage list; the V1-V5 names in decisions and in AC-UX-1 to AC-UX-15; any requirement tied to the status page), ADR-026 (decision 2: the orientation note and the percentile-column description placed on V2 apply on PG-INDICATOR and PG-COUNTRY instead; decision 7: sort rules apply on the indicator page, default alphabetical; AC-UX-13 and AC-UX-15 page lists). Documents that would need follow-up edits after approval (not ADRs): `docs/design/briefs/dashboard-ux-brief.md` section 4, `docs/plans/dashboard-ux-implementation-plan.md`, the design document sections naming V1-V5 [not re-read]. ADR-023, ADR-024 and the export spec are applied unchanged. The `status` data (`ops/` heartbeat, alerts) stays available to operators outside the dashboard (`docs/ops/`).

## Constraints respected
- Static site, no live queries, no off-origin request: pages read only the files of `docs/specs/dashboard-export-spec.md` (spec section 3 maps each page to its files).
- D6: no rank, percentile, mean, n/N, position or overall status is computed; the new country dot strip plots stored percentiles; the indicator value chart plots stored values; sorts use stored fields; the only added lookup is "is a series listed in `meta/series.json`", a set-membership read of a stored list.
- No new library: Plot marks, HTML tables and CSS only (ADR-024 decision 1). The text filters are plain DOM code.
- Weight: country and indicator pages load JSON metadata and domain scorecards; Parquet series (and the Parquet reader libraries, first interaction about 1.8 MB gzipped on the fixture [REPO baseline, T133]) load only on demand. Budgets and measurements: AC-RD-53.
- Projections: none shown (Decision 7).

## Consequences
- Positive: each of the user's stated complaints has a named place where it is fixed (spec section 6 traceability); one country or one indicator is one click from the home page and one link from any table; empty rows say why; units and reference dates are printed where the numbers are; two pages (Guide, Status) fewer to build and maintain; no export change is required to ship the core.
- Negative: about 125 additional generated pages; the country page reads all domain scorecards (export spec: about 200 KB uncompressed per domain, under 2 MB in total [export spec section 5, analyst estimate]); on today's Eurostat-only export most country profiles will be mostly "no value" rows, which improves honesty but not usefulness until more sources load (baseline (e)); old `peers/<id>` URLs break; readers lose in-site pipeline status and a state legend page (the inline sentences replace the legend); more copy to confirm (ADR-025 decision 11); acceptance of the structure rests on unconfirmed journeys and answers proposed from the audience.
- Risks: the journeys are wrong (mitigation: Q1 and the validation protocol in spec section 8); an indicator that belongs to two domains appears in two scorecard files and the two copies must agree (AC-RD-24); the reason for a missing value cannot always be derived from stored fields (CR-3); Plot tip behaviour is [UNVERIFIED] here; the Framework produces no server-rendered cell content (baseline (d)), so the no-JS fallback stays a notice plus static links.
- Reversal: pages are independent and the export is unchanged, so reverting to the domain-centred home is a navigation and home-page change; Guide and Status can be restored as separate pages without touching the entity pages; the old pages removed are `peers/<id>` and `status`.

## Answers to the open items (user: "move as recommended", 2026-11-06)
The user accepted the recommendation of the Opus review (2026-11-06) for each item below. This records the answers; it does not approve ADR-030, which stays `proposed` until the user approves it explicitly. Items marked "measure" or "check" are not yet done; items marked "user" still need the user's own input (for example the list of unclear names in Q3).
Basis: the user stated the audience (students and professors of economics and similar) and the data-only rule. Each answer below is PROPOSED, with its reason; none is user-confirmed, and the user may overturn any. The audience is a stated fact; the reasons drawn from it about how that audience behaves are assumptions and are marked [UNVERIFIED]. "Confirm" marks an answer that still needs a fact only the user has.

- Q1 Journeys and users. PROPOSED: users are economics students and professors, not a general reader. Keep J1, J2 and J3 as equal primary pages; no ranking among them is claimed. H5 (take data away) is raised to SECONDARY-HIGH; H3 stays secondary; H4 is met by inline unit, period, source and markers. Reason: coursework and research need cross-country comparison (J2), time series (J3) and country profiles (J1), and need to cite and reuse numbers. Confirm: journeys are untested; the validation protocol in spec section 8 still applies.
- Q2 Series per chart. PROPOSED: keep the cap of 5 overlaid lines; more become small multiples. Reason [UNVERIFIED assumption]: economists routinely compare a handful of countries on one indicator; a lower cap would make that routine task harder, and the stated problem was overlaying many series, which the cap and one-indicator-per-chart already address. Confirm: which chart produced "too many" (unanswered).
- Q3 Naming. PROPOSED: use the standard economic term from the source as the display name, identifiers secondary, state codes always paired with plain words (Decision 5); add `short_name` only if long names break layout (CR-7); no `definition` field. Reason: this audience knows the terms, and a definition is explanatory prose that the data-only rule removes. Confirm: which names the user found unclear.
- Q4 Missing data. PROPOSED: the two-way sentence of Decision 5 is enough for now; no CR-3 yet; rows without a value are shown, grouped after rows with a value, not collapsed, with a filter. Reason [UNVERIFIED assumption]: economists judge coverage and need to see gaps; hiding them would misrepresent the dataset. Confirm: the choice depends on measuring how many sparse-export rows `meta/series.json` classifies as defined-but-empty (not yet measured). CR-3 stays open as a follow-up if sentences prove insufficient.
- Q5 Forecasts. PROPOSED: not in the first redesigned version; no projections sentence on any page. Reason: no stored projection exists (ADR-011 v2, CR-2), and mixing projections with data without a stored marker would risk misreading; the data-only rule adds no explanatory line.
- Q6 `peers/<id>` URLs. PROPOSED: acceptable to drop; no stub redirect pages. Reason: stubs would be non-data pages; the old URLs are in a pre-release site, whose external citations are [UNVERIFIED]. Confirm: no known external links to `peers/<id>`.
- Q7 Page generation. PROPOSED: generated pages (about 125). Reason: students and professors cite and share links in slides, syllabi and papers; stable per-country and per-indicator paths serve that, and print works without JavaScript.
- Q8 Domain order. PROPOSED: a configured order (CR-9), following the textbook sequence of macro topics, alphabetical by id until it exists. Reason [UNVERIFIED assumption]: this audience expects a conventional order, not an alphabetical one. Confirm: the order itself is the user's choice.
- Q9 Secondary journeys. PROPOSED: no "what changed" feed (the revisions page stays); add a CSV download of the displayed series as a change request (CR-10, not made here), keeping the Parquet and JSON links. Reason: a feed is operations content; academics take data to Excel, Stata or R. Confirm: that CSV is wanted.
- Q10 Evidence. NOT CLOSED by the audience: it is a document gate. PROPOSED action: copy the survey and analysis into `docs/research/` for the user's approval; re-checking OECD, IMF, ECB and analyst-tool pages in a browser is optional and the user's call.
- Q11 Timing. PROPOSED: build and evaluate on the fixture and on today's sparse export, but do not present it to students or professors until a fuller export loads; the baseline's own re-check gate stays. Reason: a reader from this audience would read mostly empty profiles as a poor dataset. Confirm: the user's release threshold.
- Q12 Strings. NOT CLOSED by the audience: the user must confirm the strings of spec section 7 (all DRAFT, ADR-025 decision 11). The set is smaller after the removal of Guide and Status.

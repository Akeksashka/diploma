# ADR-012: Privilege-matrix authority, no `mm_ingest` access to `analytics.*`, and a run-metadata view for the read-only export role (amends ADR-008)

Date: 2026-10-24 (Phase 2 rework after the planning pass). No external facts are used in this ADR; every statement below is about this repository's own documents (ADR-008, `docs/specs/ddl-neon-schema.md` section 8, `docs/specs/dashboard-export-spec.md` sections 3 and 10).

## Context
Two defects were found by the planning pass.

1. Grant conflict. The ADR-008 summary matrix (Decision, role table) lists `analytics.run` under `mm_ingest` SELECT. The normative cell-by-cell matrix in the DDL spec section 8 gives `mm_ingest` no privilege on `analytics.run` ("none"), and test T-DDL-10 asserts the DDL matrix. ADR-008 itself says "the DDL spec wins in case of conflict", but an approved ADR that contradicts the spec it points to is an ambiguity that an implementer can resolve either way. Smaller differences of the same kind exist: ADR-008 gives `mm_analytics` SELECT on `ops.*` (DDL: only the listed `ops` tables, not `ops.schema_migration`) and gives `mm_reader` no entry for run metadata (see 2).
2. Export cannot read run metadata. The export manifest (`ingest_run_id`, `analysis_run_id`, `known_cutoff`, `code_version`) and check EXP-10 ("in refresh mode the `analysis_run_id` used belongs to the current `ingest_run_id`") need `analytics.run`. `mm_reader` may read only published objects (ADR-008, DDL section 8) and has no privilege on `analytics.run`, so the export step as specified cannot produce its own manifest or run EXP-10. `status.json` `last_run` also needs `started_at`, `finished_at` and `mode` of the ingest run, which live in `ingest.run` (no `mm_reader` privilege); the view `ops.v_run_summary_public` was named in the specs but its columns were never defined.

Does anything need `mm_ingest` to read `analytics.run`? The steps that run under `mm_ingest` are plan, fetch, load, monitor, record-export, backup and decide (workflows spec section 2 table of secrets). `monitor` computes freshness, backlog, DB-size and COV-01 from `curated`/`ref`/`ops`; `record-export` inserts `ops.export_status` from the artifact (the `analysis_run_id` column is a plain `bigint` without a foreign key, so no read privilege is involved); the validation spec states that analytics alerts do not create issues in v1 (validation spec section on alerting, "they do not create issues in v1"). No step was found that needs it. [Based on a read of the workflows and validation specs on 2026-10-24; if a later step needs analytics output under `mm_ingest`, it needs a new view and an ADR, see Consequences.]

## Options considered
For the grant conflict:
- A. Grant `mm_ingest` SELECT on `analytics.run` (make the DDL match ADR-008). Widens a writer role that holds the most privileges for no identified use; also makes `mm_ingest` able to read `params`/`mapping_sha256`/`overrides_sha256`.
- B. Keep the DDL as normative (`mm_ingest`: none) and amend ADR-008. Least privilege; one source of truth.
For the export's run metadata:
- C1. Grant `mm_reader` SELECT on the base table `analytics.run`. Exposes `params` (all thresholds actually used), `mapping_sha256`, `overrides_sha256`, `config_asof`; breaks the rule "`mm_reader` has no SELECT on any base table".
- C2. A narrow view `analytics.v_run_published` over `analytics.run` exposing only the columns the export needs, owned by `mm_owner` (a view runs with its owner's rights unless declared security-invoker [general PostgreSQL behaviour, UNVERIFIED on Neon but standard]), SELECT granted to `mm_reader`.
- C3. Pass `analysis_run_id` and `known_cutoff` from the `analyze` step to the `export` step as workflow artifact or outputs. No database privilege, but then EXP-10 compares a value with itself; a mismatch between the artifact and the database could not be detected, and the manifest would rest on an unauthenticated number.
- C4. Denormalise run columns into every published table. Redundant data in many rows.
- For `status.json`: extend `ops.v_run_summary_public` (already granted to `mm_reader` through `ops.v_*`) and define its columns, instead of granting `ingest.run`.

## Decision
1. Option B. The DDL spec section 8 is the single normative privilege matrix; the matrix in ADR-008 is a non-normative summary. Where the two differ, the DDL spec wins and the expected matrix of T-DDL-10 is derived from the DDL spec only. `mm_ingest` has no privilege on any `analytics.*` or `analytics_r.*` object. This amends the following parts of the ADR-008 Decision table: (a) `mm_ingest` SELECT list: remove `analytics.run`; (b) `mm_analytics` SELECT on `ops.*`: read as the listed `ops` tables of the DDL matrix (not `ops.schema_migration`); (c) `mm_reader`: add `analytics.v_run_published`, and read the `ops.v_*` entry as the views listed in DDL section 7.
2. Option C2 plus the `ops.v_run_summary_public` definition. `analytics.v_run_published` exposes exactly `analysis_run_id, ingest_run_id, as_of_run_date, known_cutoff, load_cutoff, code_version, git_sha, config_sha256`. It deliberately excludes `params`, `mapping_sha256`, `overrides_sha256` and `config_asof`. `ops.v_run_summary_public` is defined in the DDL spec section 7 (columns: ingest run id, workflow, mode, status, started_at, finished_at, and the published-scope counts). Both are owned by `mm_owner`; `mm_reader` has SELECT on them and still has no privilege on `analytics.run`, `ingest.run` or `ops.run_summary`.
3. The export selects its run as: the row of `analytics.v_run_published` with the greatest `analysis_run_id` whose `ingest_run_id` equals the `ingest_run_id` supplied by the workflow (an environment variable set by the `plan` step output). EXP-10 fails when no row exists. The manifest fields come from that row.
4. Other fields of the pipeline are unchanged: `mm_reader` stays strictly read-only; `record-export` still writes `ops.export_status` under `mm_ingest`.

## Consequences
- Pro: least privilege kept; export can verify its input run against the database; the matrix has one authority; no new role, secret or component.
- Con: two more objects in the matrix (`analytics.v_run_published`, defined `ops.v_run_summary_public`); view column lists must be kept in step with `analytics.run` (a test asserts the exact column set).
- Tests (added to the DDL spec): T-DDL-10 expected matrix gains the `analytics.v_run_published` row and the explicit negatives "`mm_ingest` cannot SELECT `analytics.run`" and "`mm_reader` cannot SELECT `analytics.run`, `ingest.run` or `ops.run_summary`"; T-DDL-26 checks the exact columns of the two views and that `params` is not selectable by `mm_reader`; AC-EXP-9 (export spec) checks that manifest values equal the view and that EXP-10 fires for a stale run.
- If a later feature needs `mm_ingest` to read analytics output (for example opening issues from alerts), add a narrow view and amend this ADR; do not grant base-table SELECT.
- ADR-008 remains `approved` and its text is unchanged. This ADR is `approved` (front matter: approved by the user on 2026-10-24). The DDL and export specs that implement it were set to `approved` on 2026-10-24, reset to `draft` on 2026-10-25 by the round-6 amendment batch (which wrote the tests announced above, T-DDL-26 and AC-EXP-9, into them), approved by the user on 2026-10-25 after a read-only review, and set to `draft` again by the Phase 2 fix pass of 2026-10-25; the user re-approves them. No claim is made that ADR-008 is superseded: only the three points in Decision 1 are amended.

# ADR-007: Layered validation with severity policy, release-aware freshness, and alerting through GitHub Issues

Revision note (review fixes): self-enable call removed and non-circular dead-man detection defined (A6); expected re-estimation families are loaded and reported rather than blocked (A4); human-accepted drift reloads from stored raw (A2); coverage diagnostic added (B7). Second round (2026-10-18): REV-01 uses a materiality rule and respects the group flag `reestimating`; fallback ladder for the 60-day rule. Round 5 (2026-10-24): REV-01 materiality uses the loader's half-unit rule on `published_decimals`; COV-01 excludes initial loads; queue naming and stale-banner basis corrected; BKP-01 inactive.

## Context
- Needs: validation contracts, anomaly and staleness detection, release-calendar-aware freshness SLAs, alerting (architect brief). CLAUDE.md requires the series metadata convention on every series.
- Two different notions of "stale" exist and must not be conflated: (1) feed health (did the source publish what we expected?), and (2) ranking staleness (D6, D14: a value older than the per-indicator limit is excluded from ranks but kept and displayed).
- Monthly cadence means a silent failure can go unnoticed for a month; scheduled workflows can be delayed, dropped or auto-disabled (ADR-001). GitHub Actions has no built-in alert channel except notifications and the API; the repo is public, no external paid service is allowed.
- Tools: pandera 0.34.1 (MIT, lightweight) vs Great Expectations 1.24.0 (heavier, data docs) (tooling research E, finding 13).
- Known data-quality realities: Eurostat dataset code changes (`prc_hicp_manr` -> `prc_hicp_minr`, classification and base-year change from January 2026 data), stale OECD series (e.g. Japan CPI ends 2021-06), partial/intermittent source outages (ECB 503) (data-sources research F5, F13, risk 6). Some families recompute their whole history by design (BIS credit gap, OECD CLI, SA series), which a naive mass-revision rule would block every time. Sources also differ in published rounding, so tiny differences between vintages are noise, not revisions.

## Options considered
1. pandera schemas + SQL checks + custom freshness logic; alerts as GitHub Issues.
2. Great Expectations with data docs published to Pages.
3. External monitors (healthchecks.io, Grafana Cloud free). Free-tier terms not verified; adds a component; Grafana Cloud free has 14-day retention (tooling research F).

## Decision
Option 1.
- Validation layers, in order, each with a stable check ID (catalogue and thresholds in `docs/specs/validation-monitoring-spec.md`): RAW (HTTP status, non-empty, bot-challenge signature, size sanity, hash), PARSE (pandera contract on staging frames: required columns, dtypes, parseable periods, numeric values or declared missing markers, frequency consistent with series metadata, no duplicate keys), META (NOT NULL / CHECK constraints in the database for source, series key, frequency, unit, seasonal adjustment; known_at and raw_id on every observation), SEM (per-indicator plausible bounds, jump detection against own history, units), REV (revision size and depth, share of series revised in one fetch, tolerance, expected re-estimation), COMP (series count and per-entity coverage versus last successful load, input availability), COV (stale-on-arrival diagnostic), ORD/LOAD (load order and backlog), FRESH (release-aware), DB (size, projection, per-object row cap), BKP (dump coverage; BKP-01 is inactive while no private repository exists).
- Severity policy: `error` blocks the load of that raw object (other groups proceed) and opens an issue; `warn` loads the data, records the finding and opens/updates an issue; `info` is recorded only. Nothing is silently dropped: a rejected row goes to `staging.rejected` with a reason code. A value judged suspect by SEM is still loaded (it is what the source published) with `quality_flag = 'suspect'`; analytics skip suspect rows only if listed in `ops.quality_override` by a human decision.
- Mass revision versus expected re-estimation (A4, second round; materiality rule restated in round 5): REV-01 measures the share of a dataset's keys with a MATERIAL revision in one fetch. A revision is material when it is a revision under the loader's comparison rule (the difference exceeds `max(rel_epsilon * max(|a|,|b|), 0.5 * 10^-d)` with `d` = the series' derived `published_decimals`, that is half a published unit, the same rule as ingestion spec step 7 and DDL I-CUR-3) and, where the group sets a materiality, also exceeds `max(materiality_abs, materiality_rel * |old|)` (relative term not applied to ratio-dimension units). The earlier wording "one unit of the series' `published_precision`" was inconsistent with the loader (a full unit hides typical 0.1 pp revisions of one-decimal rates) and is withdrawn; `published_precision` is only the config display hint of the export. Smaller differences are rounding or float noise (REV-05). More than 20 % material revisions is a re-estimation event for groups without the `reestimating` flag: the object stays unloaded (no `ingest.raw_load` row; listed in `ingest.v_raw_unloaded`), `ops.drift_event` (kind `mass_revision`) is raised, a human decision is required (ADR-002 succession). Groups of the re-estimation class, that is the group flag `reestimating` (dataset families that recompute history by design: BIS credit gap, OECD CLI, SA re-estimation; set in config or by a human through `decide` for a known rebase window), skip REV-01; their material revisions are loaded, labelled `revision_class = 'reestimation'`, and reported by REV-06 (info) with counts, but a per-object cap `max_revised_rows` still blocks an implausibly large object. Any change in unit, base period, SA flag, classification or frequency metadata is always a drift event (META-02), never "expected".
- Human decisions (A2): when a human accepts a drift event (the new series version and mapping switch being a reviewed config commit), the blocked object or deferred series is reloaded from the stored raw bytes without refetching, in `fetched_at` order, with its original `known_at`; a rejected decision records `rejected` and successors proceed. Decisions are applied by the dispatch-only `decide` workflow (workflows spec section 11), which records the GitHub actor.
- Freshness (feed health) is evaluated per series group against an expected latest period computed from frequency, typical publication lag and tolerance (config per source group, optionally an explicit release calendar); states `fresh | late | stale | broken`. Ranking staleness (D14 limits) is computed separately in `analytics.indicator_snapshot`. D14 is user-approved and unchanged; a coverage diagnostic (COV-01) reports per indicator the share of entities whose values are already stale when first seen, as a warning to the user, with A12, A14 and A22 listed as known risk [UNVERIFIED, from review]. Round 5 (PROPOSED P20): COV-01 counts only entities whose latest period arrived after launch (first stored row is not `load_kind = 'initial'`, because the launch fetch date is not a publication date), reports the number of qualifying entities, and shows "not yet measurable" until enough post-launch periods exist. An optional `release_lag_aware` limit (max of the class limit and typical publication lag plus tolerance) is switched on for a named list of indicators, the list pending the user (analytics spec section 8, P5; design 14b Q31; plan OQ-10); the global default is false (see the bookkeeping note at the end).
- Alert channel: GitHub Issues created by the workflow with `GITHUB_TOKEN` (`issues: write`), label `pipeline` or `data-quality`, one issue per `(check family, source group)` found by title key, comment on repeat, closed automatically when the check passes in a later run. Repo watchers receive e-mail through GitHub notifications [GitHub notification behaviour not verified in this session].
- Dead-man protection (A6, second round): the refresh and catch-up schedules are protected by an explicit fallback ladder, because the 60-day rule disables all scheduled workflows together and a re-enable call from a scheduled workflow is circular (withdrawn). (a0, restored in review round 3: the earlier "circular" objection applies only after disablement; a preventive call by the monthly run before day 60 is not circular) the scheduled `finalize` calls the enable-workflow API with an `actions: write` token, failure only warns, effect on the inactivity counter [UNVERIFIED] (see ADR-001). (a) Heartbeat commit: each finalised scheduled run writes `ops.run_summary` and commits a small `ops/heartbeat.json` (run id, UTC time, per-group status) to the default branch; whether a bot commit resets the inactivity clock is [UNVERIFIED], and so is whether `GITHUB_TOKEN` may push to a protected default branch (BB26). A heartbeat from a non-scheduled path (`ingest-manual`, dispatch) is not relied on, since it only runs when a human acts. (b) A documented human check on the 2nd of each month (the only level that does not depend on GitHub's scheduler). (c) An optional external free dead-man ping [OPTION, UNVERIFIED, not adopted; a new ADR and the user's decision are needed, design Q15]. The dashboard stale banner (the manifest's `known_cutoff`, not `generated_at`, older than 45 days, evaluated in the visitor's browser) is a further signal: a failed `analyze` must not be hidden behind a fresh build time. AC-OPS-4 is time-boxed (days 7, 55, 65, 125 after the first scheduled run; workflows spec section 9). FRESH-02 and the status page "overdue" text work only while some workflow still runs.
- Great Expectations is not adopted (no data-docs need; extra dependency).

## Consequences
- Checks are code and tests in this repo; thresholds are config and are recorded per run so alert history is reproducible.
- Issue-based alerting is noisy if thresholds are wrong; each family has a dedupe key and a per-run cap of 20 new issues (excess summarised in one issue).
- A skipped or disabled monthly schedule is detected by a human via the missing run, the stale banner or the monthly check, not automatically; this residual risk is accepted unless AC-OPS-4 fails or the user chooses a watchdog, and is listed in the design doc risks (R1).
- Re-estimation families add storage (ADR-002 worst case); the REV-06 cap, DB-05 and the DB-02 projection bound the risk.
- Materiality depends on correct `published_decimals` per series (derived at first load; frozen; increase-only); a wrong value would hide real small revisions or raise false mass-revision errors, so it is part of the series-map `expect` review.
- Pandera/pandas 3 compatibility must be confirmed at implementation (tooling research, risk 1).

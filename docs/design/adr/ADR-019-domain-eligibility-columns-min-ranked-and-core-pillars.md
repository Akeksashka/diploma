# ADR-019: Domain eligibility is configuration: `min_ranked_indicators` and `core_pillars` become `ref.domain` columns (replaces the constant 3 and the unimplemented P8 clause)

Date: 2026-11-04 (Phase 2 amendment batch; revised the same day with the user's answers). Facts are about this repository, read on 2026-11-04: `docs/plans/macro-monitor-v1-implementation-plan.md` (notes of T42 and T44), `docs/specs/analytics-and-r-contract-spec.md` (section 4.4, AC-AN-6, AC-AN-19, P8), `docs/specs/source-config-schema.md` (section 3), `src/macro_monitor/analytics/scorecard.py`, `src/macro_monitor/analytics/run.py`, `src/macro_monitor/registry/sync.py`, `src/macro_monitor/registry/schemas/indicators.schema.json`, `src/macro_monitor/storage/migrations/0001_ref.sql`, `0002_config_history.sql`, `0006_roles_grants.sql`, `0008_analytics.sql`. No external source is used for the decision; PostgreSQL behaviour used in the migration is cited in the amendment spec `docs/specs/domain-eligibility-amendment.md`.

## Context
- The analytics spec (section 4.4, AC-AN-6) says a domain with fewer than `min_ranked_indicators` (default 3) ranked indicators is descriptive. `ref.domain` has no such column. The implementation uses the module constant `MIN_RANKED_INDICATORS = 3`; the dataclass `DomainDef.min_ranked_indicators` exists but `load_domain_context` never fills it (plan T42 note, items 1 and 2; `scorecard.py`).
- Proposed amendment P8 (analytics spec section 4.4 and section 9) adds an optional `ref.domain.core_pillars` rule: when a domain declares pillars, an entity must have at least one available indicator from each pillar, otherwise it is `low_coverage`. AC-AN-19 contains a clause for it. No column, no config effect and no code exist: the module docstring says "not implemented ... reported", and the T44 note says "needs migration/ADR".
- A half-step already exists in code: `indicators.schema.json` accepts `core_pillars` (array of strings) on a domain, while `sync.py` (`_sync_indicators`) ignores it. The key is therefore accepted and silently without effect, which is the worst state for a rule that changes published ranks. The specs name neither a way to say which indicator belongs to which pillar nor what a pillar string refers to.
- Eligibility is static configuration (count of configured ranked indicators), so it can be, and since T44 is, applied before the snapshot is written (`demote_ineligible`). A constant in code means a change of the threshold or of a domain's pillars is a code change, outside `ref.config_history` and outside `config_sha256` provenance of the analysis run.
- Constraints: ranks are published results (ADR-014 principle: a value that changes published ranks must not be inherited silently); the schema moves only by forward-only migrations; the shipped behaviour (3, no pillars) must not change when the migration is applied, so the golden `published_set.json` stays valid.

## Options considered
1. Keep the constant 3 and withdraw P8 and the AC-AN-19 clause. Smallest change. Cost: a domain cannot be tuned (for example a domain with only two meaningful ranked indicators), and the known weakness P8 was meant to address (an entity ranked on one easy indicator of a domain while the core pillar is missing) stays unaddressed. The accepted-but-ignored `core_pillars` key would have to be removed from the schema.
2. Columns on `ref.domain` (`min_ranked_indicators`, `core_pillars`) plus an optional `pillar` tag on `ref.indicator_domain`, all written by `sync-config` from `indicators.yaml`. Chosen below.
3. A generic `params jsonb` on `ref.domain`. No CHECK constraints, no typed access, hidden from review; the opposite of how `stationarity_class` and `release_lag_aware` were handled (ADR-014, columns because analytics reads them every run).
4. Reuse `concept_id` as the pillar. `concept_id` means "the same concept measured twice, count once" (P15); a pillar means "different aspects that must each be represented". Conflating them would change de-duplication.
5. Define pillars by `priority: core` (require at least one available core-priority indicator). Needs no new tag, but couples a methodology rule to a catalogue attribute that has another meaning (D-level priority of the selection), and cannot express more than one pillar.

## Decision
Option 2.
1. `ref.domain.min_ranked_indicators smallint NOT NULL DEFAULT 3 CHECK (min_ranked_indicators >= 1)`. Config key `min_ranked_indicators` on a domain entry (optional, default 3). The eligibility test of analytics is unchanged except that the threshold is the column of the domain: a domain is eligible when `is_ranked` and the number of its ranked members (`kind = 'indicator'`, `rank_mode <> descriptive_only`, `indicator_domain.is_ranked`) is at least its own `min_ranked_indicators`.
2. `ref.domain.core_pillars text[] NOT NULL DEFAULT '{}'`. Config key `core_pillars` on a domain entry (optional, default none; the key the schema already accepts, now with the meaning below). A pillar is a short label ([a-z0-9_]+). Pillar membership is declared on the domain membership of an indicator: `ref.indicator_domain.pillar text NULL` (config: `domains: [{id, ranked, pillar}]` in the indicator entry).
3. Pillar rule (P8, adopted as written in the analytics spec, now precise): in an eligible domain with a non-empty `core_pillars`, an entity is `low_coverage = true` when its share `n_available / n_defined` is below `min_coverage_for_rank` OR at least one declared pillar has no available indicator (no percentile in the candidate set) for that entity. The rule is evaluated per candidate set (full and published) with the availability of that set, exactly as `n_available` already is. An empty `core_pillars` switches the rule off.
4. USER DECISION (2026-11-04): v1 ships `min_ranked_indicators: 3` on every domain (the current behaviour) and `core_pillars` empty on every domain; no `pillar` tags are shipped. The defaults reproduce the current behaviour, so the golden files stay valid. The mechanism is tested with fixture configs only, as was done for `alert.override` (Q50). Adding pillars later is a separate user decision after a real run shows how many entities are unranked by share alone.
5. USER DECISION (2026-11-04): `low_coverage_reason` is kept. `analytics.scorecard` and `analytics.scorecard_published` gain `low_coverage_reason text NULL` with values `share`, `core_pillar`, `share_and_core_pillar` (NULL when `low_coverage` is false and on rows written before the migration), so the dashboard can say why an entity is shown unranked. The exporter passes it through (never derives it). With the shipped config only `share` can occur.
6. USER DECISION (2026-11-04): `min_coverage_for_rank` = 0.5 (B8) is confirmed; it stops being a "proposed default".
7. Config validation (source-config rules 38-40, in the amendment): `core_pillars` only on `ranked: true` domains; every declared pillar is used by at least one ranked member of that domain, otherwise the domain could never rank and `sync-config` fails; a `pillar` tag only on a ranked membership; `min_ranked_indicators` above the number of configured ranked members is a warning (the domain is descriptive, which is the intended state of `prices` under P13), not an error (this last point is still open, question 1).
8. Migration 0013 (amendment spec): additive `ALTER TABLE` only; the constant default 3 and the empty array default mean every existing row keeps today's behaviour and no table is rewritten.

## Consequences
- Pro: threshold and pillars are visible in `config/indicators.yaml`, versioned in `ref.config_history` (the generic trigger `ref.fn_config_history_feed` uses `to_jsonb(row)`, so new columns are captured without a trigger change; checked in `0002_config_history.sql`), and covered by the run's `config_sha256`. The accepted-but-ignored key stops being a trap: after this change every accepted key has an effect or is rejected.
- Pro: shipped behaviour is identical (3, no pillars): AC-AN-1 golden files do not change; the first run after the migration has the same scorecards.
- Con: three DDL changes (two columns on `ref.domain`, one on `ref.indicator_domain`) plus two on the scorecard tables; the analytics read query, the sync code, the JSON schema and the export (`meta/domains.json`, `low_coverage_reason`) change. `scorecard_published` was created with `LIKE ... INCLUDING ALL`, which does not follow later `ALTER` on `scorecard`, so the migration alters both tables.
- Con: pillars add judgement to a ranking rule. A wrongly chosen pillar set silently makes many entities `low_coverage` (the mean percentile stays visible, only the position is withheld). Mitigation: none are declared in v1; `config-report` prints, per domain with pillars, the number of entities that would be `low_coverage` by the pillar rule; a domain's pillars are `proposed` until the user confirms them.
- The analytics spec statements "fewer than 3" and "P8 optional" are replaced by the column wording; AC-AN-19 clause 3 is rewritten with a database fixture; AC-AN-6 names the column; B8 loses "proposed". These edits are specified in `docs/specs/domain-eligibility-amendment.md` (section 7) and take effect when that document is approved and merged.
- Not changed: D12 (agri and global unranked), D6 (no composite across domains), concept de-duplication (P15), the published/withheld mechanics.
- Reversal: drop the columns in a later forward-only migration; with empty pillars and 3 everywhere nothing depends on them.

# ADR-022: Restore step 3 clears migration-seeded tables with plain DELETE before `\copy` (amends the restore procedure of ADR-015 and `docs/specs/public-dump-spec.md` section 6)

Date: 2026-11-04. Facts come from the repository files cited below (read 2026-11-04). The choice of option (a) is the user's decision (stated in session, 2026-11-04); this ADR records and specifies it. Claims not checked are marked [UNVERIFIED].

## Context
- Finding of implementation task T71: restore step 2 applies `schema.sql`, the concatenation of the migration files (`docs/specs/public-dump-spec.md` section 3, `schema.sql`; section 6 step 2). Two migrations also insert rows into `ref.unit`: `src/macro_monitor/storage/migrations/0001_ref.sql` (line 210, plain `INSERT`, nine units) and `src/macro_monitor/storage/migrations/0010_unit_seed_pc_act.sql` (one unit, `ON CONFLICT DO NOTHING`). Step 3 then runs `\copy ref.unit` from the `v_ref_unit` dump, which contains the same rows (`v_ref_unit` is "all" rows, no redaction, spec section 2), and fails with `duplicate key value violates unique constraint "unit_pkey"`. Spec section 6 and ADR-015 are silent on rows created by migrations.
- Inventory of seeded tables (search of all twelve files `0000`-`0011` in `src/macro_monitor/storage/migrations/` for `INSERT`, `VALUES`, `COPY`, 2026-11-04): the only data-inserting statements are the two `ref.unit` inserts above. Other hits are not seed data: `0002_config_history.sql` line 52 is the body of the trigger function `ref.fn_config_history_feed` (inserts at run time, not at migration time); `0006_roles_grants.sql` lines 34 and 53 use `VALUES` as a literal list inside a role/grant loop. `0000_schema_migration.sql` creates `ops.schema_migration` but inserts nothing; the spec already states that its rows come from data, not from `schema.sql` (spec section 3). Other seeds mentioned in `docs/specs/ddl-neon-schema.md` (the eleven domains, entity `WLD`) are "the config seed" written by `sync-config` (ddl lines 96 and 113), not by a migration, so they are absent after step 2. Result: today exactly one table, `ref.unit`, holds rows after step 2. [Dynamic SQL built with `EXECUTE` could insert rows without the literal text `INSERT INTO`; the search found no such statement, but only text search was done.]
- `ref.unit` has no `config_history_feed` trigger (the feeders are on twelve other `ref` tables, `0002_config_history.sql` lines 61-84; `ref.unit` is not among them). The only foreign key to it is `ref.series.unit_code` (`0001_ref.sql` line 150; search of all migrations for `REFERENCES ref.unit` returned this one line).
- `TRUNCATE` is not usable on `ref.unit` because an incoming foreign key blocks it unless the referencing table is truncated too (PostgreSQL behaviour; documentation not re-read for this ADR [UNVERIFIED]); the user confirmed it fails here. `ref.config_history` needs no clearing: its feeder triggers fire only on the twelve tables above, none of which holds rows after step 2, so it is empty.
- Step 3 already runs `ALTER TABLE <t> DISABLE TRIGGER USER` per table before its `\copy` (spec section 6 step 3), so the append-only guards and `ref.config_history` feeders are off when a `DELETE` is issued at that point.

## Options considered
a. Step 3 clears migration-seeded tables with plain `DELETE` before their `\copy`. CHOSEN by the user.
b. (not chosen) Load seeded tables with `INSERT ... ON CONFLICT` from a staging table. Needs more than `\copy`; rejected by the "psql, gzip, sha256sum only" constraint's spirit and complexity.
c. (not chosen) Remove the seed from migrations and move it to the config seed. Changes applied migrations (forbidden, CLAUDE.md "never edit an applied migration") and the dump would still need the rows.
d. (not chosen) `TRUNCATE ... CASCADE`. Would also empty dependants and is unnecessary; the user found `TRUNCATE` unusable.

Options b-d are listed for the record only; the decision is not re-opened.

## Decision
Restore step 3 gains a "clear seeded rows" action, placed per table between `DISABLE TRIGGER USER` and the first `\copy` of that table.

1. Rule (derived, not a hand-kept list). After step 2 and before the first `\copy`, a table is "seeded" when it is in `manifest.load_order` and `SELECT count(*)` over it is greater than zero. For every seeded table the restore runs `DELETE FROM <table>;` (no `WHERE`, no `TRUNCATE`) and then proceeds with `\copy`. Tables with zero rows are not touched.
2. Why derived rather than an explicit list or a new manifest field. A derived rule covers any future migration that seeds a table without anyone having to update a list in the manifest, the spec and the restore script in step; an explicit list silently misses the next seed and the failure would reappear as a duplicate-key error. A manifest field (`seeded_tables[]`) would need a format bump (`format_version` 1.1, schema file `public-dump-manifest.schema.json` change) and would be wrong whenever the writer's idea of "seeded" differs from the schema file's; the restore-side check looks at the database actually produced by `schema.sql`, which is the thing that matters. The cost is that the rule is open-ended, so it is guarded in point 5.
3. Guard tables. If a non-empty table after step 2 is `ref.config_history` or `ops.schema_migration`, the restore aborts with an error instead of deleting: both are append-only history or the migration ledger (CLAUDE.md "Never UPDATE or DELETE ... history tables"), and non-empty means `schema.sql` or the target database is not what the restore assumes.
4. Order and dependants. The clearing is part of each table's own turn in `load_order` (parents first, spec section 3 `load_order`). Because dependants come later in `load_order`, they are still empty when a parent is cleared, so no foreign key is violated and `DELETE` works with foreign keys enforced; no constraint is dropped or deferred. For `ref.unit` the dependant `ref.series` is loaded after it. Invariant: no table in `load_order` that references a seeded table may precede it (parents-first already requires this) and no seeded row may be referenced by another seeded row of a different table; if a foreign-key error occurs on `DELETE` the restore fails (fail closed) and the database is discarded. [That `ref.unit` precedes `ref.series` in the written `load_order` is implied by the parents-first invariant and is not checked against the writer code here, UNVERIFIED; AC-DUMP-4 covers it.]
5. Pin of the expected set. A repository `db` test applies `schema.sql` to an empty database and asserts that the set of non-empty tables equals the pinned set `{ref.unit}`. A migration that adds a seed fails this test until the pinned set is updated deliberately; this keeps the open-ended rule from deleting rows nobody expected.
6. Triggers. The `DELETE` runs after `ALTER TABLE <t> DISABLE TRIGGER USER` for that table, i.e. with user triggers disabled, so it cannot fire append-only guards or add `ref.config_history` rows. The existing `ENABLE TRIGGER USER` after the last `\copy` is unchanged. Table ownership (`mm_owner`) is sufficient; no superuser is added.
7. Verification (existing step 5, no new step). `SELECT count(*)` of every table must equal the sum of `rows` of its files in the manifest. This proves the dump, not the migration seed, is the final content of a seeded table (for `ref.unit`: the count equals `rows` of `ref.unit` in the manifest). `ref.config_history` count equals the manifest (feeders did not fire). Semantics: the dump is the truth; a seed row absent from the dump is absent after restore.
8. Separate `psql` invocations: `DELETE` and `\copy` are separate commands, as the `\copy` is a piped `psql -c`. A failure between them leaves a seeded table empty; the restore target is an empty database created for the restore, so the remedy is to drop it and restart (unchanged from the existing procedure).

## Consequences
- Fixes the duplicate-key failure of `ref.unit`; without it neither AC-DUMP-4 nor AC-DUMP-5 can pass, since both start with a restore (spec section 7). After the amendment they are expected to pass for this cause; they are not run here.
- Spec amendment (pending this ADR's approval): `docs/specs/public-dump-spec.md` section 6 step 3 gets the clearing action; section 7 AC-DUMP-4 gets the added check "non-empty tables after step 2 equal the pinned set and counts equal the manifest afterwards"; a change-log entry marks the amendment. The `restore-test` command ("runs exactly these [steps], nothing more", spec section 6) and `restore-test.yml` (section 7) run the amended step 3 unchanged otherwise: no new command, no new tool, no manifest or schema-file change, so the writer and `public-dump-manifest.schema.json` are unaffected.
- AC-DUMP-5 is unaffected in expectation: the restored `ref.unit` equals the dump's rows (order key: primary key), so the second dump gives identical `sha256_csv`.
- New test obligation: the pin test of point 5. Requires a plan task (Phase 3); not created here.
- Risk: `DELETE` on a seeded table in a database that someone restores into by mistake (not empty) would remove rows. Mitigated by the prerequisite "an empty database" (spec section 6) and the guard in point 3; there is no `WHERE` clause by design, since the dump replaces the whole table.
- Not covered: tables seeded outside migrations (config seed via `sync-config`) are not present after `schema.sql` and need no clearing.
- Reversal: if a future migration set grows many seeds, switching to a manifest `seeded_tables[]` field is a compatible additive change (minor format bump).

## Item 1 - loaded_at / load_cutoff (ADR-002, DDL, ingestion spec, workflows spec if tests live there)
ADR-002 (already inspected), insert after the "Latest and as-of access" bullet (line 38) and replace that bullet and the "Reproducibility of analytics" bullet (line 39):
- `curated.observation` gets `loaded_at timestamptz NOT NULL` = load transaction time, set by the loader, monotone per loader commit, never updated. Reason: known_at = fetch time, but an object fetched before a cutoff can be loaded after it (held-back successors, `decide` reloads keeping original known_at, day-4 catch-up), so `known_at <= known_cutoff` alone returns more rows when re-run later.
- `curated.fn_observation_asof(known_cutoff, load_cutoff default NULL)`: latest row per key with `known_at <= known_cutoff` AND (if given) `loaded_at <= load_cutoff`, excluding tombstones. Same two parameters for `v_observation_latest`-style as-of views.
- Analytics read with both; `analytics.run` records `load_cutoff` (= run start time) beside `known_cutoff`; rerun with recorded pair reproduces the result. Only-known_cutoff recomputation is labelled "what we would know now about then".
- Rebuild (consequence 44, item (7), line ~44): `loaded_at` is not replayed exactly; compare on natural key + values/status excluding `loaded_at` and Neon ids; load_cutoff reproducibility holds only on the live DB, a rebuilt DB reproduces only known_cutoff results.
DDL spec: add `loaded_at` column to curated.observation DDL; index consideration: existing as-of index on (series_id, ref_period_start, known_at) is kept; add `(loaded_at)` BRIN or btree on (series_id, loaded_at) only if the AC-OPS measurement shows the as-of function needs it (propose BRIN, cheap since loaded_at is monotone); update fn_observation_asof signature; analytics.run gets `load_cutoff timestamptz NOT NULL` (coordinate name with the analytics spec, which another agent owns). Block UPDATE of loaded_at (already covered by the append-only trigger; mention).

## Item 3 - published_decimals (ADR-002 line 30, ingestion spec comparison rule, DDL spec ref.series column and grants, unit test)
Replacement text for ADR-002 line 30 clause "(from the source's DECIMALS attribute, else observed in the first load)": derived as the MAXIMUM decimals over the FULL first-load history, parsed from the source text or the DECIMALS attribute (never from a trailing-zero-stripped JSON number), frozen once set, may only be INCREASED by an explicit logged change that raises an `ops.drift_event` (kind `precision_change`), never silently decreased. Same wording in the ingestion spec. DDL: column-level UPDATE grant on `published_decimals` stays, plus a BEFORE UPDATE trigger rejecting `NEW.published_decimals < OLD.published_decimals` and rejecting a change from NULL only when history is already loaded (NULL -> value is the initial set); the increase path writes the drift_event in the same transaction. Unit test: series history with coarse old values (0 decimals) and finer recent ones (2 decimals): published_decimals = 2; a revision of 0.004 on a value is NOT dropped (half unit = 0.005 would drop 0.004 only if decimals were 2... use a revision of 0.3 vs an assumed 0-decimal unit: |0.3| < 0.5 would be dropped under the wrong coarse rule, must be kept under the max rule with decimals 2 when delta >= 0.005).

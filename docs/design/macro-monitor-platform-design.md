## 1. Goals and non-goals

Goals
- G1 Automated monthly refresh (day 1) of the approved indicator set (about 80 active indicators, 28 core) for 42 countries plus EU27 and euro-area aggregates (and the global entity WLD for global series), history from 1991, running entirely on free web services (GitHub Actions public repo, Neon Free, GitHub Pages), no card on file.
- G2 Preserve every release and revision going forward (D10) in a bitemporal, append-only store; immutable raw archive with URL, fetch timestamp and SHA-256 (CLAUDE.md).
- G3 Series metadata on every series: source, series id, frequency, unit, seasonal adjustment, vintage/release date.
- G4 Respect source terms, rate limits, robots.txt; conditional requests; fail closed on web scraping.
- G5 Produce analysis-ready outputs for U1 (scorecards with percentile rank, coverage n/N, staleness, reference-period alignment), U2 (alerts), and a defined hand-off for U3 analysis in R.
- G6 Detect and report broken, late and drifting feeds with release-aware freshness, through GitHub Issues.
- G7 Everything testable offline (recorded bytes, Postgres container).
- G8 An interactive dashboard (U1) on the web, free, refreshed monthly: domain scorecards, peer comparison, time-series explorer, vintage/revision view and data-freshness status, served as a static site on GitHub Pages from exported files, with no live queries against Neon (ADR-010, ADR-008; section 8a).

Non-goals (this design)
- A live-query or server-hosted dashboard (Streamlit, Posit Connect Cloud, Shiny server, Grafana): rejected in ADR-010 for v1; reversible without pipeline change if the app reads the same exports.
- Browsing earlier snapshots of the dashboard (time travel) and user-saved views or accounts; as-of queries stay in Neon and the dump (ADR-002, ADR-003).
- Composite country rank (deferred by D6); imputation (forbidden by D16).
- Automated IMF downloads (D23); real-time vintage backfill (D10).
- Forecasting/nowcasting, forecast evaluation, probability alerts and the model layer: VERSION 2 (user decision 2026-10-25; section 0 item 5, ADR-011 `proposed`). R optional modules for U3 remain allowed.
- Paid services of any kind.

### 3.3 Run lifecycle (monthly, day 1, 04:23 UTC)
1. `plan`: warm Neon (retry), check schema version, `sync-config` (records config history: effective-dated mapping, ADR-009), choose due groups. Two kinds of work are planned: fetch groups, and load groups that include any backlog in the load queue (raw objects without an `ingest.raw_load` row). Open the draft raw release. `plan` does not touch staging.
2. `fetch` (matrix, up to 4 parallel; each leg has its own timeout, 300 minutes for the OECD group, BB28): per request run the change-detection ladder against the LATEST stored object of the request key; if changed: store new bytes if the content is new (hash first, upload asset, `raw_blob`), write the `raw_object` row and the run-scoped staging rows in one transaction, then update `request_state`. A source that reverts to earlier bytes is a new object (A -> B -> A). Each group isolated.
3. `load`: the load queue is every `raw_object` without a successful `raw_load`. The loader drains it per series group in strict `fetched_at` order (ties by `raw_id`), one transaction per object under a per-object advisory lock, appending a `raw_load` row (status, counts, `detail`) each time; `loaded_at` is read from the database clock after the lock is held (ADR-002); a mapped series seen for the first time gets its `ref.series` and `ref.series_map` rows in the same transaction (ADR-018); a failed or blocked predecessor holds back its successors for that group (see risk R33); objects found out of order across groups are recorded, not reordered; an older manual edition is refused (ORD-03). Then `analyze` (Python): takes the same lock briefly to read `known_cutoff`/`load_cutoff` from the database clock, then snapshot, ranks (full and published sets), scorecards (full and `scorecard_published`), alerts.
4. `r-analysis` (optional, non-blocking).
5. `finalize`: publish the raw release (becomes immutable), freshness, backlog and DB-size checks (including the 12-month projection), open/close issues, `export` (`mm_reader`; dashboard files and `export-status.json` as an artifact, validated), `record-export` (`mm_ingest` into `ops.export_status`), heartbeat, monthly public dump (the only profile; there is no full dump; gzipped CSV of the `pubdump` views, `schema.sql` and a hashed manifest, ADR-015).
6. `site` (after `finalize`; needs `export` success): build the static site from the export artifact and deploy to GitHub Pages. If export or build fails, the previous site stays live and a `pipeline` issue is opened.
7. Catch-up on day 4 re-fetches only failed or skipped groups and loads any unloaded raw objects from stored raw (no refetch), then republishes the site. Preflight on day 25 probes sources and reminds about manual downloads (WEO: 25 April and 25 October, after the expected releases; the configured window ends on the 24th and the reminder is on the preflight day itself, source-config rule 11; the window is Q41).
Everything is idempotent: a re-run with unchanged sources writes no new raw objects and no new observations, and re-exporting the same cutoff yields identical files (EXP-08). Concurrent `monthly-refresh`, catch-up, `ingest-manual` and `decide` runs are safe by construction (run-scoped staging, per-object load lock, ordering rules; workflows spec section 3).

### 3.4 Time, calendars and mixed frequency
- Native frequencies D/M/Q/A are stored as published; no resampling at rest. Reference period stored as `[ref_period_start, ref_period_end]`, so alignment and staleness use `ref_period_end` (age = run date - end). The dashboard shows each series at its native frequency; peer views compare latest values with their reference dates, staleness flags and a `reference_period_spread_days` per ranking (entities whose reference period lies more than the allowed lag behind the `rank_reference_period` are shown but unranked, flag `lagging`; B1; round 5: the earlier "outside the modal window" wording is withdrawn), never blended across frequencies without the flag (indicator selection risk 11).
- Fiscal-year and marketing-year bases (India/Australia/Japan fiscal years in WEO, agri balances) are a series attribute `calendar_basis`; calendarisation is an analytics transformation, not a storage change (not implemented in v1: such series are not used with GDP-denominator transforms).
- Daily market inputs are not ingested in v1: BIS provides monthly policy rates, exchange rates and REER (sources F9), consistent with "daily series aggregated to monthly".
- Semi-annual vintages (WEO April/October, AMECO) are annual observations with `vintage_label`; projection editions are stored per edition even when unchanged (ADR-002; the forecast store of ADR-011 is v2). Manual WEO files carry an edition date and are loaded in edition order (PROPOSED P22). The WEO group is a named-edition group (section 14c, ADR-017).
- Configuration history (B11): mapping (`ref.series_map`, `ref.inheritance_rule`) is effective-dated (`valid_from`/`valid_to` plus `recorded_at`; a change closes the old row and inserts a new one, ADR-009) and every change of the configuration tables, now including domains, entities and the source publication flags, is mirrored into the append-only `ref.config_history`; indicator parameters (windows, thresholds, targets) are also git-versioned and reproduced per analytics run through `git_sha` and `config_sha256`.

### 3.5 Currency basis, units, SA, base year
`ref.series` holds unit, multiplier, base period, price basis, currency and flow basis (period flow, annualised rate, stock; round 5, PROPOSED P18); `ref.indicator.currency_basis` (B1/B2/B3, D7) governs which transformations are allowed in `analytics`. Changes of unit/base/SA at the source create a new series version, never an in-place rewrite (ADR-002). Source-published SA is used; NSA series are only transformed by YoY; config validation requires `SA`/`SCA` for series feeding transforms that need seasonal adjustment (e.g. Eurostat `s_adj` `SCA`, not `CA`). The dashboard shows unit, base period and SA flag next to every series (taken from `meta/series.json`).

## 4. Data model (summary; normative DDL in `docs/specs/ddl-neon-schema.md`)

Entities: `ref.source` (with `archive_mode` and `publish_site`), `ref.entity` (42 countries + `EU27` + `EA` + `WLD` = 45 entities; aggregates `is_ranked = false`; `WLD` is `is_global` and carries global series), `ref.entity_group_member` (euro area with Bulgaria from 2026-01-01, G7, advanced/emerging), `ref.domain` (ranked flag, minimum coverage for rank; 11 domains since 2026-10-27: growth, prices, labour, external, fiscal, fin, social, structural, environment, agri, global), `ref.indicator` (catalog IDs M01...; `kind` indicator or input; generated flag `is_support`; `scope` country or global; priority; currency basis; staleness class; transform; alert method; `rank_mode` in `monotone_good | target_distance | descriptive_only` with no default; `good_dir` (0 for every non-monotone indicator); optional `display_dir` colouring hint; alignment parameters; resolved `stationarity_class` and `release_lag_aware`, ADR-014), `ref.indicator_domain`, `ref.indicator_input`, `ref.indicator_target`, `ref.series` (what a source publishes, immutable measurement attributes including `flow_basis`, `published_decimals`, `group_id`; created by the loader on first sight, ADR-018), `ref.series_group` (per source group: `reestimating`, `compare_mode`, materiality, `snapshot_mode`, `max_revised_rows`, `edition_ordered`; `reestimating` and `edition_ordered` exclude each other), `ref.series_map` (headline / fallback / comparison; effective-dated; ADR-009), `ref.inheritance_rule` (euro-area inheritance), `ref.global_translation` (WLD to per-country, deferred).

Support indicators (B5), single list: indicators with `kind = 'input'` (`is_support = true`; support indicators and input indicators are ONE set) are mapped like any series but never ranked, alerted, put in a domain or shown as scorecard indicators or in dashboard files (they are never snapshotted by analytics, so they appear in no published table and carry no `publish_scope`; the scope `excluded` is only for withheld pairs, export spec section 1a; second fix pass: they are exported in no file at all, export spec principle 4). Transforms such as `SUM12_PCT_GDP` and reserve cover use them under a fixed alignment rule (latest four-quarter sum, else latest annual, matching currency, period-flow quarters only; analytics spec section 3, fail closed). Current list and naming (reconciled in round 5; the user decided on 2026-10-18 that X01-X03 are added to the config seed, section 14a):

| Meaning | This document, ADR-009 | DDL spec | Analytics spec |
|---|---|---|---|
| Nominal GDP, local currency | X01 | X01 (usage `denominator_gdp_lcu`) | X01 (section 3 table: the default denominator of `SUM12_PCT_GDP`) |

X01-X03 are not in the approved indicator selection; the user decided to add them to the config seed (section 14a, item 2); the selection document itself is not edited. Their sources are a required research follow-up (Q22, Q32).

Global series (B6): scope `global` indicators (M24 and similar) are stored for `WLD` only, are not in the per-country snapshot, ranks or scorecards (the per-country snapshot covers 44 entities: 42 countries and 2 aggregates), and appear in the explorer under the informational group `global` (`publish_scope = info_only`). Per-country translation of commodity prices into local currency needs the exchange rate (M16) and is specified as a transform (`GLOBAL_LCU_YOY`) but deferred (Q23).

Time dimensions: valid time = reference period; knowledge time = `known_at` (our fetch time, authoritative) plus `source_release_at` (source's timestamp, nullable) plus `vintage_label` (named editions such as `WEO-2026-10`); transaction time = `loaded_at` (clock read under the load lock, ADR-002).

Vintage semantics (D10): first fetch of a series stores its entire history with `load_kind = initial` (revised data, not real time; labelled so for backtests). Later fetches insert rows only when a value or status changes beyond the group's comparison tolerance (published precision, relative epsilon) and, for `reestimating` groups, beyond the materiality threshold: `new_period`, `revision`, `tombstone`; revisions of re-estimation families are labelled `revision_class = 'reestimation'`. A value that the source itself publishes as missing, confidential or not available is stored as `value_status = 'MISS'` with `value` NULL (round 5); it is distinct from our tombstone `DEL`, is returned as NA, and is never ranked or alerted. Projections carry `value_status = PROJ` and are excluded from ranks and alert windows by view design (and from dashboard v1 files, including the revision files: a projection edition is a new forecast, not a revision, DDL I-CUR-11); in v1 A03 has no dashboard output and M24 appears only in the explorer (B9). Archive imports of older manual editions (PROPOSED P22) carry `load_kind = 'import'` and are never "latest".

Alerts, ranks, scorecards, snapshots are per-run tables in `analytics` (not persisted as full transformed series), computed twice: a full set (internal) and a published set (`indicator_rank_published`, `scorecard_published`, published alerts) restricted to publishable (indicator, entity) pairs, with `publish_scope` on each row (A8). Coverage n/N (D16, counting only rank-oriented indicators) and staleness (D14) are columns of the snapshot and scorecard tables. Each analytics run stores the git sha and hashes of config, mapping and overrides (B11) and its two cutoffs read from the database clock. The dashboard export adds no tables to Neon; its status is recorded by `mm_ingest` from the export artifact into `ops.export_status`.

Ranking semantics (analytics spec section 4; all proposed defaults, user to confirm): `rank_mode = monotone_good` indicators are percentile-ranked by `good_dir`; `target_distance` indicators are ranked on absolute deviation from a configured target (B2); `descriptive_only` indicators (proposed: inflation until target metadata exists, current account, policy rate, REER, exchange rate; classification table in analytics spec section 4.1, Q28) show values without percentiles. Euro-area-inherited values are computed and flagged and are EXCLUDED from percentile ranks (Q7, decided 2026-10-27). The percentile is the mid-rank `(W + 0.5 * T) / n` with `T` counting the entity itself (PROPOSED P21, worked example in analytics spec 4.3). Reference period (B1): the `rank_reference_period` is the latest period for which `rank_period_coverage_pct` (proposed 70, an integer percent, position `(pct * n + 99) // 100`) of the candidates have data; entities more than `max_lag_vs_rank_period` (92/190/366 days for M/Q/A) behind it are `lagging` and unranked, later entities are `ahead` and ranked; `reference_period_spread_days` (max minus min `ref_period_end` among ranked entities) is stored in `analytics.indicator_alignment` and always exported. Coverage threshold (B8): a domain whose n_available/n_defined falls below `min_coverage_for_rank` (proposed 0.5) shows its figure and n/N but no rank position; the domain figure is the "mean percentile of the domain's indicators" (not uniformly distributed, not a percentile of the domain; column name `percentile_rank` kept); a domain with fewer than 3 ranked indicators is `descriptive_only` (P3); Agri-food (D12) and Global (B9) are informational and unranked (the former Markets domain, B3, was dropped on 2026-10-27).

Comparison series (A02b OECD, A02c EC) are stored like any series but mapped with `role = comparison` so they cannot enter the A02 ranking (D18) or the dashboard files. A02 headline is the IMF WEO series (25 of 42 countries, D22).

Capacity (analyst estimate, unmeasured; normative arithmetic in DDL spec section 9; row size corrected in round 4 and propagated in round 5): about 2,000-3,500 series, about 0.5 M observation rows at first load, base case about 20 k rows/month later at about 220-300 bytes per row including indexes, about 110-150 MB at first load and 60-70 MB/year after, against the 1 GB Neon limit. The earlier re-estimation estimate (about 1.1 M rows/year, assuming only 3 years of SA history revised, about 240-330 MB/year at the corrected row size) was too weak. Worst case: about 1,300 SA monthly series x 400 observations whose whole history is re-estimated at each release changes most keys: about 520 k rows/month = about 6.2 M rows/year = about 1.7 GB/year exact (1.4-1.9 GB at 220-300 bytes), exceeding 1 GB within the first year [analyst reasoning]; OECD CLI and the BIS gap behave similarly by construction. Exact insert-on-change is therefore not viable for such groups. Decided mitigation (ADR-002): groups with `reestimating: true` and `snapshot_mode: diff_above_tol` (default for SA/model-estimated groups) keep the full vintage as an immutable Parquet snapshot in the raw release (outside Neon) and load into Neon only keys moved beyond the materiality tolerance (proposed relative 0.001, with an absolute floor of half a unit of the last published digit, the comparison rule) plus new periods; if 5-15 % of keys cross the tolerance (assumed), the SA worst case becomes about 26-78 k rows/month = about 80-250 MB/year. Spike AC-OPS-8 measures the share on the first three releases per group. Guards: DB-02 (700/900 MB and 12-month projection), DB-05 (rows per object), REV-06 caps; retention policy is Q18. Staging is run-scoped and deleted after load (peak below 200 MB by whitelist filtering). Dashboard `data/` about 5-15 MB against the 1 GB Pages limit (budgets in the export spec).

Key operating rules
- Secrets: GitHub Actions secrets exposed only to the step that needs them; one Neon role per purpose (five: owner, `mm_ingest`, `mm_analytics`, `mm_reader`, `mm_r`); fork PRs get no secrets; no `pull_request_target` on PR code; actions pinned by SHA; minimal `permissions`; dispatch inputs only through `env`, never interpolated into `run:` scripts. The `site` job has no database secret (it receives the export as a workflow artifact) and only `pages: write` and `id-token: write`; the `export` step has only `NEON_URL_MM_READER` (strictly read-only; there is no export-specific role or secret); `record-export` has only `NEON_URL_MM_INGEST`. The artifact quota (Free 500 MB, [DOC] limits page) is far above the export size. `RAW_PRIVATE_TOKEN` is inactive (no private repository). The production workflows set `MM_ENV=production` and `MM_RAW_STORE=release_public`, so the local-directory raw store cannot be used in production.
- Concurrency: `concurrency` group per workflow with `cancel-in-progress: false`; because different workflows overlap, safety is in the database: run-scoped staging that nothing truncates, a Postgres advisory transaction lock per raw object in the loader (also taken briefly by the analytics step to read its cutoffs), ordering rules per series group, and a migrate lock (GitHub keeps only one pending run per group, so it cannot be the only guard). The Pages deployment uses its own concurrency group so a catch-up run cannot overlap a refresh deployment [UNVERIFIED: exact mechanism of the deploy action].
- Failure alerting: Issues via `GITHUB_TOKEN` (`issues: write`), deduplicated by title key, auto-closed on recovery; also an `if: failure()` step per job.
- Runner time and quota: public repo, standard runners free [tooling research]; expected fetch matrix 1-2 h wall clock dominated by the OECD budget (analyst estimate; OECD leg timeout 300 minutes, BB28); each job far below the 6 h limit; export plus site build is minutes (analyst estimate); if the repo ever becomes private, re-budget against 2,000 min/month and note that Pages availability for private repos on Free is [UNVERIFIED].
- Scheduling hazards and the 60-day rule (R1; workflows spec section 9 is authoritative): minute 23/41 (not on the hour), delay/drop tolerated by the catch-up run. The earlier "self-enable" API call was withdrawn as "circular"; that holds only after disablement, and a preventive call is restored as rung (a0) (round 3). Fallback ladder, successive safety nets: (a) monthly heartbeat commit of `ops/heartbeat.json` (an [UNVERIFIED] reset of the inactivity clock; whether `GITHUB_TOKEN` can push to a protected `main` is also [UNVERIFIED], BB26); (b) a documented human check on the 2nd of each month, the only level independent of GitHub's scheduler; (c) an optional external dead-man ping, not adopted (Q15). Detection independent of any scheduled workflow: the dashboard's stale banner (data older than 45 days by the manifest's `known_cutoff`, evaluated in the visitor's browser) and the human check. AC-OPS-4 is time-boxed (days 7, 55, 65, 125; section 11).
- Neon: first connection per job retries with backoff (cold start); writers use the direct endpoint; compute budget well below 100 CU-hours because no live queries hit Neon (visitors never touch Neon), to be measured (AC-OPS-6); DB-size check at 700 MB with a 12-month projection; the monthly public dump and quarterly restore test as the real backup (6 h history is not one); sources outside the public/public partition have no dump (Q46); the dump does not contain `analytics.*` tables (ADR-015).

## 7. Validation and monitoring (detail: `docs/specs/validation-monitoring-spec.md`, ADR-007)
- Layers: RAW, PARSE (pandera), META (DB constraints + `expect` drift check + clock skew META-05), SEM, REV (tolerance, materiality, mass revision, expected re-estimation, named editions), COMP, COV (stale-on-arrival diagnostic), ORD/LOAD (order and backlog, older manual editions ORD-03), FRESH, DB, BKP (BKP-01 inactive, BKP-02 lists unbacked sources, BKP-03 dump self-check). Severity `error` blocks the object, `warn` loads and alerts, `info` records. The export adds EXP-01..EXP-10 (export spec section 10), failing the `export` step (and so the deployment) on error.
- Revision materiality (REV): per raw object the check family is chosen once, by the group. A group with `reestimating: true` goes through REV-06 (loads material revisions labelled `reestimation`, `info`, blocks above `max_revised_rows`); a named-edition group (`edition_ordered: true`, `reestimating: false`, the IMF WEO group; ADR-017) goes through REV-07 (report only: it loads, never blocks and raises no drift event); any other group goes through REV-01 (mass revision above 20 % of keys materially revised blocks the object). All three count only material revisions; round 5: a revision is material when it is a revision under the loader's comparison rule, that is above half a unit of the derived `published_decimals` (and above the group's materiality where set); non-material differences are REV-05 noise. The class decision and counts are stored in `raw_load.detail`.
- Re-estimation events (unit/base/classification change, mass revision in a group with neither flag) never rewrite history; they open an `ops.drift_event` and require a human decision (new series version + mapping change); after an accepted decision the blocked object or deferred series loads from stored raw.
- Freshness (feed health) is release-aware: expected latest period from frequency, typical lag, tolerance, optional explicit calendar. It is separate from ranking staleness (D14 limits, user-approved and unchanged), which is computed in analytics and never deletes data. A coverage diagnostic (COV-01) reports per indicator the share of entities that are stale on arrival, as a warning for the user to reconsider limits; round 5 (PROPOSED P20): only entities whose latest period arrived after launch (not `initial`) qualify, the number of qualifying entities is reported, and the dashboard shows "not yet measurable" until enough post-launch periods exist; A12, A14 and A22 are known risk [UNVERIFIED]; the `release_lag_aware` staleness is on for a named list of indicators, the list pending the user (plan OQ-10; a row-by-row proposal is in `docs/specs/release-lag-and-split-proposal.md`, not decided), with the global default false (Q31). Both feed health and ranking staleness are shown on the dashboard (feed health on the status view, ranking staleness on scorecards).
- Alerts: GitHub Issues; the dashboard status view shows last run time, group states and the unloaded backlog; heartbeat file. Residual risk: a silently disabled schedule is noticed by the human via the stale-data banner or the monthly check (no external watchdog added unless the user chooses one).
